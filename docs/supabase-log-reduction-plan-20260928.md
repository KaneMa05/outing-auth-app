# Supabase 로그 수집량 절감 기획

작성일: 2026-09-28. 상태: 기능·주기 보존을 우선한 서버 요청 통합을 구현·검증했고, 사용자 승인 후 운영 DB에 적용했다. 서버 푸시·배포 진행.

최종 구현 범위와 검증 결과는 [반영 검토서](releases/20260928-supabase-log-reduction.md)를 따른다. 정상 heartbeat는 6회 → 1회, 보상 동기화는 잠금 순서를 보존하기 위해 3회 → 2회다. 전체 만료 좌석 정리 분리, 정기 갱신 간격 확대, 보상 확인 주기 변경은 이번 구현에 포함하지 않았다. 아래 확장안의 모든 항목을 적용했다는 의미는 아니다.

## 권장 방향

스터디카페 접속 유지(heartbeat)의 DB 요청 통합을 가장 먼저 진행한다. 이어서 보상 동기화 중복 제거, 일시 장애 후 조회 경로 복구를 적용한다. 실시간 화면 갱신 조정과 전체 만료 좌석 정리 분리는 후속 단계로 둔다.

사용자가 공부하는 동안 30초마다 접속을 확인하는 동작은 유지한다. 같은 작업을 처리하기 위해 여러 번 오가는 서버 요청을 줄이는 것이 첫 목표다. 화면 디자인이나 학습·보상 규칙 변경은 포함하지 않는다.

## 확인한 근거와 한계

- 첨부 화면: 결제 기간 수집량 16.68GB / 포함량 20GB. 보관 용량이 아닌 기간 누적 수집량이다.
- 최신 공식 페이지: 2027년 초까지 과금 유예, 유료 플랜 포함량 20GB, 이후 초과 1GB당 $0.50. 검색 도구의 과거 문서에는 5GB가 남아 있었으나 직접 연 최신 페이지는 20GB였다.
- 운영 앱 RONPARK APP의 2026-09-27 00:00~2026-09-28 00:00 UTC, 즉 한국 시간 9월 27일 09:00~28일 09:00를 읽기 전용으로 집계했다.
- 전체 311,211건 중 API 게이트웨이 로그 301,772건(약 97%). 이는 건수 비중이며 바이트 비중은 측정하지 않았다.
- 첨부 사용량 화면이 조직 전체 합계인지 프로젝트 필터 결과인지는 확인하지 않았다. 다른 프로젝트 사용량까지 이번 앱의 개선 효과로 계산하지 않는다.

| 주요 API 경로 | 해당 24시간 요청 수 |
| --- | ---: |
| 스터디카페 좌석 `study_cafe_presence` | 71,174 |
| 기기 검증 `validate_student_device` | 43,779 |
| 학생 조회 `students` | 43,560 |
| 학습 세션 `study_cafe_sessions` | 32,134 |
| 카페 화면 데이터 `get_study_cafe_snapshot_data` | 11,046 |
| 봇 외형 `study_cafe_bot_appearance` | 11,041 |
| 학습 포인트 정산 `award_study_cafe_time_points` | 10,259 |
| 보상 동기화 `sync_student_rewards` | 9,037 |

이 경로들은 여러 기능이 공유한다. 각각을 전부 heartbeat나 특정 화면의 호출로 간주하지 않는다. 상위 경로에서 반복 오류가 대량 발생한 정황은 없었다.

DB는 연결·연결 해제 로그와 전체 실행 시간 로그가 꺼져 있고, `log_statement=ddl`, `log_min_messages=warning`, `pgaudit.log=none`이었다. DB 상세 로그 축소보다 API 요청 절감의 우선순위가 높다.

## 1순위: heartbeat DB 요청 통합

### 현재

공개 좌석의 정상 heartbeat는 다음 6회 호출이다. 기존 `tests/study-cafe-api.test.js`에도 6회 호출을 확인하는 검증이 있다.

1. 기기 토큰 검증
2. 활성 학생·수강생 유형 조회
3. 전체 만료 좌석 조회 및 필요한 정리
4. 본인 학습 세션 조회 및 필요한 학습일 전환
5. 본인 좌석 조회
6. 접속 시각 갱신

### 1차 변경안

기기 검증, 학생 조회, 기존 만료 좌석 정리 순서를 유지한다. 4~6번을 서버 전용 DB 함수(RPC) 하나로 묶어 정상 공개 좌석 경로의 Supabase HTTP 요청을 **6회 → 4회**로 줄인다. 날짜 전환과 사설 방 좌석 처리도 함수의 동작 계약에 명시한다. 만료 좌석 처리·푸시가 발생하는 경우의 전체 호출 수는 별도 측정한다.

외부 요청 수는 이 경로에서 약 33% 감소한다. 1시간 동안 정상 heartbeat 120회가 발생하는 예시에서는 DB HTTP 요청이 720회에서 480회로 줄어든다. DB 내부 SQL 실행 횟수나 전체 로그 GB가 같은 비율로 줄어든다는 의미는 아니다.

### 유지할 동작과 설계 조건

- 30초 확인 주기, 화면 비활성화 시 처리, 자동 일시정지·복귀 흐름을 유지한다.
- 기기 등록 해제, 비활성 학생, 접근 불가 유형의 거부를 매 요청마다 유지한다.
- 공부 중/일시정지/착석 상태별 시각 처리, 새벽 4시 학습일 전환과 순공시간 계산을 보존한다.
- 공개 좌석과 사설 방 좌석을 함께 검증하며, 좌석이 없으면 기존 오류 계약을 유지한다.
- heartbeat와 퇴실·일시정지·날짜 전환이 동시에 발생해도 세션 중복 생성, 좌석 부활, 시간 중복 적립이 없어야 한다.
- RPC는 서버 전용 호출로 제한한다. 기본 PUBLIC 실행 권한과 anon/authenticated 접근을 제한하고 SECURITY INVOKER를 우선한다. 클라이언트가 보낸 학생 ID만으로 권한을 인정하지 않는다.
- 잠금은 본인 관련 행에 짧게 적용하고 푸시·외부 HTTP 호출은 트랜잭션 밖에 둔다. 기존 처리와 잠금 순서를 검토한다.
- DB 쓰기 결과를 알 수 없는 timeout 뒤 기존 쓰기 경로를 자동 재실행하지 않는다. 요청 재실행의 안전성 또는 상태 재확인을 검증한다.

대상: `api/study-cafe.js`, 추가 DB migration, 관련 API·DB 동작 테스트. 사설 방 API 자체의 별도 heartbeat 통합은 이 경로 검증 후 별도 적용한다.

## 2순위: 보상·포인트 중복 조회 제거

현재 성공한 스터디카페 요청은 heartbeat까지 포함해 보상 동기화를 예약한다. 60초 제한과 중복 실행 방지는 있으나, 공부 보상이 새로 발생할 가능성이 없는 상태에서도 예약 경로가 호출된다. 인터넷 수강생의 전체 카페 조회에는 별도 포인트 정산과 장비 조회도 붙는다.

변경안:

- heartbeat 성공과 보상 동기화를 직접 연결한 부분을 제거하되, 기존 주기 동기화와 필수 이벤트 경로를 먼저 보존한다.
- 첫 홈 방문 보상, 공부 종료·일시정지·퇴실 후 확인, 화면 복귀 시 누락 복구, 상점 구매 직전 잔액 정산을 유지한다.
- 후속으로 서버가 계산한 다음 보상 확인 시점과 미수령 알림 상태를 활용해 불필요한 정산을 줄인다. 클라이언트 시계로 지급 여부·금액을 결정하지 않는다.
- 30분 학습 포인트와 가입·연속 학습 보상의 조건을 구분한다. 한 보상의 완료 상태로 다른 적립까지 중단하지 않는다.
- 기존 응답의 잔액·장비 정보 재사용은 최신성 조건을 정의한 뒤 적용한다. 구매·착용·기기 변경 직후는 다시 확인한다.
- 기존 보상 표시 지연보다 악화되지 않도록 검증한다. 필요 시 동기화 시점 최적화는 후속으로 분리한다.

대상: `app.js`의 카페 API 성공 후 처리, `student-rewards.js`, 필요 시 `api/student-rewards.js` 및 보상 RPC. 보상 코드가 공통이므로 오프라인 수강생의 첫 홈 방문 보상도 회귀 검증한다.

## 3순위: 일시 장애 후 효율적인 조회 경로로 복귀

현재 카페·사설 방의 화면 조회 RPC가 한 번 실패하면 해당 서버 프로세스에서 지원 플래그가 계속 false로 유지된다. 카페에서는 이후 단일 조회가 여러 개의 개별 조회로 바뀔 수 있다. 실제로 이 경로가 차지하는 사용량은 아직 측정하지 않았다.

- 함수 미설치·응답 형식 불일치·일시적 네트워크/DB 오류를 구분한다.
- 읽기 fallback은 유지하되 일정 대기 후 단일 요청만 RPC 재확인을 하도록 한다. 시작값은 60초, 반복 실패 시 최대 5분까지 늘리는 안으로 검증한다.
- 동시 재시도를 합치고 반복 경고는 요약한다. 운영자가 오류를 파악할 수 있는 기록은 유지한다.
- 재시도 정책은 읽기 경로에 적용한다. 저장·정산·구매 요청의 무조건 재실행에는 적용하지 않는다.

대상: `api/study-cafe.js`, `api/study-cafe-rooms.js`, 기존 RPC fallback 테스트.

## 후속 단계: 다른 사람의 변경 알림에 따른 전체 재조회 축소

현재 공개 카페는 실시간 메시지를 350ms 동안 모은 뒤 전체 화면 데이터를 재조회한다. 그보다 간격이 긴 메시지는 전체 조회를 반복할 수 있다. 사설 방에도 별도 실시간 갱신 예약 경로가 있다.

- 본인 입실·퇴실·타이머 조작과 화면 복귀는 즉시 확인한다.
- 다른 사람의 변경으로 발생한 조회만 모은다. 시작안은 최대 약 2초 이내 갱신이며, 연속 이벤트가 와도 마지막 상태가 반드시 반영되도록 대기 상한을 둔다.
- 진행 중 조회는 공유하고, 그 사이 들어온 변경은 완료 후 최대 한 번 추가 반영한다. 오래된 응답이 새 상태를 덮어쓰지 않게 한다.
- 2분 안전 조회와 연결 장애 시 복구 조회는 유지한다.
- 전체 재조회 대신 좌석·프로필 등 필요한 데이터만 받는 방식은 다음 확장안으로 둔다.

사용자에게 타인 상태의 반영 지연이 생길 수 있어 1차 배포 범위에서 분리한다. 2초는 확정 요구사항이 아닌 검증할 제안값이다.

## 후속 단계: 전체 만료 좌석 정리의 중복 실행 제한

매 사용자 요청에서 전체 만료 좌석을 확인하는 구조를 줄일 여지가 있다. 다만 좌석 반납, 종료 시간 보정, 자동 퇴실 푸시를 함께 처리하므로 첫 단계에는 유지한다.

후속 기획에서는 서버 인스턴스 간 공유되는 실행 제어 또는 기존 작업 스케줄을 검토한다. 프로세스 메모리 플래그만으로 중복을 막는 방식은 충분하지 않다. 정리 작업의 최대 지연, 장애 시 복구, 좌석 선택 시 즉시 만료 확인, 푸시 중복 방지 기준을 먼저 정한다. DB 함수 통합 후 이 부분까지 바꾸어야 더 낮은 요청 수를 목표로 할 수 있다.

## 화면 범위

- 주요 변경 대상: 온라인 관리반·인터넷 수강생의 스터디카페 내부 요청 처리.
- 오프라인 수강생·교사·관리자 화면의 UI와 기존 동작은 유지한다.
- 공통 인증·보상 함수의 기존 계약은 유지하며, 해당 공통 코드 변경 시 모든 수강생 유형을 확인한다.
- 기존 작업 중인 파일을 덮어쓰지 않고 변경을 분리한다. OX·성적 등 다른 기능 개선은 포함하지 않는다.

## 성공 기준과 확인 방법

| 항목 | 확인 기준 |
| --- | --- |
| 정상 공개 좌석 heartbeat | 동일 조건에서 Supabase HTTP 6회 → 4회 |
| 학습 기록 | 공개/사설 방, pause/resume/stop, 새벽 4시 전환에서 시간 누락·중복 없음 |
| 동시 처리 | heartbeat와 퇴실·정리·날짜 전환 경합에서 좌석/세션 일관성 유지 |
| 권한 | 해지 기기·비활성 학생·다른 학생 요청 거부, RPC 직접 접근 차단 |
| 보상 | 첫 방문·30분 적립·연속 학습·구매 잔액의 누락·중복 없음 |
| 장애 복구 | 일시 RPC 오류 이후 단일 조회 복귀, 재시도 폭주 없음 |
| 사용자 체감 | 조작 성공률·응답 지연이 개선 전보다 악화되지 않음 |
| 실제 비용 효과 | 같은 프로젝트·유사한 활성 학습 시간당 API 요청 수와 로그 GB 비교 |

현재 건수로 전체 GB 절감률을 확정하지 않는다. 정상 heartbeat의 경로별 목표부터 검증한 뒤 전체 사용량을 측정한다. DB 함수 통합이 잠금 대기나 DB 부하를 증가시키면 요청 수 목표만으로 채택하지 않는다.

로컬 API mock 테스트뿐 아니라 격리된 DB에서 날짜 전환·동시 실행·권한·재시도 결과를 확인한다. 운영 학생 데이터에 쓰기 테스트를 하지 않는다. 기존 학습 기록·좌석 정리·푸시·보상·기기 검증 테스트와 빌드를 통과한 후 배포 검토한다.

승인된 운영 적용 후 24~48시간 초기 추세, 이후 유사한 요일을 포함한 3~7일을 비교한다. 트래픽 변화와 다른 프로젝트 사용량을 구분한다. 자동 로그 조회를 반복하는 감시 루프를 새로 만들지 않고, 짧은 기간의 집계와 기존 사용량 화면으로 측정한다.

## 구현·적용 순서

1. 현재 계약을 검증하는 테스트와 기준 호출 수를 정리한다.
2. heartbeat 통합을 독립 변경으로 구현하고 로컬·격리 DB에서 검증한다.
3. 보상 중복 조회 제거와 읽기 fallback 복구를 각각 검증한다. 단계를 나누어 효과를 구분한다.
4. 기존 함수와 응답 계약을 보존한 추가형 DB 변경, 서버 코드, 복구 절차를 준비한다.
5. 사용자에게 구체적인 변경·검증 결과를 제시하고 운영 DB 반영·푸시·배포의 최종 확인을 받는다. 이번 기획 요청은 운영 적용 승인이 아니다.
6. 승인된 순서로 DB 호환 변경 → 서버 코드 적용 → 운영 확인을 진행한다. 문제가 있으면 이전 서버 코드로 복구할 수 있도록 기존 경로를 보존한다. 결과 불명의 쓰기를 자동 fallback하지 않는다.
7. 실제 사용량을 확인한 뒤 실시간 조회 조정과 만료 좌석 정리 분리의 필요성을 결정한다.

## 추가 절감안 — 최종 목표를 정상 heartbeat 1회로 확대

사용자의 추가 절감 요청에 따른 확장 기획이다. 앞의 6회 → 4회는 변경 범위를 작게 잡은 중간안이다. 최종 목표는 **정상 heartbeat의 Supabase HTTP 요청 6회 → 1회**로 상향한다. 중간안을 반드시 별도 운영 배포할 필요는 없다. 로컬에서 단계별 검증 후 완성된 범위로 배포 검토한다.

### A. 인증부터 접속 갱신까지 서버 전용 RPC로 통합

서버가 해시한 기기 토큰과 학생 식별자를 받아 기기 유효성, 학생 활성 상태·유형, 본인 좌석·세션, 학습일 전환, 접속 갱신을 하나의 RPC에서 처리한다. 인증 결과를 캐시하거나 생략하지 않고 매 요청 검증한다. 기존 기기 검증의 레거시 기기 전환·등록 제한·폐기 기기 처리 계약을 유지한다.

RPC는 서버 역할만 실행할 수 있도록 제한한다. 기기 검증이 실패하면 학습·좌석 갱신을 수행하지 않는다. 현재 검증 함수의 advisory lock과 학생 행 잠금이 통합 트랜잭션 내에서 더 오래 유지될 수 있으므로, 날짜 전환·퇴실·기기 폐기와의 잠금 순서 및 대기 시간을 반드시 확인한다. 운영 함수 정의와 로컬 정의의 차이는 구현 전에 대조한다.

전체 타인의 만료 좌석 정리는 아래 B로 분리한다. 본인의 좌석이 이미 만료됐는지 여부는 접속 시각을 덮어쓰기 전에 판정해야 한다. 기존 조건으로 만료된 좌석을 heartbeat가 되살리지 않도록 한다.

정상 heartbeat 120회/시간의 예시: 현재 DB HTTP 720회 → 중간안 480회 → 통합안 120회. 최종안의 이 경로 절감은 약 83%다. 브라우저→앱 서버의 heartbeat 120회는 그대로이고, 별도 정리 작업·푸시·예외 처리의 요청은 이 계산에 포함하지 않는다. 전체 로그 GB나 전체 서비스 요금 83% 절감을 의미하지 않는다.

### B. 전체 만료 좌석 정리를 사용자 수에 비례하지 않게 변경

매 heartbeat·조회마다 전체 좌석을 정리하는 대신, 실행권을 공유하는 한 작업이 일정 주기로 묶어 처리하도록 한다. 시작안은 30~60초 단위이며 기존 만료 기준과 사용자 체감 지연을 검증하여 확정한다. 단순히 heartbeat에서 정리 코드를 제거하는 것으로 끝내지 않는다.

- 공개 카페와 사설 방의 만료·순공시간 보정 규칙을 각각 보존한다. 두 경로의 현재 규칙을 임의로 통일하지 않는다.
- 새 좌석 선택, 본인 heartbeat, 복귀 시에는 관련 좌석의 유효성을 즉시 확인한다.
- 마지막 유효 활동 시각을 기준으로 시간을 정산한다. 배치 실행이 늦어진 시간을 공부 시간으로 추가하지 않는다.
- DB 내부 정리와 푸시 발송을 분리하고, 발송 대상을 영속적으로 기록해 재시도 누락·중복을 방지한다.
- 스케줄 중단·실행 중 장애·중복 실행·같은 좌석 동시 갱신을 검증한다. 기존 정리와 새 정리를 동시에 무제한 실행하지 않는다.
- 새 작업의 호출 수와 실행 비용을 총 절감 계산에 포함한다. 공유 타이머나 실행 기록 관리 비용도 측정한다.

### C. 정기 전체 조회를 변경 알림 중심으로 전환

사설 방은 현재 실시간 연결 상태에서 15초, 연결 불가 상태에서 4초 간격으로 재조회를 예약한다. 조회 완료 후 다음 주기를 예약하므로 실제 요청 수는 응답 시간에 따라 달라진다. 공개 카페에는 별도의 실시간 전체 조회와 2분 안전 조회가 있다.

우선 사설 방의 입퇴실·좌석·채팅·삭제·강퇴·방 폐쇄·프로필 등 모든 표시 변경에 알림이 있는지 확인한다. 현재 전역 연결 플래그만으로 해당 방의 알림 수신이 정상이라고 판단하지 않는다.

알림 수신과 재접속 복구가 검증된 방에 한해 정기 안전 조회를 15초 → 60초로 늘리는 안을 적용한다. 다른 이벤트가 없고 응답 시간을 무시한 단순 계산에서 정기 조회 부분이 시간당 240회 → 60회로 약 75% 감소한다. 이벤트에 따른 조회와 heartbeat는 별도이므로 전체 방 트래픽의 75% 절감을 뜻하지 않는다.

본인 조작은 즉시 반영하고, 알림 누락 가능성이 있는 재연결·화면 복귀에는 최신 전체 상태를 확인한다. 연결 장애 시 4초 fallback을 바로 느리게 바꾸지 않는다. 연속 오류가 발생할 때만 점진적 대기와 무작위 지연을 적용하는 안을 검증한다. 채팅·강퇴·새 좌석 상태의 허용 지연을 만족하지 못하면 기존 간격을 유지한다.

후속으로 공개 카페의 상태 변경 알림에 필요한 최소 변경 데이터와 버전을 포함하여 전체 재조회를 줄일 수 있다. 학생 개인정보·잔액·기기 정보는 공개 채널에 넣지 않는다. 순서 역전·중복·버전 누락 시 전체 상태로 복구한다. Broadcast 사용량이 증가할 수 있으므로 Realtime 메시지·전송량 비용까지 비교한다.

### D. 응답에 필요한 작은 결과를 함께 전달하고 변경 없는 데이터 재사용

- heartbeat 응답에 다음 보상 확인 시점 등 필요한 작은 결과를 포함해 별도 조회를 줄인다. 보상 지급은 서버 규칙에 따라 필요한 시점에만 계산하며, 모든 heartbeat마다 무거운 정산을 실행하지 않는다.
- 본인 조작 응답에 이미 확정된 좌석·세션·잔액 등을 포함하여 동일 정보의 직후 재조회가 꼭 필요한지 줄여 나간다.
- 봇 외형·상품 목록처럼 여러 사용자에게 공통이고 변경이 드문 데이터는 짧게 재사용한다. 개인 잔액·인증·좌석 소유권과 혼합 캐시하지 않는다.
- 다른 사람 좌석 갱신 때마다 본인 장비·과목·할 일을 다시 읽지 않도록 데이터 갱신 범위를 나눈다. 변경 이벤트 누락 시 복구와 구매·착용 직후 무효화가 필요하다.
- 서버리스 인스턴스의 로컬 캐시는 인스턴스마다 따로 존재하므로 효과를 보장하지 않는다. 별도 유료 캐시 도입은 먼저 실제 효과를 측정한 뒤 판단한다.

### E. DB 내부 쓰기 감소는 보조 과제

로컬 `validate_student_device` 정의는 검증마다 `last_used_at`과 클라이언트 정보를 갱신한다. 유효성·폐기 여부는 매번 읽되, 표시용 최종 사용 시각의 쓰기만 예를 들어 1~5분 간격 또는 정보 변경 시로 줄이는 안이 있다. 이는 기기 목록의 시각 정확도, 기기 정책에서 해당 시각을 사용하는지 확인한 뒤 결정한다.

이 변경만으로 API 요청 로그 수가 줄어들지는 않는다. 주된 목적은 DB 쓰기·잠금 부담 완화이며, 이번 로그 절감의 최우선 작업으로 계산하지 않는다.

### 수정된 권고 순서

1. **정상 heartbeat 1회 통합 + 만료 좌석 정리 분리**를 하나의 완성된 목표로 구현·검증한다. 매 요청 인증과 30초 주기를 보존한다.
2. **보상 중복 조회와 응답 직후 재조회 감소**, 일시 장애 후 RPC 조회 경로 복귀를 진행한다.
3. **사설 방 실시간 알림 완전성 검증 후 정기 조회 축소**, 공개 카페의 변경 데이터 갱신을 진행한다.
4. 공통 데이터 재사용과 기기 메타데이터 쓰기 최적화는 실제 잔여 사용량을 보고 채택한다.

이 확장안은 첫 기획보다 DB 변경·동시성 검증 범위가 크다. 구현 전에 운영 정의·권한·스케줄 지원을 읽기 전용으로 확인하고 기존 테스트에 실제 DB 경합 검증을 더한다. 절감률을 서로 더하거나 16.68GB에 그대로 곱하지 않는다. 전체 효과는 같은 프로젝트의 활성 학습 시간당 호출 수·로그 GB·DB 지연·Realtime 사용량으로 검증한다.
