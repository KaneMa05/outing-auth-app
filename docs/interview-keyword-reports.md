# 전공 키워드 조건과 판정 리포트

2026-10-29 로컬 구현·검증 기록. 운영 DB 적용·유료 AI 호출·푸시·배포 없음.

## 구현 범위

관리자 `분류·채점 기준 → 문항 검토`에서 평가 항목마다 기준 키워드와 해당 키워드의 허용 표현을 등록한다. 평가 항목 안에서 `모두 충족(all)` 또는 `하나 충족(any)`을 선택한다.

예: 통신·보고 항목을 all로 설정하고 아래 두 키워드를 등록한다.

- VHF: 허용 표현 `브이에이치에프`
- 상황실: 허용 표현 `상황센터`

`브이에이치에프로 상황센터에 보고합니다`는 두 키워드의 표현 조건을 충족한다. VHF와 브이에이치에프를 모두 말할 필요는 없다. `VHF를 사용합니다`는 상황실 키워드가 누락되어 이 all 항목을 충족하지 못한다. 키워드가 있어도 부정·잘못된 관계·타인의 주장 인용 등은 기존 문맥 판정에서 불인정한다. 키워드 검출 자체와 문맥 판정은 별도로 표시한다.

문항의 모든 필수 평가 항목을 충족해야 O다. 일부 항목 충족은 △, 충족 항목 없음 또는 핵심 오류는 X다. 한 all 항목의 일부 키워드만 말한 경우 그 항목은 충족하지 않은 것으로 처리한다. 인식·문맥 판정 불일치 시 검토 대기이며 확정 grade/score는 null로 유지한다.

## 기준 데이터와 호환성

```json
{
  "label": "통신과 보고",
  "match": "all",
  "keywords": [
    {"term": "VHF", "aliases": ["브이에이치에프"]},
    {"term": "상황실", "aliases": ["상황센터"]}
  ],
  "terms": ["VHF", "브이에이치에프", "상황실", "상황센터"],
  "context": "VHF로 상황실에 보고함",
  "reject_context": "통신 수단이나 보고 대상을 부정함"
}
```

`terms`는 기존 서비스와의 호환용으로 키워드·허용 표현을 순서대로 펼친 배열이다. API와 DB가 배열의 일치를 검증한다. 한 항목 안에서 중복 표현을 여러 키워드에 등록하지 못하게 하여 같은 발화 하나로 서로 다른 키워드를 충족시키는 설정을 막는다. 표현은 항목당 최대 30개, 각 120자다.

keywords/match가 없는 기존 terms 목록은 기존 OR 의미를 유지한다. 관리자가 기존 기준을 열어 저장할 때는 첫 표현을 기준 키워드, 나머지를 허용 표현으로 보여준다. 질문 본문·공개 상태·다른 분류의 답변 기능은 변경하지 않는다.

판정 버전은 `exam-evidence-2`, 문맥 프롬프트는 `exam-context-2`다. all 항목은 인용 근거에 모든 키워드 그룹의 인정 표현이 실제로 있어야 한다. AI가 이를 빠뜨리고 accepted로 반환해도 서버에서 판정 제안을 보류한다.

## 리포트 저장·조회

기존 `/api/interview-exam`에 추가했다. 새 엔드포인트나 Vercel 설정 변경은 없다.

- `validate_audio`에 UUID `requestKey`를 보내면 AI 호출 전에 DB에 요청을 예약한다. 생성 후 전사·문맥 근거·키워드별 검출/누락·제안 판정·배점·질문/기준 스냅샷·버전·해시를 하나의 리포트로 저장한다. 새 관리자 화면은 requestKey를 항상 보낸다.
- `report_list`: 문항별 리포트 목록. 30개 단위 페이지 조회.
- `report_get`: 리포트 ID로 저장 당시 결과를 조회한다. 조회에는 AI 설정이나 호출이 필요하지 않다.

새 화면에서 판정 실행 후 리포트를 저장하고, 같은 문항의 저장 기록을 열어 볼 수 있다. JSON 내려받기도 제공한다. 질문·기준이 바뀌어도 기존 리포트는 덮어쓰지 않는다. 재검증은 새 requestKey의 별도 리포트다.

생성은 기존 `interview.write`, 목록·조회는 `interview.read` 권한을 검사한다. DB는 service_role에만 RPC와 테이블 접근을 허용하고 RLS를 활성화한다. 함수는 SECURITY INVOKER이며 빈 search_path를 고정한다. 학생 또는 일반 브라우저 역할의 직접 접근은 거부한다. 이 단계의 리포트는 **관리자 WAV 검증 기록**이며 학생별 응시 리포트 공개·관리자 확정 성적 기능을 추가한 것은 아니다. 원음은 기존 검증 화면처럼 서버에 보관하지 않고 원음 해시를 남긴다.

기존 클라이언트가 requestKey 없이 보내는 검증 요청은 이전과 같이 결과만 반환하며 저장하지 않는다. 공개된 학생 화면·네이티브 연습·공통 녹음 모듈은 변경하지 않았다.

## 중복·실패 처리

DB 예약은 서로 다른 함수 인스턴스에도 적용된다. 같은 requestKey와 같은 입력의 완료 결과는 재사용하며 AI를 다시 호출하지 않는다. 같은 키의 다른 음성·기준은 충돌로 거부한다. 처리 중이거나 종료 확인이 안 되는 요청도 자동 재실행하지 않는다.

DB 예약 실패는 AI 호출 전에 중단한다. 생성 후 저장 실패/응답 유실은 `persisted:false`와 생성된 리포트를 반환하여 화면에서 내려받을 수 있게 한다. 이 경우 화면은 서버 저장 성공으로 표시하지 않는다. 실제 DB 반영이 불확실할 수 있으므로 기록 새로고침으로 확인한다. 생성 결과만 재전송하는 복구 API는 아직 없으며, 리포트 저장 장애 때문에 유료 분석을 자동 재실행하지 않는다. 프로세스가 분석 중 종료되면 processing 기록이 남을 수 있다.

Supabase 공식 변경 이력과 RLS 문서를 확인했다. 실제 Supabase 로컬 스택/Docker 대신 격리 PGlite에서 SQL을 실행하고 조회로 동작을 검증했다. 운영 Supabase Advisors 호출은 수행하지 않았으며 로컬 검사에서 RLS·역할별 거부·함수 invoker/search_path·원본 스냅샷 보존을 확인했다.

## 검증

신규 `interview-keyword-rules.test.cjs`, `interview-exam-reports.test.cjs`: 13개 통과.

- all/any, 그룹별 허용 표현, 기존 OR 호환
- 미등록 표현·누락·부정·인용 근거 불충분 시 잘못된 승인 방지
- API와 직접 DB 저장의 잘못된 조건/중복 표현 거부
- 실제 로컬 SQL 저장·조회, 같은 요청 재사용, 다른 음성 충돌
- 기준 변경 후 과거 리포트 보존
- 조회 시 AI 호출 없음, 저장 실패 시 원 결과 보존
- 관리자 읽기/쓰기 분리, 학생·anon·authenticated 거부, RLS 및 함수 설정

실제 내장 브라우저에서 관리자 화면의 모두 충족 선택 → 상황실 키워드/상황센터 허용 표현 추가 → 기준 저장 → 합성 WAV 선택 → 모의 AI 판정 → DB 리포트 저장 → 새로고침 → 저장 리포트 재조회까지 확인했다. 새로고침 후 기준 조건과 허용 표현도 보존되었다. 실제 외부 AI의 의미 판정 정확도 측정은 아니다.

기존 전공 판정·평가 지표·면접 DB/API 검사, 공통 기반 11개, Live UI 5개, 네이티브 launcher 4개, release-safety 3개 통과. 고유 임시 폴더의 격리 빌드와 변경 모듈 구문 검사도 통과했으며 config.js는 원래 바이트와 동일했다.

기존 `interview-rubrics.test.cjs`는 시작 단계의 corpus SHA-256 검사에서 실패했다. 기록된 해시 `d603cf…`와 현재 원본 해시 `821675…`가 다르며 두 자료 파일은 이번에 수정하지 않았다. 원본 검수 자료를 자동 재생성하거나 해시를 덮어쓰지 않았다. 새 키워드 DB 검증은 이 자료 파일에 의존하지 않고 별도 가상 문항으로 통과했다.
