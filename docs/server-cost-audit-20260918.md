**1. Observability는 요청마다 여러 이벤트를 과금한다**

Vercel은 Edge 요청, 함수 실행, 함수 안의 외부 API 호출 등을 각각 이벤트로 집계한다. 예를 들어 함수 1회에서 DB를 6회 호출하면 일반적인 경로에서 Edge 1 + 함수 1 + 외부 호출 6 = 약 8개 이벤트가 생길 수 있다. 따라서 화면의 이벤트 417만 회를 사용자 방문 417만 회로 해석하면 안 된다. `console.log` 출력 개수와도 다르다. [이벤트 집계 방식](https://vercel.com/docs/observability#tracked-events)

현재 비용은 4.17M × $1.20/M ≈ $5.00으로 공식 단가와 맞는다. 로그 문장 삭제보다는 외부 왕복 횟수를 줄이거나, 고급 관측 기능의 필요성을 판단하는 것이 직접적인 대응이다.

권고: 이번 조사 기록을 보존한 뒤 30일 상세 기록과 고급 Query가 상시 필요하지 않다면 Billing → Observability Plus → Manage projects에서 `outing-auth-app` 제외를 검토한다. 앱 기능을 바꾸지는 않지만 관측 데이터 보존·상세 분석 기능은 줄어든다. 무료 Pro 관측의 보존 기간은 1일, Plus는 30일이다. 장애 분석을 계속 진행할 계획이면 개선 전후 비교를 마친 뒤 제외하는 것도 타당하다. [제외 방법과 기능 차이](https://vercel.com/docs/observability/observability-plus)

**2. 30초 heartbeat 한 번에 DB를 6회 호출한다**

근거: `app.js:2863`, `api/study-cafe.js:90`, `api/study-cafe.js:595`, `api/study-cafe.js:541`, `tests/study-cafe-api.test.js:368`.

화면이 보이고 포커스가 있으며 좌석이 있는 사용자는 30초마다 heartbeat를 보낸다. 정상적인 공개 좌석, 날짜 전환이나 만료 좌석이 없는 경우에도 다음 여섯 요청이 순차 실행된다.

1. 기기 토큰 검증 RPC
2. 활성 학생 및 유형 조회
3. 만료된 전체 공개 좌석 조회
4. 날짜 전환 판단용 본인 학습 세션 조회
5. 본인 좌석 조회
6. 본인 좌석 heartbeat 업데이트

기존 테스트를 실행해 이 정상 경로가 6회 호출임을 확인했다. 사설 방 경로, 날짜 전환, 만료 좌석 정리·푸시가 붙으면 더 늘 수 있다.

현재 공개 좌석 heartbeat를 1시간 계속 보내면 사용자당 함수 120회, 이 경로의 DB 요청 약 720회다. 100명이 하루 8시간을 같은 조건으로 사용한다는 예시에서는 하루 함수 96,000회·DB 요청 576,000회가 된다. 이는 이용자 수를 측정한 결과가 아닌 규모 설명용 계산이다.

개선 방향: 현재 인증과 시간 기록 규칙을 유지하는 전용 RPC로 학생 확인·본인 세션/좌석 검증·갱신을 합친다. 전역 만료 정리는 매 사용자 heartbeat에서 반복하는 대신 중복 실행을 제한하거나 별도 배치로 분리하되, 좌석 선택 시 만료 여부는 즉시 확인한다. 30초 주기를 먼저 늘리는 방식은 연결 끊김 감지와 순공시간 보정에 영향을 줄 수 있어 후순위다.

**3. 미국 함수가 시드니 DB와 반복 왕복한다**

[실제 함수 설정](https://vercel.com/ronpark/outing-auth-app/settings/functions)은 Fluid Enabled, 기본 지역 `iad1`, Standard 1 vCPU / 2GB였다. 연결된 Supabase 프로젝트는 `ap-southeast-2`이다. `vercel.json`은 OX 함수만 `syd1`로 지정한다. 따라서 스터디카페·보상 함수는 기본 지역 설정을 따른다.

Supabase 경로별 P75는 기기 검증 268ms, 학생 조회 252ms, 좌석 조회 251ms, 세션 조회 253ms, 좌석 갱신 252ms였다. 호스트 상세 전체 지연은 평균 369ms, P75 386ms였다. 이를 모두 SQL 실행 시간으로 해석해서는 안 된다. 운영 DB의 누적 statement 통계에서는 기기 검증 평균 약 4.48ms, snapshot 약 15.15ms였다. 기간과 집계가 다르므로 직접 빼서 네트워크 시간을 산출할 수는 없지만, 앱의 다중 원격 왕복을 개선할 근거가 된다.

Fluid 메모리 과금은 실제 사용하는 241MB만이 아니라 할당 메모리와 처리 중인 시간에 기반한다. I/O 대기 중에도 메모리 비용은 계속된다. 여러 요청이 한 인스턴스를 공유하므로 실행 횟수 × 평균 시간으로 청구 GB-hours를 그대로 역산할 수도 없다. [과금 방식](https://vercel.com/docs/functions/usage-and-pricing)

권고: `study-cafe`와 `student-rewards`를 우선 후보로 시드니에서 비교 측정한다. 미국의 메모리 단가는 $0.0106/GB-hour, 시드니는 $0.0149로 약 41% 높다. 같은 메모리 할당에서 과금 시간이 약 29% 이상 줄어야 메모리 항목 자체가 절감된다. CPU 지역 단가도 높아지므로 전체 요금으로 검증해야 한다. 지역만 바꾸면 무조건 저렴해진다고 약속할 수 없다. [지역별 공식 단가](https://vercel.com/docs/functions/usage-and-pricing#regional-pricing)

Standard 2GB는 현재 Fluid 기본 선택이며, 화면에 512MB 옵션은 없었다. `vercel.json`에 memory를 512로 쓰는 해결책은 현재 Fluid 설정 방식과 맞지 않는다. [메모리 설정](https://vercel.com/docs/functions/configuring-functions/memory)

**4. 전체 snapshot과 보상 조회가 함께 반복된다**

근거: `app.js:2108`, `app.js:2869`, `app.js:2998`, `api/study-cafe.js:639`, `api/study-cafe.js:829`, `student-rewards.js:35`, `student-rewards.js:79`, `api/student-rewards.js:51`.

전체 스터디카페 조회는 안전 갱신 2분 주기 외에 실시간 변경 메시지에도 실행된다. 현재 350ms debounce는 짧은 연속 메시지는 합치지만, 메시지 간격이 그보다 길면 여러 사용자의 변경에 따라 전체 snapshot 요청이 반복될 수 있다. 본인 조작의 즉시 반영은 유지하고 타인의 변경만 최소 갱신 간격을 두거나 필요한 부분만 갱신하는 것이 후보이다.

정상 snapshot 경로는 전처리 4회에 snapshot RPC 1회, 봇 외형 1회가 붙는다. 인터넷 수강생은 포인트 정산과 장비 조회 2회가 추가돼 총 8회다. 일부 조회는 병렬이지만 요청 및 이벤트 개수는 그대로다. 최근 7일 포인트 정산과 장비 조회가 각각 약 118,000회였다. 지갑·장비 변경이 없을 때까지 전체 조회마다 재계산할 필요가 있는지 분리할 수 있다.

보상 API는 기기 검증 → 학생 확인 → 보상 RPC의 3회 호출이다. 보상 RPC는 최근 7일 약 78,000회였고 외부 요청은 약 235,000회였다. 클라이언트는 60초 제한과 진행 중 중복 방지를 이미 적용한다. 하지만 모든 성공한 스터디카페 요청이 보상 동기화를 예약하며, heartbeat도 포함된다. 타이머의 자체 자격 조건만 고쳐서는 이 경로가 사라지지 않는다.

개선 방향: 보상 지급 조건을 바꾸지 않고 다음 적립 가능 시점·완료 상태에 따라 동기화한다. pause/stop/release 후 필요한 확인은 유지하며 기존 snapshot의 지갑 정보를 재사용할 수 있는지 검토한다. 인증을 캐시하거나 검증을 생략하는 방식은 권고하지 않는다.

**5. 장애 시 비용이 커질 수 있는 보완점**

`api/study-cafe.js:740`과 `api/study-cafe-rooms.js:266`은 snapshot RPC가 한 번 실패하면 해당 프로세스에서 지원 여부 플래그를 false로 고정한다. 일시적 DB 오류도 구형 다중 조회로 전환시키며 정상 복구 후 재시도 기한이 없다. 공개 카페의 경우 snapshot 1회가 구형 조회 9회로 늘 수 있다. 실제 비용에서 이 경로가 차지한 비율은 이번 지표로 분리하지 못했다.

운영 DB에서 두 snapshot RPC의 존재 및 실제 호출 기록을 확인했으므로, 최적화 SQL이 아예 미설치라는 진단은 맞지 않는다. 오류 종류를 구분하고 일정 시간 후 제한적으로 재시도하도록 개선하는 것이 후보이다.

스터디카페 공통 서버 fetch는 봇 외형 요청을 제외하면 명시적인 제한 시간이 없다. 브라우저가 요청을 포기해도 서버 쪽 DB 요청이 즉시 종료된다고 보장할 수 없다. 다만 현재 대시보드 Timeout은 표시상 0%라서 확인된 주원인으로 보지 않았다. 읽기·쓰기별 제한 시간과 취소 후 저장 결과 재확인 규칙을 함께 설계할 대상이다.

**운영 DB 검토의 범위와 해석**

운영 DB에서는 시스템 카탈로그, 함수 정의, 익명 집계 통계만 조회했다. 학생별 기록이나 토큰을 추출하지 않았다. SQL을 실행해 실제 기기 인증·보상 지급을 일으키는 방식의 운영 테스트는 하지 않았다.

누적 statement 통계 초기화 시점은 2026-05-01이며 최근 7일 청구 기간과 다르다. 기기 검증 약 632,000회와 기기 테이블 약 630,000회 업데이트는 반복 검증의 누적 부하를 뒷받침하지만 이번 주 사용량으로 재계산하면 안 된다. 기기 검증은 매회 학생 행 잠금과 last_used_at 갱신을 수행한다. 인증 유효성 확인은 유지하면서 표시용 최종 사용 시각의 쓰기 빈도를 제한하는 방안은 별도 동시성 검증이 필요하다.

스터디카페 봇 cron은 매분 DB 내부 함수를 실행한다. 확인한 함수 정의에는 Vercel로 나가는 HTTP 호출이 없었다. 봇 외형 조회는 실제 사용자 요청의 snapshot 경로에서 발생한다. 봇 cron 자체가 분당 Vercel 함수를 호출한다고 판단할 근거는 없다.

작은 좌석 테이블의 seq_scan 수만으로 인덱스 부족이라고 판단하지 않았다. 테이블이 작으면 순차 조회가 정상적인 선택일 수 있다. 새 인덱스나 DB 사양 업그레이드를 이번 비용의 우선 해결책으로 제시하지 않는다.

**적용 순서와 검증 기준**

| 순서 | 작업 | 확인할 효과·회귀 |
| --- | --- | --- |
| 1 | Observability Plus 상시 필요성 판단, 제외 후보는 이 프로젝트로 한정 | 향후 이벤트 사용량 감소, 상세 장애 분석 기능 축소 수용 여부 |
| 2 | 스터디카페·보상 함수 지역 비교 | 동일 부하에서 P75/P95, 메모리 GB-hours, CPU 요금 합계 |
| 3 | heartbeat의 DB 왕복 통합 | 정상 경로 6회 대비 감소, 기기 해지 즉시 반영, 좌석 충돌·날짜 전환·순공시간 정확성 |
| 4 | 전체 snapshot과 보상 조회의 중복 제거 | 시간당 활성 사용자당 호출 수, 포인트 중복·누락 없음, 장비 변경 즉시 반영 |
| 5 | RPC fallback 재시도 및 서버 요청 제한 시간 | 일시 오류 후 RPC 복귀, 저장 성공/실패 오판 방지 |

계측은 절대 요청 수만이 아니라 활성 학습 시간당 요청 수로 비교해야 한다. 비용 절감률은 지역 변경과 호출 수 개선 후 실제로 측정한다. 온라인 관리반·인터넷 수강생의 카페 변경을 다른 화면에 일괄 적용하지 않으며, 보상 공통 코드 변경 시 오프라인 수강생도 검증한다. 교사·관리자 기능의 회귀도 확인한다.

서비스 중단을 피하기 위해 비용 초과 시 프로젝트 자동 정지를 켜는 것을 절감책으로 삼지 않는다. 현재 Billing은 Notifications On, Pause Projects Off였다. 필요하면 알림 기준만 조정한다. 푸시·배포는 프로젝트 지침에 따라 최종 확인 후 수행한다.
