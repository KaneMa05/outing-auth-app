# 전공 개념·관계 판정 보완 · 2026-10-30

전공의 키워드 발화·허용 표현·문맥 판정을 유지하면서, 관리자가 명시적으로 선택하는 개념 판정 방식을 추가했다. 기존 기준과 과거 리포트를 자동 변환하지 않는다. iOS 전용 worktree의 네이티브 코드, 인성 분석기와 실전 면접 진행 코드는 수정하지 않았다. 이번 구현은 웹·서버 전공 채점 경로에 적용한다.

## 기준 작성

관리자 `분류·채점 기준 검토`의 필수 평가 항목에서 다음 중 하나를 선택한다.

- 지정 용어와 문맥 확인: 기존 방식. 등록된 키워드 또는 승인된 허용 표현의 실제 발화와 올바른 문맥이 모두 필요하다.
- 개념·관계의 의미 확인: `assessment.mode=concept`으로 저장한다. 참고 키워드가 없어도 검토된 개념을 정확하게 설명하면 인정할 수 있다. 참고 키워드는 기존 데이터 형식과 표현 확인을 위해 한 개 이상 등록하며, 의미 판정의 필수 발화 조건으로 사용하지 않는다.

정확한 전문용어도 요구하려면 용어 확인 항목을 별도로 추가한다. 개념 이해와 용어 사용을 한 번에 혼동해서 판정하지 않는다.

개념 방식은 항목별로 모두/하나 충족 조건, 개념별 주장·관계/적용 조건·부분 인정 조건·틀린 설명의 경계, 정답/오답 설명 예시를 입력한다. 기존 `context`와 `reject_context`는 전체 문맥으로 유지한다. 예시는 기준을 설명하는 자료이며 단어 일치 대상이나 새 평가 항목이 아니다.

각 항목에 개념 1~5개, 한 문항에 총 30개까지 허용한다. 개념의 주장·관계·부분 조건·오류 경계는 각각 최대 1,000자다. 주장의 내용과 오류 경계는 필수이며 관계와 부분 조건은 비울 수 있다. 정답/오답 예시는 각각 최대 5개·예시당 1,000자다. 전체 평가 항목은 기존과 같이 최대 20개다. 관리자 기준 저장 본문은 최대 200 KB로 제한한다.

새 마이그레이션 `supabase/migrations/20261030045623_interview_concept_assessment.sql`은 기존 JSONB 기준 컬럼에 대한 추가 검증 트리거만 만든다. 기존 학생 데이터·테이블·권한·기준 내용은 변경하지 않는다. 전공 지식형에만 개념 기준을 허용하며 API와 직접 RPC 양쪽에서 형식·중복·길이·총 개수 등을 검증한다. 함수는 SECURITY INVOKER, 빈 search_path와 서버 역할 실행 권한을 사용한다.

## 판정과 집계

기존 두 번의 독립 전사와 서로 다른 모델의 독립 문맥 판정을 사용한다. 전사 불일치·음질 문제는 기존처럼 검토로 넘긴다. 두 판정 모델은 서로의 결과를 보지 않는다.

새 프롬프트 `exam-context-3`과 구조화 응답은 용어 기준과 개념 기준을 구분한다. 용어 기준은 기존 criteria 배열에 원래 평가 항목 인덱스로, 개념은 별도의 concepts 배열에 펼친 개념 인덱스로 응답한다. 모델이 전체 점수나 개념 충족 조건을 임의로 집계하지 못하게 한다.

개념별 상태는 충족·부분 충족·틀린 설명·설명 누락·불확실이다. 충족·부분 충족·틀린 설명에는 편집하지 않은 주 전사문에서 복사한 연속 인용이 필요하다. 인덱스 누락/중복, 추가 필드, 존재하지 않는 인용, 부분 기준이 없는 개념에 대한 부분 인정 등은 판정 제안을 보류한다. 키워드가 있다는 이유로 개념의 누락을 오류로 바꾸거나 정답으로 인정하지 않도록 프롬프트에 명시했다.

서버 집계 순서는 다음과 같다.

1. 불확실한 개념이 있으면 불확실. 실제로 틀린 설명이 확인되면 해당 평가 항목은 불인정한다.
2. 그 외에는 모두/하나 충족 조건으로 완전 충족 여부를 계산한다.
3. 완전 충족은 아니지만 올바르게 설명한 개념 또는 등록된 부분 조건에 해당하는 설명이 있으면 항목은 부분 충족이다. 필요한 설명이 모두 없으면 누락이다.
4. 두 모델의 개념별 판정이 하나라도 다르면 최종 제안은 보류한다. 두 모델의 항목 합산 결과가 같더라도 개념별 판단이 다르면 합의로 취급하지 않는다. 리포트 항목 요약도 검토 필요로 표시한다.
5. 전체 O는 모든 필수 평가 항목의 완전 충족을 요구한다. 일부만 충족하거나 부분 충족이면 △, 충족한 내용이 없으면 X를 제안한다. 관리자가 기존 `critical_errors`에 명시한 핵심 오류만 전체 답변의 X를 강제한다.

‘하나 충족’에서도 다른 개념을 명백히 틀리게 설명한 결과는 무시하지 않는다. 일부 개념을 온전히 설명하고 나머지를 빠뜨려 전체 항목이 부분 충족인 경우와, 하나의 개념 설명 자체가 부분 인정 조건에 해당하는 경우를 구분한다. 개념 수에 비례한 점수 계산이나 가중치는 추가하지 않았으며 기존 관리자 지정 O/△/X 배점을 사용한다.

명확하게 철회한 오류 뒤의 정정은 전체 정정 문맥을 인용해 최종 주장으로 검토하도록 했다. 철회가 불명확하거나 모순이 해결되지 않으면 불확실로 넘긴다. 이는 모델에 제공하는 판정 규칙이며, 코드가 자연어의 의미·정정 여부를 완벽하게 증명한다는 뜻은 아니다.

## 리포트와 보존

감사 버전은 `exam-evidence-3`이다. 프롬프트 해시는 용어/개념 응답 스키마를 모두 포함한다. 기준 스냅샷에 개념·관계·부분/오류 경계와 예시를 함께 고정한다.

기존 관리자 검증 API와 학생 전공 제출 API가 같은 판정 서비스를 사용하므로 별도 유료 호출 경로나 새 엔드포인트를 만들지 않았다. 기존 보고서 저장소에 `conceptResults`를 포함해 저장하고, 관리자 검증 화면과 학생 리포트 양쪽에 개념별 두 AI 판정·인용·이유·부분/오류 경계를 표시한다. 학생 화면의 해당 키워드 목록은 참고용으로 표시하며 미발화를 오답으로 단정하지 않는다. 보류 이유와 핵심 오류 근거도 표시한다.

관리자 검증은 처리 후 최신 기준을 다시 확인해 변경 중 제안을 보류한다. 학생 응시는 시작 시 기준을 고정하며 이후 관리자의 기준 수정은 이미 시작한 응시와 과거 리포트를 바꾸지 않는다. 학생 응시 전에는 기준·정답을 노출하지 않으며, 완료 후에도 관리자 검토 기록·감사 설정을 포함한 전체 rubric을 학생에게 반환하지 않는 기존 정책을 유지한다. 저장 결과 조회에는 AI를 호출하지 않는다.

모든 결과의 status는 review_required이고 공식 grade/score는 null이다. O·△·X와 배점은 검토용 suggestion이다. 두 모델의 동의는 교정된 정확도나 강사 검토 완료를 뜻하지 않는다.

## 검증 범위

관련 자동 검사 105개 통과: 신규 개념/관계 집계와 관리자·학생 DB/API 통합, 기존 키워드·관리자 리포트·학생 전공, 공통 저장, 인성, Live UI, 모드 분리, 네이티브 launcher, release safety. 마지막 표시 보완 후 개념 판정·리포트 및 전공 UI 검사 16개를 추가 실행해 통과했다. 기존 전공 판정/음질/제공자 계약 검사도 통과했다. 고유 임시 폴더의 격리 빌드, 변경 JS 구문 검사, config.js 상태 보존과 diff 공백 검사도 확인했다.

신규 검사에는 다음이 포함된다.

- 참고 키워드가 없는 충족, 키워드가 있는 잘못된 관계, 누락과 오류 구분.
- 등록된 부분 조건과 미등록 부분 인정 거부, 모두/하나 서버 집계.
- 같은 합산 결과지만 개념별 판정이 다른 사례, 명확한 정정/불확실 상태의 중재.
- 별도 필수 전문용어를 의미 충족으로 대체하지 못하는 검사.
- 인용 위조·인덱스 위조·임의 점수, 형식/중복/길이/개수·인성 유형 사용 거부.
- 기준 변경 후 이전 응시/리포트 보존, 재조회/중복 제출 시 추가 분석 금지, 계정 격리·RLS·함수 권한.

브라우저에서는 실제 관리자 UI로 개념 하나 충족 조건과 관계 문장을 변경해 로컬 DB 저장·새로고침 후 재조회했다. 실제 학생 UI에서 합성음 MediaRecorder → 기기 저장 → WAV 제출 → 로컬 서버 저장 → 모의 판정 → 리포트 표시를 3회 확인했다. 다른 표현의 설명은 O, 키워드가 있지만 반대 관계인 설명은 X, 방향이 빠진 설명은 △가 저장됐다. 새로고침 후 같은 △ 리포트가 조회되고 참고 키워드 미발화와 개념별 인용이 유지됐다.

이 검사는 고정된 모의 전사·모의 모델 판정을 사용한다. 실제 학생의 음성을 외부 AI로 판정한 정확도 검증은 아니다. 원문에 있는 인용인지 확인하는 것과 그 인용을 올바르게 해석하는 것은 별개다. 실제 정확도는 강사가 문항별 기준과 예시를 검수하고, 별도의 대표 답변 검증 세트로 거짓 정답·거짓 오답·보류율을 측정해야 한다. 모델·프롬프트·기준 변경 때도 같은 세트로 확인해야 한다. 기존 문항 전체에 자동으로 개념 기준을 생성하거나 승인하지 않았다.
