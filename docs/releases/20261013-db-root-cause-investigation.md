## 원인별 판단

- **메모리 압박과 시스템 디스크 I/O 정체:** 가장 유력하게 조사할 가설. 반복된 실제 paging과 IOwait, DB 전반의 시작/실행 지연이 근거다. 18:58~20:08 원시 호스트 지표가 없어 최초 유발 원인으로 확정하지 못했다. 디스크 burst 제한이나 호스트 장애도 별도 확인이 필요하다.
- **특정 SQL/OX:** 기존 OX 정렬의 임시 파일 사용은 별도 조사에서 입증된 개선 대상이다. 그러나 18:40~19:00 gateway의 OX 호출은 29건, 평균 origin_time 681ms였고 요청 내용의 세부 작업 구분도 없다. 이번 전체 장애의 단독 원인 또는 해당 최적화의 완전한 해결 효과는 입증되지 않았다.
- **봇 cron:** 18:57 완료 후 18:58에는 시작 자체가 실패했다. 최초 원인이라고 단정할 근거가 없다.
- **외부 공격/요청 폭증:** 확인한 상위 요청은 앱의 학생·기기·카페 기능이며, 18:45 정상 구간에도 REST 656건/분이었다. 이후 18:57은 320건/분이었다. 이는 단순 요청량 급증 가설을 지지하지 않지만, 완료 로그만으로 공격·순간 부하를 완전히 배제하지 못한다. 역할·국가·IP만으로 요청을 정상 또는 악성으로 판정하지 않았다.
- **전체 DB 연결 한도:** 복구 후 정상 값만 있다. 장애 당시 포화 여부를 배제할 수 없다. Realtime/PostgREST 전용 풀 대기는 전체 max_connections 초과와 구분한다.
- **OOM/디스크 가득 참/교착:** 확인한 PostgreSQL 로그에서 이를 입증하는 직접 오류를 찾지 못했다. 호스트 커널 로그가 없으므로 완전한 배제는 아니다.
- **Supabase Realtime 공지:** 같은 날 공지는 있으나, 이 프로젝트 PostgreSQL 장애와의 직접적인 인과관계는 미확인이다.

### 원인 후보 대조

- **메모리 압박과 시스템 디스크 대기:** 장애 직전 commitment 한도 초과를 추가 확인했다. 기존 실제 paging·IOwait 기록과 함께 가장 강한 자원 병목 후보다. 그러나 페이지 교체가 있는 동안 정상 응답도 있었고, 해당 순간 OOM·할당 실패·프로세스별 메모리 증가·호스트 throttling 직접 기록은 확보하지 못했다. 특정 작업이 최초 촉발 원인이라는 확정에는 아직 부족하다.
- **특정 OX 호출:** 18:57:53.541 OX 요청은 origin_time 39ms/upstream 22ms였다. 이후 여러 독립 기능이 느려졌으므로 이 요청을 원인으로 지목할 근거가 없다. 이전 OX 정렬 임시 파일 문제는 실증된 별도 개선 사항이다.
- **초기 조회의 병렬 폭증:** 18:58:09와 18:58:15에 브라우저의 여러 초기 조회가 묶여 있다. 앞선 기기 검증 지연보다 뒤의 로그이며, 이것만으로 최초 촉발을 지목하지 않는다. 18:45:50의 10초 버킷은 341건/평균 321.5ms, 18:56:50은 190건/276.4ms로 더 많은 요청도 정상 처리한 사례가 있다. 집계만으로 모든 순간 동시 부하를 배제할 수는 없다.
- **PostgREST의 `Thread killed by timeout manager`:** 장애 직전에도 존재하지만 09~18시 각 시간대에 188~488개 로그 메시지가 반복됐다. 정상 구간에도 있는 메시지이며 해당 문구를 OS OOM kill 또는 최초 원인의 직접 증거로 해석하지 않는다. 메시지 한 개에 같은 문구가 여러 번 포함돼 있어 메시지 수와 종료 스레드 수는 다르다.
- **18:10:49 SQL 문법 오류:** 기존에 열린 로그 탭에는 관리 API의 `codex-readonly-audit` 조회에서 `day` 부근 문법 오류(SQLSTATE 42601)가 선택돼 있었다. 이는 실행 전 문법 오류이며, 당일 최초 조회 timeout은 이미 11:35에 발생했다. 이 오류 로그 자체로 전체 접속 장애의 시작을 설명할 수 없다. 성공한 다른 진단 쿼리의 부하까지 무조건 배제한다는 뜻은 아니다.

### 갱신한 판단

장애 전 원인 단서가 없었던 것이 아니다. **직전 메모리 commitment 한도 초과, 앞선 반복 timeout, 실제 paging과 시스템 디스크 대기**라는 근거가 있다. 이에 따라 메모리/시스템 I/O 압박 가설은 강화된다. 다만 약속된 메모리 초과와 실제 할당 거부·OOM은 동일하지 않으며, 단일 SQL·연결 폭증·호스트 제한 중 최종 촉발 요소를 확정했다고 보고하지 않는다.

최초 촉발을 더 좁히는 다음 증거는 18:57:50~18:58:15의 프로세스별 메모리, memory reclaim/PSI, fork·할당 실패, 시스템 디스크 queue/latency 및 제한 발동 이력이다. 기존 지원 요청 초안에 추가할 구체적인 수치가 확보됐지만 이번 재조사에서 외부 전송은 하지 않았다.

해석 참고: [Supabase 메모리 commitment 정의](https://supabase.com/docs/guides/observability/reports#memory-commitment), [swap·시스템 디스크 구분](https://supabase.com/docs/guides/troubleshooting/memory-and-swap-usage-explained-aPNgm0), [로그 시각 및 필드](https://supabase.com/docs/guides/troubleshooting/discovering-and-interpreting-api-errors-in-the-logs-7xREI9).

## 최초 촉발 작업 추적 — 추가 조사

최초 촉발 원인 확정은 아직 완료되지 않았다. 11:35·14:12~14:14·18:58의 API 로그 305·488·103건을 각각 대조했다. 14:12:38까지 카페·OX 요청은 upstream 수 ms 수준이었으며 14:12:40 heartbeat부터 265~441ms로 증가했고 뒤이어 서로 다른 기능이 수초로 느려졌다. 18:57:57에도 기기 검증과 heartbeat의 지연이 함께 증가했다. 첫 느린 응답은 병목의 피해자일 수 있어 해당 함수가 최초 원인이라고 판단하지 않는다.

읽기 전용 운영 SQL로 cron.job_run_details 및 설정·함수 정의를 확인했다. 18:57 봇 SQL 실제 실행은 18:57:02.367~03.661이었다. 18:58 작업은 startup timeout이며 본문 실행이 확인되지 않는다. 다만 신규 백엔드 생성 자체의 부담까지 배제할 자료는 없다. 14:12의 느려짐은 그 분 cron 완료(14:12:01.321)와 checkpoint 완료(14:12:17.189) 이후였다. 실행된 봇 본문 하나를 모든 장애의 공통 촉발로 지목할 근거는 확보하지 못했다.

최초 실패한 PostgREST PID 101163/101156/101157/101162는 각각 18:50:48/36/43/48에 생성된 기존 세션이었다. 따라서 이 실패들 자체는 18:58의 신규 연결 폭증 증거가 아니다. Realtime 재연결 증가와 신규 PID들은 뒤에 나타난다. 전체 연결 생성 기록이 없어 다른 연결의 동시 생성은 배제하지 않는다.

### 실제 기록 범위

현재 설정: log_min_duration_statement=-1, log_min_duration_sample=-1, log_transaction_sample_rate=0, log_statement=ddl, log_duration=off, log_connections=off, log_disconnections=off, log_temp_files=-1. auto_explain은 10초 이상 대상으로 켜져 있으나 analyze/buffers/nested_statements는 off다. 따라서 성공 SQL 기록이 전혀 없다고 표현해서도 안 되며, 모든 SQL의 순서·실제 버퍼/자원 사용을 남기는 설정도 아니다. 이는 재시작 이후 현재 설정으로, 과거 설정과의 동일성까지 확정하지 않았다.

18:50~18:58:15 PostgreSQL 로그 22건에서 duration 기록 0, 연결 생성 기록 0, automatic vacuum/analyze 기록 0, ERROR/FATAL/PANIC 0을 확인했다. 이 결과는 기록이 없다는 뜻이며 작업이 실행되지 않았다는 뜻이 아니다. pg_stat_statements reset 시각은 다시 확인해도 20:07:16.781이다. 성공한 요청의 실제 실행 이력·당시 프로세스 자원 사용을 현재 로그만으로 완전히 복원하지 못했다.

Supabase 내부 대조가 가능하도록 초기 지연 요청 ID와 PID를 보관했다. 근거 파일은 `.tmp/20261013-trigger-investigation-evidence.json`, 전송 검토용 요청문은 `.tmp/20261013-trigger-rca-support-request.txt`다. 기존 광범위한 공백 주장을 수정하고, 18:57:50~18:58:15의 최초 프로세스/자원 사건, 원시 자료 보존 여부, 연결 생성·자동 청소·WAL·백업·플랫폼 작업과의 상관 확인을 요청한다. Supabase 지원 UI는 회신을 이메일로 보내는 신규 문의 양식이며 회신 내용은 확인하지 못했다. 요청문은 아직 전송하지 않았다.

이번 추가 조사에서는 read-only 트랜잭션의 조회만 실행했다. 운영 데이터·설정·앱 코드 변경, 재시작, 푸시·배포는 하지 않았다. [PostgreSQL 로깅 설정 정의](https://www.postgresql.org/docs/17/runtime-config-logging.html).

### 코드·데이터 크기 대조

`shared.js`의 `loadStateFromRemote`/`loadExamAnswersFromRemote`는 반복 timeout의 조회 형태와 일치한다. 10월 6일 변경은 교사 사진 조회를 1,000개 단위 순차 페이지 조회로 바꾼 것이다. 현재 통계상 사진은 약 1,090행/총 0.82MiB, 정답 1,825행/1.24MiB, 성적 913행/0.85MiB다. 사진의 일반 조회는 원본 이미지 data_url을 제외한다. 현재 크기와 과거 크기의 동일성은 확인되지 않았지만, 이 코드 변경만으로 거대한 이미지 일괄 로딩이 발생했다고 주장할 근거는 없다.
