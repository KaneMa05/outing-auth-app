## 우선 개선할 항목

### 1. 성적 메뉴가 없는 인터넷 수강생에게도 성적 자료를 요청 — 높음

`shared.js:2205` 공통 로더는 학생 유형이나 현재 메뉴와 무관하게 시험 목록, 시험 과목, 정답, 시험 파일 메타데이터, 파이널 성적을 요청한다. 로그인 학생은 추가로 성적 비교 대상의 제출 내역·체력 점수를 읽는다. `app.js:64`의 인터넷 수강생 메뉴에는 성적 탭이 없지만 이 로더는 그대로 실행된다.

기수가 없는 인터넷 수강생은 `getStudentRemotePeerIds`에서 기수 제한을 적용하지 않는다. 체력 조회는 `matchTrack:false`이므로 전체 학생 명단으로 넓어진다. 80명씩 나누어 읽기 때문에 14~15시 당시 명단 324명 기준 체력 조회만 5개 요청으로 분할될 수 있다. 순위가 필요한 화면의 비교 대상은 보존해야 하지만, 인터넷 수강생 첫 화면에 체력·시험 성적을 선행 조회할 이유는 별도 검토가 필요하다.

현장 근거:

- 정답 조회 496건: **과목 ID 조건 0건**. 성공 응답 중 `0-999/*` 245건, `1000-1954/*` 249건. 실패/범위 경계가 있어 두 페이지 건수가 일치한다고 가정하지 않는다.
- 파이널 성적 조회 285건: 기수/학생 필터 0건. 성공 284건 모두 `0-999/*`.
- 전체 학생 명단 324행 반환 287건. 나머지 학생 조회 대부분은 인증 과정의 단일 학생 조회 1,840건이므로 전체 명단 조회와 구별한다.
- 체력 조회 1,305건 모두 학생 조건은 있었지만, **80명 묶음 1,024건**, 4명 묶음 247건, 26명 묶음 34건이었다. 필터가 있다고 반드시 본인 자료만 읽는 것은 아니다.
- 조사 중 DB 실제 개수: 학생 343명, 시험 38개, 시험 과목 449개, 정답 1,955개, 파이널 성적 1,023개, 체력 300개. 이 개수는 14~15시 로그보다 뒤의 값이다. 현재 인터넷 수강생 120명은 모두 기수가 없다.

작은 가상 자료(학생 2명, 각 테이블 1페이지)로도 초기/전체 갱신은 **15개 읽기**, 30초 경계 성적 갱신은 **11개 읽기**가 실행됐다. 실제로는 80명 분할·1,000행 페이지와 사진 조회, 인증, 메뉴별 API가 더해진다. 모든 접속이 정확히 15회라는 뜻이 아니다.

개선 방향: 인증/학생 기본 정보와 화면별 자료 로딩 분리. 인터넷 수강생의 성적·체력 조회를 제외할 수 있는지 먼저 확인하고, 오프라인/관리반은 성적 진입 시 비교 대상·기수·공통시험·과거 기록을 보존하여 가져온다.

추가 정확성 확인 대상: 현재 파이널 성적은 1,023행인데 운영 초기 조회에는 명시적 페이지 처리가 없고 과거 성공 응답은 1,000행에서 끝났다. 현재 증가분의 정확한 시점과 화면 영향은 별도 검증이 필요하다. 조회량을 줄이면서 누락 문제를 만들거나 유지하지 않아야 한다.

### 2. 홈·플래너에서도 스터디카페 전체 자료를 갱신 — 높음

`app.js:5273` 홈 카드와 `app.js:5601` 플래너가 `ensureStudyCafeRemoteLoaded`를 호출한다. 전체 snapshot에는 좌석, 오늘 세션/순위, 과목, 할 일, 목표, 프로필, 포인트/장비 등이 묶여 있다. 최초 성공 후 캐시가 있지만 실시간 변경 이벤트·2분 안전 갱신·복귀·메뉴 전환의 갱신 경로가 별도로 존재한다.

최적화 bundle이 활성화된 정상 `load` 한 번도 `api/study-cafe.js:51` 기준 아래 **6개 DB 요청**으로 이어진다.

1. 기기 인증
2. 본인 학생 정보
3. 오래된 좌석 확인
4. 본인 활성 세션 및 날짜 전환 확인
5. 화면 snapshot bundle
6. 공부 시간 포인트 정산

각 호출이 하나의 HTTP DB 왕복이라는 뜻이며 RPC 내부 SQL 개수는 아니다. 오래된 좌석 정리·날짜 전환이 실제로 필요하면 요청이 더 늘어난다.

운영 1시간: snapshot bundle 1,676회, 포인트 정산 1,718회, 활성 세션 테이블 GET 1,802회, 좌석 테이블 GET 1,789회. bundle 한 종류만 줄이고 앞단의 공통 처리를 남기면 전체 요청량이 크게 남는다. 사용자별 정산·인증·날짜 전환 규칙을 무작정 생략해서는 안 된다.

실시간 갱신은 최단 시작 간격 1초로 병합되며 실제 모든 사용자에게 매초 발생한다는 뜻은 아니다. 홈에서도 전체 카페 갱신을 받으므로 여러 사람이 입퇴실할 때 다른 사람의 홈 조회까지 함께 늘 수 있다. 대상 화면과 바뀐 항목에 맞는 작은 응답으로 나누는 것이 우선이다.

### 4. 다른 교사 메뉴에서도 외출·사진 전체 갱신 — 높음

`shared.js:988`, `shared.js:1166`은 로그인된 교사 탭이 보이면 현재 메뉴와 무관하게 외출·사진을 읽는다. Realtime 연결 시 30초, 연결되지 않으면 5초 주기다. 사진 조회는 원본 이미지가 아닌 메타데이터이며 1,000개씩 모든 페이지를 읽는다. 사진이 현재 1,152행이므로 외출 1회+사진 2회가 일반적인 한 주기다.

단순 주기 환산으로 교사 창 하나당 약 6회/분 또는 36회/분이 가능하다. 실제로는 실행시간, 저장 중 건너뛰기, 숨김 탭 중단, 실시간 이벤트가 영향을 준다. 최초 교사 진입은 가벼운 외출 선행 조회 후 전체 로더에서 같은 외출·사진을 다시 읽는 경로도 있다.

개선 방향: 외출 화면 외에서는 배지/변경 여부만 가져오고, 필요한 날짜·활성 외출의 사진 메타데이터만 갱신한다. 외출 승인·복귀 상태의 즉시 반영을 유지해야 한다.

### 5. 성적 화면의 30초마다 폭넓은 메타데이터 갱신 — 중간~높음

성적 자동 갱신 30초와 시험 메타데이터 유효기간 30초가 같아 정기 갱신은 주로 메타데이터 포함 경로로 간다. 다른 탭의 출석·외출은 제외하도록 이미 개선됐지만 학생 명단, 공지, 직렬, 시험, 시험 과목, 정답, 파일, 응시과목 설정 및 비교 대상 성적을 다시 읽는다. 작은 fixture에서도 11개다. 학생 수·문항 증가에 따라 더 늘어난다.

기수가 확인되면 성적 갱신의 정답/파이널 필터는 적용된다. 초기/강제 전체 로딩과 혼동하지 않는다. 성적 발표·정답 수정 반영을 유지하면서 변경 버전이나 대상 시험 단위 갱신으로 줄이는 것이 후보이다.

## 수강생 메뉴별 확인표

## 요청량 검증 숫자

정상 API 경로를 실제 handler와 빈/소량 가상 DB 응답으로 실행한 결과다. 인증 실패, 오래된 좌석 정리, 날짜 전환, RPC 미설치 대체 경로에서는 수가 달라진다. DB RPC 1회가 내부적으로 SQL 1개라는 뜻은 아니다.

| 프런트 API 동작1회 | Supabase DB 요청 |
| --- | ---: |
| 카페 전체 load | 6 |
| 카페 heartbeat | 1 |
| 특정 날짜 플래너 | 6 |
| 플래너 월 요약 | 5 |
| 본인 기간 통계 | 5 |
| 주간/월간 순위 | 8 |
| 상점 load | 9 |
| 개인방 load | 4 |

heartbeat는 좌석이 있고 화면이 보이며 포커스가 있을 때30초마다 실행된다. 이를 단순 삭제/간격 확대하면 자리 자동해제·학습시간에 영향을 줄 수 있다. 카페 랭킹룸15초 화면 업데이트와 타이머의 초 단위 숫자 갱신은 로컬 렌더이며 DB 호출과 구별했다.

## 권장 수정 순서와 보존 조건

1. **오류 직후 반복 요청6곳 중단**: 정상 성공 흐름 유지, 오류 표시·수동 재시도/제한된 backoff. 메뉴 이탈과 인증 만료에서 멈추는지 검증.
2. **수강생 유형/메뉴별 초기 조회 분리**: 인터넷 화면에 없는 성적·체력 우선 제외 검토. 홈 진입이 모든 시험 정답을 기다리지 않게 한다. 오프라인/관리반 순위·외부 성적·과거 기록·답안 복구는 보존.
3. **홈/플래너용 작은 카페 조회**: 공통 방 상태와 본인 계획·장비·정산의 갱신 조건을 구분한다. 인증·포인트 중복 방지·좌석 유효성·04시 날짜 전환을 보존.
4. **교사 외출/사진 전역 갱신 축소**, 성적 메타데이터의 변경 단위 갱신. 실시간 출석/외출 승인 요구사항은 유지.
5. 비교 가능한 사용 시간대에서 요청 수, 오류율, API 지연, swap/I/O를 전후 확인. 요청 감소만으로 인프라 병목이 완전히 해소된다고 선언하지 않는다.

이번 작업은 조사이므로 수정·빌드·푸시·배포·마이그레이션·재시작·요금 변경은 하지 않았다. 제품 코드가 변하지 않아 전체 회귀 테스트를 다시 돌리지 않았고, 분석용 모의 실행과 소스/운영 로그 검증을 수행했다. 배포가 필요한 수정은 프로젝트 지침에 따라 최종 확인 후 진행한다.
