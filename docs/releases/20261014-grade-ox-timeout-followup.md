# 성적 조회 및 OX timeout 후속 최적화

상태: 앱 배포와 보류했던 DB 변경 모두 운영 적용 완료. 앱은 `cd283c7`로 먼저 배포했고, 사용자의 추가 진행 승인 후 2026-10-14 16:42 KST에 DB 연결·기존 함수 해시·잠금 대기를 확인하여 두 마이그레이션을 적용했다. 추가 Vercel 배포는 하지 않았다.

## 변경 내용

- 수강생 최초 진입·강제 새로고침에도 기존 주기 갱신의 정답/최종 성적 범위 제한을 적용한다. 최신 학생 명단을 읽은 뒤 기수·순위 비교 대상을 결정한다. 공통 시험, 과거 회차, 외부 응시자, 기수가 달라진 과거 동료 기록을 유지하며, 기수를 알 수 없으면 전체 조회로 보완한다.
- 학생이 바뀌거나 명단에서 기수가 변경되면 30초 메타데이터 갱신 간격 안에서도 정답 범위를 다시 읽는다. 조회 도중 계정이 바뀌거나 일부 조회가 실패하면 부분 결과를 게시하지 않는다.
- 학생 343명, 시험 38건이라는 운영 집계에 근거하여 명단·시험 메타데이터의 최신성은 유지한다. 기존 순위·이력과 화면 기능을 유지하며, 아래 추가 최적화에서 교사 자동 조회를 변경 감지 방식으로 바꾼다.
- OX 문제 요약을 본문/해설과 분리한 `ox_question_summaries`에 저장한다. 최초 채움과 함수 교체를 한 트랜잭션으로 수행하고, 문제 삽입/수정 트리거와 삭제 외래 키로 동기화한다. 정답은 서버 전용이며 기존 풀이 여부·버전·이용권 검사를 통과한 응답에서만 노출한다.
- OX `bootstrap`, `questions`, `attempt_counts`는 결과를 계산한 뒤 학생 기기 잠금을 잡고 기기·세션·학생·이용 상태와 이용권을 다시 검증한다. 조회 중 해제/교체/회수가 발생하면 결과를 폐기한다. RPC 호출 수는 늘리지 않는다.
- `detail`의 선택적 통계 집계도 잠금 밖에서 계산한다. 실제 문제 상세의 행 잠금은 기기 잠금 뒤에 유지하여 제출과 잠금 순서가 뒤집히지 않게 한다. 제출/메모/기기 시작·교체는 기존 잠금과 원자성을 유지한다. `device_start(includeBootstrap)` 역시 기존 원자성을 유지한다.
- 최종 검증은 새 커밋을 읽어야 하므로 조회 경로는 READ COMMITTED에서만 실행한다. 다른 격리 수준에서는 결과를 반환하지 않는다. 서비스의 기본 PostgREST 호출 방식을 사용한다.

- 합성 데이터 2,500여 문항에서 원본 행 평균 약 1,368바이트, 요약 행 약 64바이트. 새 요약 조회 결과/순서가 기존과 같고 임시 파일 쓰기는 0블록이었다. 운영 지연 개선율을 의미하는 수치는 아니다.
- 운영 환경 설정을 사용한 빌드 및 공개 설정의 비밀키 미포함 검사 통과. 생성된 `config.js`는 원래 바이트로 복구했다.
- 운영 학생 데이터는 변경하지 않았다. 운영에는 집계 및 함수/인덱스 정의 확인만 수행했다.

## 적용 순서

1. 검증한 변경 파일만 로컬 커밋한다. 기존 다른 작업의 변경 문서는 포함하지 않는다. 운영 반영은 최종 확인을 받은 후 진행한다.
2. 운영 함수 정의가 마이그레이션의 해시와 일치하는지 확인한다. 다르면 중단하고 차이를 검토한다.
3. `supabase/migrations/20261014074212_ox_narrow_catalog_and_short_read_locks.sql`을 적용한다. 잠금 대기는 2초, 전체 SQL 제한은 30초이며 실패 시 한 트랜잭션으로 취소한다. 운영에서 임의로 제한시간을 늘리지 않는다. 문제 편집과 겹치지 않는 시간에 적용한다.
4. `20261014074256_menu_read_revisions_and_cafe_summary.sql`도 별도 트랜잭션으로 적용한다. 잠금 대기 2초/전체 SQL 30초 제한이다. RLS/권한, 요약 행 수·원본과의 일치, 트리거, 함수 보안 및 이력을 확인하고 Supabase advisors를 재실행한다. OX 요약은 서버 전용이며 메뉴 변경 번호만 SELECT로 공개한다.
5. Git 푸시로 Vercel 배포를 한 번 진행한다. DB 변경은 기존 API/클라이언트와 호환되며 새 환경변수는 필요 없다.
6. 수강생 세 유형의 최초 진입/성적 갱신, 교사 시험·학생 목록, OX 진입/조회/제출/메모 및 기기 전환을 확인한다. 운영 확인에서 시험 답안·학생 진도를 임의로 작성하지 않는다.
7. 배포 직후뿐 아니라 이용량이 많은 시간대까지 Postgres 57014, API 5xx, 인증 잠금 대기, 응답 속도, Swap 활동/I/O 대기를 함께 관찰한다. 짧은 구간의 오류 0건으로 해결을 선언하지 않는다.

## 복구와 한계

- 프런트엔드는 이전 정상 배포로 되돌릴 수 있다.
- DB는 `supabase/rollback/20261014_ox_narrow_catalog_and_short_read_locks.sql`로 함수와 파생 요약 저장소를 복구한다. 이후 다른 함수 변경이 있으면 해시 검사로 중단한다. 실제 학생 진도·성적·문제 원본은 삭제하지 않는다. 로컬에서 복구 후 응답과 진도 보존을 확인했다.
- DB의 기존 메모리/Swap 압력은 별도 문제다. 증설이나 전역 timeout 변경은 포함하지 않았으며, 모든 timeout이 사라진다고 보장할 수 없다.
- 원자성을 유지해야 하는 제출/메모 및 세션 시작은 여전히 잠금을 사용한다. 오래된 클라이언트의 전체 bootstrap도 기존 반환 규약을 유지한다.

## 네이티브 동시성 테스트 재현

- 별도 로컬 PostgreSQL 17과 `pg` 패키지를 사용한다. 이번 검증 도구는 임시 경로에 고정 버전 `@embedded-postgres/windows-x64@17.10.0-beta.17`, `pg@8.23.1`로 설치했으며 앱 의존성은 변경하지 않았다.
- `OX_NATIVE_TEST_URL`을 테스트용 loopback 서버로 지정하고 `node tests/ox-read-lock-concurrency.test.cjs`를 실행한다. 필요하면 `OX_PG_MODULE`로 pg 모듈 경로를 지정한다.
- 테스트는 별도 DB를 만들고 정리하며, 앱 환경 파일을 읽지 않는다. 운영 접속 정보를 사용하지 않는다.

## 추가 메뉴 최적화 (추천 순서대로 완료)

1. 상점, 주간·월간 랭킹, 학생 알림, 교사 수험번호, 교사 푸시 이력, 교사 수강 신청의 오류 상태를 보존한다. 렌더링으로 자동 재시도하지 않으며 명시적인 다시 불러오기로 복구한다. 랭킹은 기간별 진행 요청도 중복하지 않는다.
2. 최신 명단에서 lecture로 확인한 인터넷 수강생은 시험·영역·정답·파일·과목 설정·제출·파이널·체력 조회를 제외한다. 등록 전에도 성적은 로그인 이후로 미룬다. 유형을 알 수 없는 등록 학생은 기존 조회로 보완한다. 교사 파이널은 안정적인 정렬로 전 페이지를 읽는다.
3. 교사 갱신은 outings/outing_photos 변경 번호만 먼저 읽는다. 변경이 없으면 전체 목록을 읽지 않는다. 다른 교사 메뉴에서는 외출 상태 변화는 반영하고 사진 전체 조회는 외출 관련 화면의 다음 갱신으로 미룬다. 기존 사진, 실시간 이벤트, 5초/30초 대체 갱신은 유지한다.
4. 홈·플래너는 personal_load로 본인 프로필·과목·할 일·목표·좌석·세션·오늘 공부 시간과 카페 인원 집계만 받는다. 다른 학생 세션·프로필·좌석 목록, 랭킹, 장비, 봇 외형을 읽지 않는다. 좌석 정리·공부 날짜 전환·포인트 정산을 유지하므로 일반 경로 DB HTTP 요청은 **6회로 동일**하다. 개선 대상은 RPC 내부 조회 범위와 응답량이다.
5. 성적 화면은 30초마다 변경 번호를 확인한다. 명단·공지·직렬·시험·영역·정답·파일·과목 설정이 그대로이면 성적만 갱신한다. 1페이지 fixture에서 기존 11회가 변경 없는 주기에는 4회(번호·제출·파이널·체력)로 줄었다. 페이지가 늘면 호출 수는 달라진다. 정답 수정·시험 공개·학생 기수 변경은 다음 갱신에서 다시 읽는다.

변경 번호는 원본 변경과 같은 트랜잭션에서 갱신한다. 빈 upsert와 같은 값 UPDATE는 번호를 올리지 않는다. 메타데이터 조회 전에 번호를 읽어 조회 중 커밋된 변경도 다음 갱신에서 감지한다. 답안 입력 보호와 계정 전환 후 응답 폐기를 유지한다.

### 추가 변경의 배포·복구 조건

- 변경 번호 테이블에는 이름과 숫자만 저장한다. RLS SELECT 정책을 공개하며 브라우저 쓰기는 금지한다. private 트리거 전용 함수는 직접 실행 권한을 회수한다. 본인 요약 함수는 security invoker, 빈 search_path, service_role 전용이다.
- 원본 쓰기 권한은 유지한다. 같은 테이블에 실제 변경이 집중되면 번호 행 쓰기가 직렬화되므로 운영 적용 후 쓰기 지연·잠금 대기도 관찰한다.
- 새 DB 객체가 없으면 기존 전체 조회로 보완한다. timeout 자체는 전체 조회로 확산하지 않는다.
- 추가 SQL 복구 파일: `supabase/rollback/20261014_menu_read_revisions_and_cafe_summary.sql`. 감지 트리거·번호 테이블·본인 요약 함수만 제거하며 학생·성적·사진·카페 원본을 보존한다.
- 적용 후 운영 데이터 작성 없이 조회와 로그로 확인한다. 혼잡 시간대 관찰 전에는 시간 초과가 모두 해결됐다고 판단하지 않는다.

## 후속 조회 비용 최적화 — 로컬 구현, 운영 미적용

사용자가 운영 안정성·실제 화면 점검(이전 1·2번)은 해결됐다고 확인했다. 이후 승인한 우선 범위인 랭킹·공부 통계, 교사 최초 접속, 상점 조회를 구현했다. 같은 집계 함수를 교사 장기간 공부 기록 요약에도 적용했다. 게시판·문의 검색 및 홈·플래너의 추가 정산 통합은 이 배포 묶음에 포함하지 않는다.

- `20261014082858_cafe_period_read_models.sql`: 새 읽기 함수 3개만 추가한다. 기존 세션 원본, 인증·좌석 정리·오전 4시 날짜 전환·포인트 정산의 호출 순서와 트랜잭션은 유지한다. 함수는 `SECURITY INVOKER`, 빈 search_path, service_role 전용이며 anon/authenticated/PUBLIC 실행을 차단한다. 새 테이블·인덱스·설정 변경은 없다.
- 주간·월간 랭킹과 공부 통계는 기간·학생 범위를 SQL에서 집계한다. 교사 공부 기록 목록도 세션 원본 대신 학생별 합계를 사용한다. 선택 학생 상세 기록 조회는 유지한다. 동일 합계의 랭킹 순서는 학생 ID 기준으로 고정해 두 조회 경로에서 일치시킨다. 순번·백분위 산식과 이름 마스킹은 유지한다.
- 상점은 기존 정산을 한 번 완료한 뒤 상품·보유품·장비·최근 30개 내역을 읽기 함수 하나로 가져온다. 일반 빈 상태 API 테스트에서 랭킹 DB HTTP 요청은 8→5회, 상점은 9→6회다. 좌석 정리·날짜 전환이 발생하면 요청 수는 더 많아질 수 있다.
- 새 함수가 없는 경우(404/PGRST202)에만 기존 조회로 보완하며 누락 함수 재확인에는 backoff를 적용한다. 랭킹·개인 통계의 호환 경로도 안정적인 정렬과 페이지 조회로 바꿨다. Content-Range가 있으면 서버 행 상한이 요청 크기보다 작아도 끝까지 읽는다. timeout/잘못된 응답에는 전체 조회를 재시도하지 않는다. 비상시 `STUDY_CAFE_READ_MODELS_ENABLED=false`로 기존 페이지 경로를 선택할 수 있다.
- 교사는 공통 초기 로딩에서 시험 5종·파이널·기기 등록 이력을 제외하고 해당 메뉴 진입 시 읽는다. 학생 목록은 상세/미리보기 의존성을 보수적으로 보존해 시험·파이널 자료를 준비한다. 홈·외출에서 먼저 읽은 사진은 초기 공통 로딩에서 다시 읽지 않는다. 사진과 사진 기반 복귀 시각을 보존하며 사진과 무관한 메뉴의 첫 접속은 사진 조회를 미룬다.
- 지연 로딩은 메뉴 진입 시 로딩 표시, 실패 시 수동 재시도, 동시 요청 합치기, 로그아웃·초기화 후 오래된 응답 폐기를 포함한다. 학생 앱의 조회 범위는 유지한다. PWA 캐시는 v479로 갱신했다.
