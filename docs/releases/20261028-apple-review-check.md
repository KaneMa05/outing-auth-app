# Apple 2.1 추가 정보 요청 대응

2026-10-28 · 사용자 최종 승인 후 운영 반영 진행. 신고·차단 테이블 2개 적용과 서버 환경 변수
등록 완료. 아래 검토는 준비 시점 기준이며 실제 커밋·배포·운영 검증 결과는 로컬
`artifacts/app-review-20261028/deployment-receipt.json`에 기록한다.
Apple 답변/Notes 등록과 새 네이티브 클라우드 빌드는 이번 반영에 포함하지 않는다.

## 확인된 사실

- 사용자 제공 메시지는 신규 개발자 계정에 대한 추가 정보 요청이다. 구체적인 충돌 재현 정보는 없다.
- 영상, 목적·대상, 이용 방법·계정, 외부 서비스, 지역 차이, 해당 시 권한 증빙의 6개 항목을
  **심사 메시지 답변과 App Review Information의 Notes 양쪽에** 제공해야 한다.
- 사용자 확인: 모든 앱 기능 무료, 실제 iPhone에서 직접 녹화 가능.
- 사용자 최종 정정: 심사용 계정으로 게시판·스터디룸 채팅은 열리지만 **면접반은 열리지 않는다**.
  면접반을 시연 가능한 기능으로 답변하거나 별도 면접 기능을 이번 배포에 섞지 않는다.
- `native/BUILDING.txt`의 제출 기록: 1.0.0 (4), 대한민국만, 수동 출시,
  제출 ID `dacecc86-102b-4857-b841-3166cf0b60c0`. 현재 콘솔 상태를 다시 조회한 결과는 아니다.
- App Store Connect 로그인 세션에 접근할 수 없어 현재 심사용 자격 증명/기기 여유와 Notes는 확인하지 못했다.
- 2026-10-28 운영 서버의 공개 파일 6개를 인증 없는 HTTPS GET으로 확인했다.
  운영 `app.js`에는 신규 삭제 접수 API가 없고, 운영 면접반 My에는 계정 삭제 링크가 없다.
  HTTP 200은 실기기 기능 검증을 의미하지 않는다.
  로컬 증빙: `artifacts/app-review-20261028/public-surface.json` (비밀값 없음).
- 웹 기반 화면은 운영 서버에서 로드된다. 제출된 네이티브 소스나 로컬 워크스페이스와
  심사 시점의 운영 웹 기능이 같다고 가정하지 않는다.

## 이번 로컬 수정

일반 수강생 3개 유형의 마이 → 계정 및 데이터 삭제에서 외부 메일 앱 없이 전체 삭제를 접수한다.
등록된 기기 토큰을 서버에서 검증한 본인 계정에만 접수·조회하며, 확인 문구를 요구한다.
기존 비공개 `student_inquiries`에 삭제 요청이 저장되어 권한 있는 운영자의 문의 관리에 표시된다.
삭제 요청은 기존 문의 테이블을 사용한다. 운영 DB 변경이나 실제 사용자 데이터 삭제는 하지 않았다.

기존 요청 재조회, 처리 안내 새로고침, 네트워크/저장 실패 표시를 제공한다. 접수 화면은 실제
삭제 완료를 주장하지 않는다. 기존 문의 API로 이 요청을 수정·숨기거나 일반 문의를 삭제 요청으로
위장하지 못하도록 막았다. 관리자는 답변 등록만으로 삭제가 실행되지 않는다는 안내를 받는다.
공개 안내·개인정보처리방침, 에셋 버전과 서비스워커 캐시도 함께 갱신했다.

운영자는 실제 요청 접수 후 기존 `artifacts/play-console/deletion-operations.json`의 절차에 따라
연결된 데이터·Storage 파일·외부 처리 사본을 실제 삭제하고 등록 연락처로 결과를 안내해야 한다.
이 변경은 **삭제 요청 접수**를 구현한다. 자동 전체 삭제 엔진을 구현한 것은 아니다.
Apple은 합리적인 기간의 수동 처리를 허용하지만 일반 앱에서 이메일 문의를 필수로 요구하는
흐름은 허용하지 않는다.

게시판·댓글·스터디룸 채팅·공개 의견/답글·카페 프로필과 룸 이름에 신고·작성자 차단을 연결했다.
차단은 계정별로 저장하고 서버 조회에서 적용한다. 글·댓글은 페이지를 나누기 전에 제외하며
직접 상세 접근도 차단한다. 룸 스냅샷과 기존 조회 경로 모두 차단한 사용자의 채팅을 제외하고
닉네임·상태 메시지를 가린다. 좌석과 타이머는 해제하지 않는다. 다음 조회가 실패해도 현재
캐시의 해당 채팅·닉네임을 즉시 가린다. 등록번호 대신 서버가 만든 불투명 식별자를 사용한다.

마이 → 차단한 사용자에서 해제하며, 관리자 문의 관리 → 콘텐츠 신고 관리에서 원문/첨부를
확인하고 콘텐츠 숨김·신고 기각을 처리한다. 기본 부적절 표현 필터와 커뮤니티 이용 규칙·문의처를
추가했다. 자동 필터가 모든 유해 자료를 탐지한다고 주장하지 않는다. 첨부 이미지도 신고 후
운영자가 원문을 확인해 처리하며 작성자 차단 시 그 사람의 첨부도 글과 함께 제외된다.

새 마이그레이션 `supabase/migrations/20261028025133_student_content_safety.sql`은
`student_content_blocks`, `student_content_reports` 두 테이블만 추가한다.
두 테이블은 RLS를 켜고 public/anon/authenticated 직접 접근을 차단한다. 기존 학습 테이블은
변경하지 않는다. **운영 DB에는 아직 적용하지 않았다.** 차단·신고 기능은 서버 환경 변수
`STUDENT_CONTENT_SAFETY_ENABLED=true`가 필요하다. 기존 하트비트·타이머 동작에는 차단 목록
추가 조회를 넣지 않았고, 사용자 콘텐츠를 읽을 때만 필요한 목록을 조회한다.

## 운영 반영의 구체적 범위

1. 사용자 최종 확인 후 `20261028025133_student_content_safety.sql`을 운영 DB에 1회 적용한다.
   기존 학생·학습 테이블 변경 없이 신고·차단 테이블 2개와 해당 인덱스/권한만 추가한다.
2. `selective-source.json`의 파일만 HEAD 위에 반영한 소스를 사용한다. 기존 네이티브/면접의
   미커밋 변경과 비밀 환경 파일, 생성된 스토어 증빙은 배포에서 제외한다.
3. 웹/API 배포에서 `STUDENT_CONTENT_SAFETY_ENABLED=true`를 설정한다.
   필요한 테이블 없이 먼저 기능을 활성화하지 않는다. 새 API들은 기존 서버 측 Supabase 설정을 사용한다.
4. 운영에서 전용 테스트 계정으로 삭제 요청·신고·차단·해제를 확인하고 관리자 신고함에
   접수되는지 확인한다. 실제 학생을 삭제하거나 다른 사람의 기기를 해제하지 않는다.
5. 운영자는 새 신고함을 정기적으로 확인하고 신속히 조치한다. 삭제 요청은 10일 이내 결과 안내와
   실제 연결 데이터/파일 정리가 필요하다. 두 신규 테이블의 계정 연결 자료도 정리 대상이다.
6. 사용자 실기기 영상과 데모 계정 접근 확인이 끝난 뒤 심사 답변/Notes를 완성한다.
   Apple 답변 전송이나 재제출은 이 준비 단계에서 수행하지 않았다.

   로그인 정보는 저장소에 기록하지 않고 App Store Connect의 비공개 심사 입력란에 넣는다.
5. 영상과 6개 답변을 심사 메시지 및 Notes 양쪽에 등록한다. 영상과 필수 사실이 갖춰지기 전에
   완성된 답변인 것처럼 보내지 않는다. 현재 버전에 새 빌드가 필요한지는 보완 방식에 따라 판단한다.
