# 스터디카페·성적 조회 최적화 — 적용 전 검증

2026-10-14. 대상: 인프라 점검의 우려 3번과 4번. 로컬 구현과 검증 완료 상태이며 푸시, Vercel 배포, 운영 DB 마이그레이션, 운영 환경변수 변경은 수행하지 않았다.

## 3번: 스터디카페 조회 요청 묶기

- `api/study-cafe.js`에서 기존 스냅샷, 본인 장비, 봇 외형을 새 읽기 전용 RPC 하나로 가져온다. 동일 API 응답 비교 테스트에서 상점 이용 가능한 학생의 정상 `load` 요청에 대한 Supabase HTTP 호출이 **8회 → 6회**로 감소했다. Vercel 함수 호출 수나 내부 SQL 실행 수가 25% 감소했다는 의미는 아니다. 운영 지연시간 개선율은 배포 후 측정해야 한다.
- `STUDY_CAFE_SNAPSHOT_BUNDLE_ENABLED=true`일 때만 활성화한다. 기본값/미설정은 기존 경로다. 기기 검증, 자리 만료 정리, 날짜 전환, 포인트 정산은 기존 경로를 유지한다. 포인트 정산과 읽기 RPC는 병렬로 실행하며, 새 RPC가 없는 경우에도 정산을 다시 실행하지 않는다.
- 마이그레이션 `20261014023329_study_cafe_snapshot_bundle.sql`은 기존 함수를 수정하지 않고 새 함수를 추가한다. `SECURITY INVOKER`, 빈 `search_path`, `service_role` 전용 실행 권한이다. 학생·익명 클라이언트는 직접 호출할 수 없다.
- 함수 미설치 오류(`404/PGRST202`)만 기존 조회로 대체하고 재시도 대기 시간을 적용한다. DB 시간 초과나 잘못된 응답에서는 여러 기존 요청을 추가로 보내 부하를 늘리지 않는다. 선택적 장비·봇 모듈이 없는 구형 스키마도 기존 대체 경로를 사용할 수 있다.
- 공유 캐시를 추가하지 않았다. 장비 변경을 다음 조회에서 그대로 반영한다. 화면 갱신 간격, 30초 heartbeat, 2분 안전 조회 및 04시 학습일 경계는 변경하지 않았다. 정산 호출 간격 조정과 Realtime 부분 갱신은 이 변경에 포함하지 않는다.

## 4번: 성적 주기 갱신의 조회 범위 축소

- 기존 30초 시험 정보 갱신 시점마다 전체 앱 조회로 돌아가던 경로를 성적 전용 갱신으로 변경했다. 출석·외출·벌점·휴일 4개 테이블과 외출 사진 조회를 생략하며, 다른 탭의 기존 상태를 지우지 않는다.
- 학생 명단·공지/설정·시험·문항 구성·공개 상태는 계속 새로 가져온다. 학생 소속 기수와 공통 시험의 모든 직렬·회차·과거 문항을 보존하면서 다른 기수의 정답 조회를 제외한다. 기수를 판단할 수 없으면 기존 전체 조회로 대체한다. 첫 진입 및 강제 전체 새로고침의 정답 조회는 기존 전체 조회를 유지한다.
- 파이널 성적은 해당 기수, 기수 없는 기록, 순위 비교 대상 학생의 과거 기수 기록을 포함한다. 외부 응시 여부 플래그만으로 제외하지 않는다. 대상 학생이 80명보다 많거나 기수가 불명확하면 동일 외부 기록을 여러 번 조회하지 않도록 한 번의 전체 페이지 조회를 사용한다.
- 정답은 80개 문항 묶음, 각 요청 1,000행 단위로 끝까지 조회한다. 파이널 성적도 1,000행 단위로 끝까지 조회한다. 기간을 잘라 과거 비교를 누락하지 않는다.
- 조회 도중 로그아웃/계정 변경/답안 입력이 시작되면 성적 전용 결과를 적용하지 않는다. 일반 조회 실패에서도 기존 표시 데이터를 보존한다.
- 교사 경로와 화면 UI는 변경하지 않았다. 변경된 공용 스크립트의 학생·교사 URL 및 서비스 워커 캐시 버전을 일치시켰다. 새 버전 설치가 열린 화면을 강제로 이동시키지 않는 기존 동작도 회귀 테스트로 확인했다.

## 체력 인덱스 판단

운영 DB에서 읽기 전용 실행계획과 SELECT 실행시간을 확인했다. 활성 18기 학생 최대 80명을 대상으로 `student_id = ANY(...)`, `assessment_month DESC, updated_at DESC, id ASC`, `LIMIT 1000` 조건을 사용했다. 실제 애플리케이션처럼 ID 목록을 전달하는 대신 측정 쿼리 안에서 ID 배열을 구성했다.

- 기존 `fitness_scores_month_student_idx` 사용, 274행 반환.
- 실행 4.197ms, 계획 수립 15.127ms. 디스크/임시 블록 읽기와 쓰기 0. 단일 측정이며 모든 시간대의 성능을 대표하지 않는다.
- 현재 결과만으로 새 인덱스의 이득이 입증되지 않아 추가 DDL은 준비하지 않았다. 기존 중복 `(assessment_month, student_id)` 인덱스도 이번에 제거하지 않았다. 데이터 증가나 해당 조회 지연이 확인되면 실제 조건으로 전후 실행계획을 비교하고 결정한다.

## 검증

- 전체 `npm test`의 pretest/main/posttest 통과. Windows CRLF 체크아웃에서 기존 소스 추출 테스트가 동작하도록 읽은 문자열의 줄바꿈만 정규화하는 기존 로컬 어댑터(`NODE_OPTIONS=--require=./.tmp/normalize-test-newlines.cjs`)를 사용했다. 제품 코드와 테스트 단언은 완화하지 않았다.
- `npm run test:read-optimization` 통과: HTTP 호출 감소, 전체 응답 동등성, 온라인 관리반/인터넷 수강생 접근, 오프라인 접근 제한, 기기 해제, 미설치 대체 경로, 장애 시 요청 증폭 방지, 30초 경계, 다른 탭 상태 보존, 오류·로그아웃·답안 보호, 페이지/80개 묶음 경계, 실제 파이널 순위·이전 회차 결과 동등성.
- `npm run test:read-optimization:db` 통과: 로컬 PGlite에서 기존 SQL 함수와 신규 함수 결과 비교, 반복 설치, 읽기 전용 동작, 사용자별 장비 분리, 권한, 선택 모듈 누락. 기존 로컬 PGlite 패키지를 사용하며 다른 환경에서는 `PGLITE_MODULE`로 경로를 지정할 수 있다. 운영 DB 연결을 사용하는 테스트가 아니다.
- 운영용 환경 설정으로 `build-config.js` 실행 및 공개 설정 검증 통과. 서버 비밀키/최적화 플래그가 클라이언트 설정에 포함되지 않음을 확인했다. 기존 `config.js`는 바이트 단위로 복원했다. 이 프로젝트의 build는 설정 파일 생성이며 번들 컴파일 단계는 없다.
- 변경 JavaScript 문법 검사 및 `git diff --check` 통과. 실제 운영 새 코드, 여러 연결에서의 부하 테스트, 사용자 브라우저 실사용 검증은 아직 수행하지 않았다.

## 사용자 승인 후 단계별 적용

1. **성적 변경 먼저:** 신규 스터디카페 플래그가 미설정/false임을 확인하고 앱을 배포한다. 운영 사용자에게 강제 새로고침을 요구하지 않는다. 오프라인·온라인 관리반의 성적 최초 진입/30초 갱신/다른 탭 이동, 교사 성적 입력·공개·삭제 반영, 기존 페이지를 열어둔 사용자의 흐름을 확인한다. 기존 코드가 열린 클라이언트도 기존 API와 호환된다.
2. **스터디카페 준비:** 관찰 결과 정상일 때 위 마이그레이션 파일 하나만 적용한다. 관련 없는 대기 마이그레이션을 함께 올리지 않는다. SQL은 3초 lock timeout, 15초 statement timeout을 사용한다. 실패하면 해당 단계에서 중단한다. 기존 함수/테이블의 삭제나 데이터 변환은 없다.
3. **스터디카페 활성화:** 온라인 관리반·인터넷 수강생의 검증 계정으로 기존/신규 응답과 입실·일시정지·퇴실·장비·포인트를 확인한 뒤 `STUDY_CAFE_SNAPSHOT_BUNDLE_ENABLED=true`를 포함한 배포로 활성화한다. 환경변수 변경만으로 기존 Vercel 배포가 바뀐다고 가정하지 않는다. 프리뷰가 운영 DB를 공유한다면 정산·접속 테스트도 운영 쓰기를 만들 수 있으므로 DB 테스트는 격리 환경에서 먼저 한다.
4. 각 단계 후 동등한 트래픽 시간대의 API 오류율·p75/p95, Supabase 요청 수·DB 연결·timeout·swap/IOwait를 비교한다. 15~30분 초기 관찰 후 피크 시간대와 다음 04시 전환도 관찰한다. 기기 인증/자리/포인트/순위 불일치는 즉시 중단 기준이다. 성능 회귀가 지속되면 다음 단계로 진행하지 않는다.

각 푸시·배포와 운영 DB 적용은 실제 실행 전에 사용자의 최종 확인을 받는다. 이번 파일은 실행 결과가 아닌 승인 후 절차다.

## 되돌리기

- 스터디카페: 플래그가 false/미설정인 검증된 이전 배포로 복귀한다. 단순 환경변수 수정은 이미 실행 중인 배포의 복구가 아니다. 새 읽기 전용 DB 함수는 남겨도 기존 코드에 영향이 없으므로 장애 중 제거 DDL을 수행할 필요가 없다.
- 성적: 이전 검증된 앱 배포로 복귀한다. 특정 브라우저 비교 진단에는 기존 `?scopedRefresh=0` 옵션을 사용할 수 있으나 전체 사용자 대상 복구 수단으로 간주하지 않는다. 이미 열린 페이지에는 이전/신규 코드가 잠시 공존할 수 있으므로 세션 및 입력을 강제로 초기화하지 않는다.
- 어느 단계도 학생 데이터 마이그레이션을 하지 않아 데이터 복원 작업이 필요하지 않다. 복귀를 위한 배포도 프로젝트의 최종 확인 규칙을 따른다.
