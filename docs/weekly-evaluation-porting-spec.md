# 주간평가 답안 입력·성적조회 개발 명세

작성 기준: 2026-09-28 로컬 저장소의 구현. 운영 서버의 배포 버전·실제 DB 정책을 조회한 문서는 아니다.

이 문서는 다른 앱에서 기능을 재구현할 개발자 또는 개발 AI에게 전달하기 위한 자료다. **현재 구현**과 **새 앱 권장 설계**를 구분한다. API 예시는 새 앱용 제안이며 현재 앱에 존재하는 API라는 뜻이 아니다.

## 1. 개발 범위

핵심 범위는 학생의 주간평가 답안 입력, 검토·최종 제출, 자동 채점, 주차별 성적조회, 내 답안지와 해설 PDF 조회다. 이를 운영하기 위한 교사의 시험·과목·정답 관리, 재채점, 답안 초기화도 필요하다.

현재 성적 메뉴는 오프라인 수강생 및 온라인 관리반 화면에 있다. 인터넷 수강생(`lecture`)의 일반 허용 경로에는 `grades`가 없다. 다른 앱의 이용 대상은 별도로 정하되, 기존 앱의 모든 학생 유형에 성적 메뉴가 있다고 가정하지 않는다.

성적조회에는 주간평가 외에 파이널 성적도 포함된다. 파이널은 10절에 별도 기술한다. 체력평가와 다른 학습 기능은 이식 범위에 포함하지 않는다.

필수 학생 정보: 고유 학생 ID, 이름, 기수(`cohort`), 직렬(`track`). 동명이인이 있어도 학생 ID로 구분한다. 직렬은 학생 정보 → 프로필 직렬 → 최초 직렬 순서로 확인하고 표기를 정규화한다.

## 2. 학생 화면과 사용 흐름

```text
성적 메뉴
 ├─ 주간평가 답안 입력
 │   └─ 주차 선택 → 과목 목록 → 과목 선택
 │       └─ 10문항씩 입력 → 전체 답안표 검토
 │           └─ 확인 체크 → 최종 확인 → 저장 → 제출 완료
 │               └─ 공개 조건 충족 시 내 답안지 / 답안·해설 PDF
 └─ 성적 조회
     ├─ 주간평가 → 주차 선택 → 성적 요약 + 과목별 성적
     └─ 파이널 성적 → 회차 선택 → 성적 요약 + 과목별 성적
```

### 2.1 주차·과목 목록

- 조회 가능한 주차를 내림차순으로 표시하고 가장 높은 주차를 기본 선택한다.
- 회차는 공개 상태이고, 유효한 시작 시간이 있으며, 현재 시간이 시작 시간 이후여야 보인다.
- 학생과 시험의 기수가 모두 있으면 일치해야 한다. 둘 중 하나가 비어 있으면 현재 코드는 기수 필터를 통과시킨다.
- 학생에게 해당하는 활성·출제 완료 과목이 적어도 하나 있어야 회차가 목록에 나온다.
- 과목 카드는 과목명, 제출 상태, 본인에게 보이는 문항 수, 만점, 입력 버튼을 표시한다.
- 상태 문구: `미제출`, `입력 중`, `추가 입력 필요`(draft), `제출 완료`.
- 기존 draft는 `답안 이어 입력`, 제출 기록은 있으나 유효한 저장 답안이 전혀 없으면 `답안 다시 입력`을 제공한다.
- 현재 입력 가능 판단은 시작 시간만 확인한다. `end_at`에 의한 마감은 구현되어 있지 않다.

### 2.2 답안 입력

- 학생은 매 문항에서 **1·2·3·4 중 하나만 선택**한다.
- 한 페이지에 10문항을 표시한다. 이전 10문제, 다음 10문제, 검토 후 제출 버튼을 제공한다.
- 선택한 보기의 강조·접근성 상태를 갱신한다. 다른 보기를 누르면 선택이 바뀐다.
- 정답을 여러 개 인정하는 문항이어도 학생이 복수 선택하는 UI는 아니다.
- 직렬에 따라 일부 문항만 응시하면 화면 번호는 1부터 연속 표시하지만 저장은 원래 문항 번호를 사용한다. 예: 원본 2·5·8번 → 화면 1·2·3번 → 저장 키 2·5·8.
- 기존 저장 답안이 있으면 복원하고 첫 미입력 문항이 있는 페이지부터 연다.
- 일반 입력 중의 답안은 메모리 draft다. 매 선택마다 서버에 자동 저장하는 기능은 현재 없다. 새로고침·메뉴 이동 후 항상 복원된다고 안내하면 안 된다.

### 2.3 검토·최종 제출

- 전체 답안을 번호별 표로 표시한다. 선택 값은 ①~④, 미입력은 `-`로 표시하고 미입력 번호를 별도 안내한다.
- 문항 칸을 누르면 해당 문항이 있는 입력 페이지로 돌아간다.
- `위 답안을 모두 확인했습니다.` 체크 전에는 최종 제출 버튼을 비활성화한다.
- 미입력이 하나라도 있으면 제출을 차단한다. 제출 처리 함수에서도 다시 검증한다.
- 최종 확인 문구는 문항 수와 `제출 후에는 답안을 수정할 수 없습니다.`를 포함한다.
- 저장 중에는 중복 제출, 답안 수정, 페이지·주차 이동, 돌아가기를 막고 페이지 이탈 경고를 사용한다.
- 5초·15초·30초 경과 시 저장 지연 안내를 표시한다. 지연 안내 자체가 저장 실패 판정은 아니다.
- 서버에 제출과 모든 대상 문항의 선택 값이 저장된 것을 확인한 뒤 제출 완료를 안내한다.
- 정상 제출 후 학생은 수정할 수 없다. 교사가 해당 학생·과목 답안을 초기화하면 다시 입력한다.

### 2.4 내 답안지·해설

- 내 답안지에는 과목 점수, 정답 수, 오답 수, 문항별 내 선택·인정 정답·정오를 표시한다.
- 필요한 답안이 캐시에 없으면 해당 제출 ID의 상세 답안을 조회한다.
- 현재 답안지의 정오는 현재 정답표로 다시 계산한다. 정답 변경 후에는 저장 점수도 재채점되어야 일치한다.
- 답안·해설은 PDF이며 새 창으로 연다. 회차 업로드 한도는 2개, 개별 파일은 10MiB다.
- 동일 파일이 여러 과목에 연결되어도 경로/URL 등을 기준으로 한 번만 표시한다.

## 3. 공개 조건: 화면별 현재 동작

| 대상 | 현재 조건 |
|---|---|
| 회차 목록 | 공개 + 시작 시간 도달 + 기수 조건 + 대상 출제 과목 존재 |
| 과목 출제 완료 | 활성 과목이고, 학생에게 보이는 정답표가 준비됨 |
| 일반 과목 정답표 | 답안 행 수가 과목 문항 수 이상이며 모든 행에 인정 정답 존재 |
| 해사법규 정답표 | 본인 대상 문항이 1개 이상이며 그 문항 모두에 인정 정답 존재 |
| 입력 화면 과목 점수·내 답안지 | `hidden`: 숨김 / `after_submit`: 해당 과목 제출 후 / `after_all_submitted`: 현재 대상 과목 모두 제출 후 |
| 별도 성적조회 화면 | 제출 과목이 하나라도 있으면 요약·과목별 성적 표시. 위 점수 공개 모드를 검사하지 않음 |
| 답안·해설 PDF | `hidden`이면 숨김. 그 외에는 현재 대상 과목 모두 제출해야 표시 |

`canStudentSeeExplanation()`에는 `after_submit` 분기가 있지만 실제 PDF 목록은 모든 과목 제출 여부를 직접 확인한다. 함수 이름이나 DB enum만 보고 공개 정책을 추정하지 않는다.

현재 `준비 완료`는 노출되는 과목이 하나 이상인지로 판단한다. 모든 예정 과목이 출제되어야 응시하는 구조가 아니다. 준비중 안내 문구는 이 구현과 차이가 있다. 시험 중 과목 추가·비활성화·정답 삭제는 대상 과목, 만점, 공개 조건에 영향을 줄 수 있다.

**새 앱 권장 설계:** 공개 판단 함수를 서버에서 공통 사용하고 `scoreVisible`, `answerSheetVisible`, `explanationVisible`을 응답한다. 현재 화면별 차이를 그대로 재현할지는 개발 착수 시 정책 항목으로 명시한다.

## 4. 직렬·과목·문항 매칭

### 4.1 기본 과목 구성

| 직렬 | 기본 과목 |
|---|---|
| 수사특채 | 해양경찰학개론, 형사법, 형사법(공판) |
| 경찰직 - 공채(순경) | 해사법규, 해양경찰학개론, 형사법 |
| 경찰직 - 해경학과 항해(경장) | 해사법규, 해양경찰학개론, 형사법, 항해학 |
| 경찰직 - 해경학과 기관(경장) | 해사법규, 해양경찰학개론, 형사법, 기관학 |
| 경찰직 - 함정요원 항해(순경) | 해사법규, 해양경찰학개론, 해사영어, 항해학 |
| 경찰직 - 함정요원 기관(순경) | 해사법규, 해양경찰학개론, 해사영어, 기관학 |
| 경찰직 - 해상교통관제(VTS)(순경) | 해사법규, 해양경찰학개론, 항해학 |
| 일반직 - 선박교통관제(VTS) | 해사법규, 해사영어, 항해학 |
| 경찰직 - 경위 공채(해양-기관) | 해사법규, 해양경찰학개론, 형사법, 형사법(공판), 기관학 |
| 경찰직 - 경위 공채(해양-항해) | 해사법규, 해양경찰학개론, 형사법, 형사법(공판), 항해학 |
| 경찰직 - 함정요원 항해(경장) / 기관(경장) | 기본 필기 과목 없음 |

과목 표시 순서는 해사법규 → 해양경찰학개론 → 형사법 → 형사법(공판) → 해사영어 → 항해학 → 기관학이다.

- `exam_subject_settings`의 직렬별 활성 설정이 기본 구성을 대체할 수 있다.
- 경위 공채 두 직렬은 해사법규가 필수다. `해상교통관리`는 별도 주간평가 과목에서 제외한다.
- 과목 섹션은 직렬이 학생 직렬 또는 `전체`일 때 매칭한다. `전체` 섹션에는 직렬별 과목 허용 설정을 적용한다.
- 같은 과목에 매칭되는 공통 섹션과 직렬 전용 섹션이 모두 있으면 전용 섹션을 우선한다.
- 현재 회차 노출은 섹션 매칭으로 판단한다. 회차의 `target_tracks`만으로 접근 대상을 결정하지 않는다.

### 4.2 해사법규 문항별 대상

현재 문항별 대상 직렬 기능은 해사법규에 적용한다. 공채(순경), 함정요원 항해·기관(순경), 경찰직 VTS(순경), 경위 공채 해양-기관·항해는 고정 대상이다. 일반직 VTS 및 해경학과 항해·기관은 문항별 선택 대상으로 추가한다. 대상 배열을 정규화할 때 고정 대상은 항상 포함된다.

새 앱에서는 직렬 표시명과 내부 ID를 분리하고 과목 구성·통합 순위 그룹·문항 대상을 설정 데이터로 관리하는 방식을 권장한다.

## 5. 채점·성적·순위

### 5.1 채점

- 기본은 과목당 20문항·100점·문항당 5점이다. 문항 수는 변경할 수 있다.
- 현재 로딩 정규화는 과목 만점을 기본 사양인 100점으로, 배점을 `100 / 문항 수`로 맞춘다. 임의 배점이 계속 유지된다고 가정하지 않는다.
- 교사는 복수 인정 정답을 등록할 수 있다. 예: 정답 입력 `13` → `[1, 3]` → 학생이 1 또는 3을 고르면 정답.
- `correct_answers`가 비어 있으면 이전 단일 정답 필드 `correct_answer`를 사용한다.
- 정답이면 배점 전부, 오답이면 0점이다. 감점·부분점수는 없다.
- 해사법규에서 직렬별 보이는 문항 수가 전체 문항 수와 다르면 `과목 만점 / 보이는 문항 수`로 배점을 다시 계산한다.
- 균등 배점은 소수 셋째 자리로, 과목 제출 점수는 합산 후 소수 첫째 자리로 반올림한다. 보정되는 과목의 표시 만점은 과목 만점 자체다.
- 정답 수는 맞힌 문항 개수, 오답 수는 제출한 과목의 대상 문항 수에서 정답 수를 뺀 값이다.
- 전체 만점은 현재 대상 과목의 만점 합계다. 일부 과목만 제출해도 미제출 과목 만점이 분모에 포함된다.

예: 3과목 중 한 과목만 80점으로 제출하면 총점 80/300점, 득점률 26.7%다. 오답은 제출한 과목의 오답만 집계한다. 미제출 과목은 과목별 화면에 `미제출`로 표시한다.

### 5.2 학생 주간평가 순위

1. 같은 기수와 같은 순위 그룹의 학생을 모은다.
2. 하나 이상의 과목을 제출했고 전체 만점이 0보다 큰 학생만 순위에 포함한다.
3. `득점률 = round(총점 / 전체 만점 × 100, 1)`을 계산한다.
4. 득점률 내림차순 → 총점 내림차순으로 정렬한다.
5. 현재 학생 주간평가 화면은 정렬 위치 + 1을 등수로 사용한다. 동점을 공동 등수로 묶지 않는다.

순위 그룹은 기본적으로 직렬별이다. **경찰직 - 함정요원 항해(순경)**와 **경찰직 - 해상교통관제(VTS)(순경)**는 같은 그룹으로 합산한다. 일반직 VTS는 이 통합 그룹에 포함되지 않는다.

과목별 순위는 같은 그룹에서 해당 과목 제출자를 대상으로 득점률 내림차순 → 점수 내림차순 → 오답 수 오름차순으로 정렬한다. 역시 현재 학생 주간평가 코드는 위치 기반 순위다.

### 5.3 내 위치·전회차 비교

```text
응시자 수 N <= 1이면 topPercent = 0
그 외 topPercent = round((등수 - 1) / (N - 1) × 100, 1)
전체 요약: topPercent <= 1이면 "상위 1% 이내"
그 외: "상위 ceil(topPercent)%"
과목별: "상위 max(1, ceil(topPercent))%"
등수 변화 = 직전 주차 등수 - 현재 등수
```

5명 중 1등은 상위 1% 이내, 3등은 상위 50%, 5등은 상위 100%다. 이는 득점률과 다른 지표다. 등수 변화가 양수면 ▲, 음수면 ▼, 0이면 동일로 표시한다. 직전 주차가 없으면 더 과거 주차를 찾아가지 않는다.

성적 요약에는 직렬, 내 위치, 응시자 수·등수, 전회차 대비 변화, 위치 막대, 총점/만점, 오답 수, 등수가 표시된다. 과목별로 점수, 오답 수, 상위 비율을 표시한다.

### 5.4 교사 순위와의 차이

교사 주간평가 순위는 득점률 → 총점 → 오답 수 → 학생 ID 순으로 정렬하고, 득점률·총점·오답 수가 같으면 공동 등수(예: 1, 1, 3)를 준다. 상세 답안이 모두 있으면 저장 점수보다 답안 재계산 결과를 우선한다.

따라서 동점 등 특정 조건에서 학생 화면과 교사 화면의 등수가 다를 수 있다. 새 앱 권장 설계는 서버의 단일 순위 계산을 두 화면이 함께 사용하는 것이다. 기존 학생 화면을 정확히 재현해야 한다면 그 순위 규칙을 별도로 유지해야 한다.

## 6. 데이터 구조

아래는 현재 테이블의 주요 필드다. 실행용 전체 마이그레이션은 아니며 새 앱의 인증·학생 모델에 맞춰 생성한다. 시험 관련 ID는 기본적으로 UUID, 학생 ID는 현재 앱에서 text다.

| 테이블 | 주요 필드 | 관계·중복 방지 |
|---|---|---|
| `students` | `id`, `name`, `cohort`, `track`, `student_category` | 학생 기준 정보 |
| `exams` | `id`, `name`, `cohort`, `week_number`, `start_at`, `end_at`, `target_tracks`, `is_published`, `score_release_mode`, `explanation_release_mode`, 생성·수정 시간 | 회차. 현재 스키마에는 기수+주차 UNIQUE 없음 |
| `exam_sections` | `id`, `exam_id`, `track`, `subject`, `question_count`, `total_score`, `is_active`, 생성 시간 | UNIQUE(`exam_id`, `track`, `subject`) |
| `exam_subject_settings` | `id`, `track`, `subject`, `question_count`, `total_score`, `is_active`, `sort_order`, 생성·수정 시간 | UNIQUE(`track`, `subject`) |
| `exam_answers` | `id`, `exam_section_id`, `question_number`, `correct_answer`, `correct_answers`, `points`, `target_tracks` | UNIQUE(`exam_section_id`, `question_number`) |
| `exam_submissions` | `id`, `exam_section_id`, `student_id`, `student_name`, `track`, `status`, `score`, `correct_count`, `submitted_at`, `created_at` | UNIQUE(`student_id`, `exam_section_id`) |
| `submission_answers` | `id`, `submission_id`, `question_number`, `selected_answer`, `is_correct`, `points_awarded` | UNIQUE(`submission_id`, `question_number`) |
| `exam_files` | `id`, `exam_section_id`, `file_type`, `file_path`, `file_url`, `original_name`, `uploaded_at` | `file_type = answer_pdf` |

`exam_submissions.status`는 `draft`, `submitted`, `cancelled`다. 순위에는 `submitted`만 사용한다. `draft`를 지원하지만 일반 답안 입력의 서버 자동저장과 같은 의미는 아니다.

시험 → 과목 → 정답·제출·파일, 제출 → 문항별 답안은 외래 키로 연결되며 현재 스키마는 관련 삭제에 CASCADE를 사용한다. 학생 삭제도 주간평가 제출 삭제로 연결된다. 새 앱에서 보존 정책이 필요하면 삭제·보관 규칙을 따로 설계한다.

## 7. 제출 저장과 장애 복구

### 현재 구현

1. 기존 제출과 답안을 백업하고 메모리에서 채점한다.
2. 신규 제출은 `exam_submissions`에 INSERT한다. draft 완료·답안 유실 복구는 기존 ID를 UPDATE한다.
3. 서버가 돌려준 제출 ID를 상세 답안의 `submission_id`에 반영한다. 로컬에서 만든 ID와 같다고 가정하지 않는다.
4. 상세 답안을 `(submission_id, question_number)` 기준으로 UPSERT한다.
5. 서버에서 답안을 다시 읽어 모든 대상 문항에 유효한 선택 값이 있는지 확인한다.
6. 실패하면 로컬 상태를 복원한다. 신규 제출의 불완전한 서버 기록은 정리를 시도한다. 기존 제출·draft 또는 중복 충돌한 기존 기록은 삭제하지 않는다.

현재는 여러 요청으로 저장하므로 하나의 DB 트랜잭션은 아니다. 저장 확인은 대상 문항의 선택 값 존재를 확인하는 것이며 원래 입력 값과의 완전 비교는 아니다. 기존 기록을 UPDATE한 뒤 후속 요청이 실패하면 서버의 모든 변경이 자동 롤백되는 구조도 아니다.

### 새 앱 권장 설계

- 서버의 단일 트랜잭션에서 제출 중복 확인, 전체 문항 검증, 채점, 제출·상세 답안 저장을 수행한다.
- 학생 ID·기수·직렬은 로그인 세션에서 결정한다. 요청 본문의 학생 ID·점수·정오·배점을 신뢰하지 않는다.
- 선택 값은 정수 1~4만 허용하고, 대상 문항의 누락·중복·추가 문항을 검증한다.
- 응시 자격·공개·기간·기존 제출 상태를 서버에서 재검증한다.
- 동일 요청 재시도를 식별할 키를 사용한다. 이미 성공한 요청의 재전송은 기존 성공 결과를 반환하고, 제출된 답안을 다른 내용으로 덮어쓰지 않는다.
- 정답표 버전을 기록하고 응시 도중 변경 시 처리 방식을 정한다. 정답 변경 재채점과 과거 성적 재현에 사용한다.
- 답안 상세가 0건인지 판단하기 전에 서버 조회 성공을 확인한다. 조회 실패를 답안 유실로 취급하지 않는다.

## 8. 새 앱용 API 계약 예시

아래 경로는 제안이다. 현재 학생 앱은 주로 Supabase 테이블을 직접 조회·저장한다. 기존 `/api/exam-answers`는 교사 정답 삭제용이며 학생 제출 API가 아니다.

| 메서드·경로 | 목적·주요 반환 내용 |
|---|---|
| `GET /api/me/weekly-exams` | 본인 대상 공개 회차와 과목, 제출 상태, 문항 수, 공개 가능 여부 |
| `GET /api/me/weekly-sections/:id/entry` | 원본 문항 번호, 화면 번호, 저장된 본인 선택 값, 입력 가능 여부 |
| `POST /api/me/weekly-sections/:id/submission` | 최종 답안 검증·원자적 저장·채점 |
| `GET /api/me/weekly-exams/:id/grades` | 공개 정책을 적용한 요약·과목별 성적·등수 변화 |
| `GET /api/me/weekly-sections/:id/answer-sheet` | 공개 허용 후 본인 답안·정답·정오 |
| `GET /api/me/weekly-exams/:id/files` | 공개 허용 후 파일 다운로드 정보 |
| `POST /api/admin/weekly-exams` | 기수·주차 시험 생성 |
| `PATCH /api/admin/weekly-exams/:id` | 시작일·공개 설정 |
| `PUT /api/admin/weekly-sections/:id/answer-key` | 정답·문항 대상 변경, 재채점 |
| `POST /api/admin/weekly-submissions/:id/reset` | 학생·과목 확인 후 초기화 |

제출 요청 예시(2문항짜리 가상 섹션):

```json
{
  "requestId": "attempt-unique-id",
  "answerKeyVersion": 3,
  "answers": [
    { "questionNumber": 2, "selectedAnswer": 1 },
    { "questionNumber": 5, "selectedAnswer": 3 }
  ]
}
```

성공 응답 예시:

```json
{
  "submissionId": "server-generated-id",
  "status": "submitted",
  "submittedAt": "2026-09-28T01:00:00Z",
  "submittedCount": 1,
  "sectionCount": 3,
  "scoreVisible": false,
  "answerSheetVisible": false,
  "explanationVisible": false
}
```

점수 공개 전에는 응답에서 점수·정답·정오를 생략한다. 오류 코드는 `MISSING_ANSWERS`, `INVALID_ANSWER`, `ALREADY_SUBMITTED`, `NOT_ELIGIBLE`, `EXAM_NOT_OPEN`, `ANSWER_KEY_CHANGED`, `SAVE_FAILED` 등을 구분하고 미입력 화면 번호 등 필요한 정보만 반환한다.

정답표와 타인의 상세 답안은 학생에게 보내지 않고, 순위는 서버가 집계한 본인 결과·응시자 수만 반환하는 설계를 권장한다. 파일도 서버의 공개 조건 검증 후 다운로드를 허용한다.

저장소의 `schema.sql`에는 `anon`에 폭넓은 시험·정답·제출 접근을 허용하는 정책이 있으므로 새 앱의 권한 모델로 그대로 복사하지 않는다. 이는 저장소 분석이며 현재 운영 DB의 실제 권한을 확정한 결과는 아니다. Supabase 사용 시 테이블 접근 권한과 행별 RLS를 함께 구성한다. [Supabase 공식 Data API 보안 문서](https://supabase.com/docs/guides/api/securing-your-api)

## 9. 교사·관리자 운영 기능

- 기수별 주차 생성: 현재 기본 1~14주차. 이미 있는 기수·주차는 건너뛰고 새 회차는 비공개로 생성한다.
- 과목별 문항 수·직렬 설정, 정답 입력·저장, 문항 대상 일괄 설정, 다른 과목 섹션으로 정답 복사.
- 정답은 10문항 단위 표이며 1~4의 복수 인정 입력을 지원한다. Tab·Enter로 다음 입력 칸으로 이동한다.
- 시작일 선택 시 현재 브라우저 현지 시간 오전 9시를 ISO 시간으로 저장한다. 한국 시간 고정 기능과 같지 않으므로 새 앱에서는 기준 시간대를 명시한다.
- 정답 저장 후 기존 제출자의 상세 답안을 로드하여 재채점한다. 원본 문항 번호와 기존 제출 ID를 유지한다.
- 주차별 학생 성적표: 과목별 점수, 오답 수, 이번 등수, 상위 비율, 전회차 등수·등락, 관리 작업.
- 미제출·일부 제출 확인, 학생별 성적 이력, 학생·과목 지정 답안 초기화, 성적표 XLSX 다운로드.
- 학생 한 명의 과목 초기화와 회차 전체 초기화는 다른 작업이다. 대상 범위를 확인하도록 한다.
- 정답 변경·재채점·초기화의 작업자, 시간, 사유를 기록하는 감사 이력은 새 앱 권장 추가 사항이다.

## 10. 파이널 성적조회까지 이식하는 경우

주간평가 답안 입력과 별개로 교사가 등록한 성적을 조회하는 기능이다. 학생이 파이널 객관식 답안을 제출하는 기능으로 해석하지 않는다.

- 본인 성적이 있는 회차가 있을 때만 파이널 성적 탭을 표시한다. 회차는 내림차순이며 최신 회차가 기본이다.
- 0점은 유효한 성적이며 공란과 구분한다.
- `final_exam_scores`의 주요 필드: `id`(text), `round`, `student_id`(text), `student_name`, `track`, `cohort`, `is_external_final_score`, `score`, `max_score`, `wrong_count`, `subject_scores`(JSON), `status`, 생성·수정 시간.
- 과목 JSON 키: `법규`, `개론`, `형사`, `영어`, `항해`, `기관`, `형소법(공판)`. 학생 직렬에 맞는 과목만 표시한다.
- 과목 값은 점수·만점·오답 수·상태로 정규화한다. 조회 코드에는 기존 숫자/문자열 등 레거시 형식의 호환 처리도 있다.
- 같은 기수·순위 그룹으로 집계하며 외부 응시자의 점수도 조건에 맞으면 포함한다. 기수가 비어 있는 외부 성적을 허용하는 현재 분기도 이식 시 확인한다.
- 통합 그룹에 서로 다른 직렬이 있으면 득점률 우선, 이후 총점·오답 수·학생 ID로 정렬한다. 단일 직렬은 총점 우선이다. 동률은 공동 등수다.
- 과목별 파이널 순위는 점수·오답 수 기준이며 공동 등수를 적용한다.
- 성적 레코드에 명시적 순위 값이 전달되면 자체 계산보다 우선하는 호환 분기가 있다. 기본 DB 테이블의 필수 필드는 아니다.
- 전회차 비교는 바로 앞 회차만 사용한다.
- 총점/만점은 대상 과목의 성적 합계를 우선하고, 과목 성적이 없으면 레코드 총점을 사용한다. 오답 정보가 없으면 일부 경로에서 5점 배점 기준으로 추정하므로 다른 배점 체계의 앱에서는 명시적 오답 수를 저장한다.
- 관리자의 엑셀 붙여넣기·동명이인·인강 ID 식별까지 이식할 경우 `final_score_identities` 설계도 필요하다. 원문 인강 ID는 학생 화면이나 공통 성적 데이터에 포함하지 않는다. 상세 내용: [기존 파이널 식별자 문서](final-score-lecture-identities.md).

## 11. 성능·동기화 요구사항

- 회차/과목/문항 정보와 학생 성적을 구분해서 조회한다. 현재 학생 시험 기본정보 재조회 판단 간격은 30초이며 고정 30초 폴링을 뜻하지 않는다.
- 학생 상세 답안은 본인 제출 ID에 한정해서 읽는다. 현재 순위용 제출 요약은 같은 기수·순위 그룹 범위로 읽는다.
- 교사 상세 성적은 필요한 시험을 선택했을 때 로드하는 흐름을 유지한다.
- 현재 정답표 로더는 1,000행씩 끝까지 읽는다. 새 앱에서는 시험 범위로 좁혀도 데이터가 잘리지 않도록 페이지네이션한다.
- 화면 렌더 한 번 안에서는 시험별 과목, 과목별 문항, 학생별 제출을 Map으로 묶어 반복 전체 검색을 줄인다.
- 입력·저장 중 자동 새로고침이 draft를 덮어쓰지 않게 한다. 재채점·초기화 후 관련 캐시를 무효화한다.
- 새 앱 권장: 순위 계산·권한 검사를 서버에 모으고 결과 DTO를 캐시한다. 학생 브라우저에 전체 학생 점수·정답표를 전달할 필요가 없도록 한다.

## 12. 검수 시나리오

| 일부 과목 제출 | 미제출 과목 표기, 전체 만점 유지, 공개 정책 적용 |
| 전 문항 오답 | 0점을 유효한 제출로 저장·순위 포함 |
| 저장 버튼 연타·응답 유실 후 재시도 | 제출·문항별 답안 중복 없음 |
| 제출 저장 후 답안 저장 실패 | 성공으로 표시하지 않음. 새 앱은 트랜잭션 롤백 |
| 기존 제출과 충돌 | 기존 답안 삭제·덮어쓰기 금지 |
| 답안 상세 조회 실패 | 답안 유실로 오판하여 재제출하지 않음 |
| draft·답안 유실 복구 | 기존 ID 유지, 저장된 선택 복원, 첫 빈 문항부터 입력 |
| 교사 과목 초기화 | 지정 학생·과목만 다시 입력 가능 |
| 정답 변경 | 관련 제출 재채점, 점수·정오·순위 일치 |
| 직렬 통합 순위·만점 차이 | 지정된 두 직렬만 통합, 득점률 우선 비교 |
| 동점자·응시자 1명 | 선택한 순위 정책 및 상위 비율 적용 |
| 직전 주차 없음 | 더 과거 기록을 전회차로 표시하지 않음 |
| PDF 공개·중복 | 공개 조건 전 접근 제한, 같은 파일은 한 번 표시 |

| 다량 문항·제출 | 조회 누락 없음, 필요 범위만 조회 |

개발 순서는 데이터·인증 및 정책 확정 → 교사 시험·정답 등록 → 학생 입력·제출 → 서버 채점 → 성적조회·순위 → 해설·초기화·재채점 → 장애·권한·모바일 검수 순으로 진행한다.

본 문서는 로컬 소스와 관련 테스트를 근거로 작성했다. 실제 모바일 화면 육안 검수, 운영 DB 권한 점검, 실제 네트워크 장애 재현을 수행한 결과는 아니다. 문서 작성 작업에서 앱 코드·운영 DB·배포 설정은 변경하지 않는다.

검증 기록: `answer-ui`, `weekly-answer-reentry`, `weekly-answer-reset`, `weekly-investigation-subjects`, `student-grade-performance` 테스트는 원본 실행에서 통과했다. `weekly-answer-loading`, `weekly-submission-id`, `grade-ranking-groups`는 CRLF 소스에서 LF 전용 정규식으로 함수를 추출하지 못해 원본 실행에 실패했다. 디스크 파일을 수정하지 않고 테스트가 읽는 문자열의 CRLF만 LF로 정규화한 재실행에서는 세 테스트 모두 통과했다. 전체 테스트·빌드 통과를 의미하지 않는다.

## 14. 다른 앱 개발 AI에게 전달할 요청문

> 첨부한 주간평가 답안 입력·성적조회 명세를 기준으로 현재 프로젝트의 기술 스택과 인증 구조에 맞춰 구현해 주세요. 학생은 주차·과목을 선택하고 4지선다 답안을 10문항씩 입력하며, 전체 검토와 확인 후 모든 문항을 최종 제출합니다. 학생별 과목 중복 제출을 막고, 서버에서 응시 자격·문항 완전성을 검증한 뒤 단일 트랜잭션으로 저장·채점해 주세요. 직렬별 과목, 해사법규 문항 대상·만점 보정, 복수 인정 정답, 주차별 요약·과목별 점수·상위 비율·전회차 비교, 내 답안지·해설 공개, 교사 정답 등록·재채점·초기화를 포함해 주세요. 정답과 타인의 상세 답안은 학생에게 사전 제공하지 마세요. 명세에 적힌 기존 화면별 공개·동점 처리 차이, 마감 미적용, 자동저장 부재는 명시적인 정책 선택 항목으로 다뤄 주세요. 변경된 정책을 기존 동작과 동일하다고 설명하지 마세요. 파이널 성적은 별도 모듈로 구현하고, 검수 시나리오에 따라 확인해 주세요. 운영 적용·푸시·배포는 최종 검토 후 진행해 주세요.
