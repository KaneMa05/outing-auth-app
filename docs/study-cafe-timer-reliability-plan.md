# 스터디카페 타이머 저장 안정화 계획

## 목표

- 서버 기록을 타이머의 최종 기준으로 사용한다.
- 네트워크 장애나 앱 강제 종료가 발생해도 공부 시간이 과다·과소 집계되지 않게 한다.
- 시작, 일시정지, 재개, 과목 변경, 종료가 중복 요청되어도 한 번만 반영되게 한다.
- 자정을 넘긴 공부 기록을 날짜별로 정확히 집계한다.

## 1단계: 비정상 종료 시간 보정 (P0)

현재는 하트비트가 끊긴 학생을 다음 정리 시점의 서버 시간으로 종료해 장시간 과다 집계될 수 있다.

- 오래된 좌석을 정리할 때 `현재 시각`이 아니라 마지막 하트비트 시각을 세션 종료 기준으로 사용한다.
- 마지막 하트비트 이후 허용할 유예 시간은 최대 30초로 제한한다.
- 앱의 `visibilitychange`와 `pagehide`에서 마지막 하트비트를 가능한 범위에서 전송한다.
- 비정상 종료된 세션에는 종료 사유를 기록해 관리자 확인이 가능하게 한다.

완료 기준:

- 앱을 강제 종료한 뒤 다음 날 접속해도 종료 이후 시간이 누적되지 않는다.
- 최대 오차가 하트비트 주기 이내로 제한된다.

## 2단계: 저장 상태와 네트워크 실패 처리 (P0)

현재는 최초 연결 실패 시 로컬 타이머가 저장된 것처럼 보일 수 있고, 일시정지 요청 실패 시 화면과 서버 상태가 달라질 수 있다.

- 서버 연결 상태를 `확인 중`, `연결됨`, `일시 장애`, `지원하지 않음`으로 구분한다.
- 운영 환경에서는 서버 저장이 확인되지 않은 타이머를 성공으로 처리하지 않는다.
- 시작은 서버가 세션 생성을 확인한 뒤 화면 타이머를 시작한다.
- 일시정지, 재개, 종료 버튼은 요청 중 중복 입력을 막고 서버 응답 후 상태를 변경한다.
- 실패 시 이전 상태로 복구하고 화면에 `저장되지 않음` 안내와 재시도 버튼을 표시한다.
- 네트워크 재연결 시 서버 상태를 다시 불러와 화면 상태를 일치시킨다.

완료 기준:

- 각 동작 중 네트워크를 차단해도 화면과 서버의 상태가 다르게 남지 않는다.
- 저장되지 않은 기록을 사용자에게 성공으로 안내하지 않는다.

## 3단계: 타이머 전환 API 원자성·중복 방지 (P0)

현재 세션과 좌석 상태가 여러 API 요청으로 갱신되어 중간 요청 실패 시 일부만 저장될 수 있다.

- 시작, 일시정지, 재개, 종료, 과목 변경을 각각 Supabase RPC 트랜잭션으로 처리한다.
- 세션과 좌석 상태를 하나의 트랜잭션 안에서 함께 갱신한다.
- 모든 타이머 요청에 요청 ID를 포함해 재시도나 빠른 연속 클릭이 중복 기록을 만들지 않게 한다.
- 과목 변경은 기존 세션 종료와 새 세션 시작을 하나의 트랜잭션으로 처리한다.

완료 기준:

- API 중간 단계에 오류를 발생시켜도 세션과 좌석 상태가 부분 저장되지 않는다.
- 동일 요청을 두 번 전송해도 세션이 한 번만 생성·변경된다.

## 4단계: 자정 및 기간 집계 보정 (P1)

- 세션 시작일만으로 날짜를 정하지 않고, 각 날짜와 실제로 겹치는 시간을 계산한다.
- 한국 시간 자정을 기준으로 일간 시간을 분리한다.
- 자정을 넘긴 실행 중 세션도 오늘 타이머와 오늘 랭킹에 즉시 반영한다.
- 통계와 랭킹이 동일한 시간 계산 함수를 사용하도록 통합한다.

완료 기준:

- 23:50부터 00:10까지 공부하면 전날 10분, 오늘 10분으로 집계된다.
- 일간 통계, 과목별 합계, 랭킹의 총시간이 일치한다.

## 5단계: 자동 테스트와 운영 관찰 (P1)

필수 자동 테스트:

1. 시작 → 일시정지 → 재개 → 종료
2. 실행 중 과목 변경
3. 각 단계의 네트워크 실패와 재시도
4. 중복 클릭과 동일 요청 재전송
5. 새로고침과 앱 강제 종료
6. 하트비트 만료
7. 자정 통과
8. 두 기기에서 동시에 조작

운영 확인 항목:

- 비정상 종료 세션 수
- 저장 실패율과 재시도 성공률
- 한 학생의 동시 활성 세션 발생 여부
- 타이머 합계와 랭킹 합계 불일치 여부

## 권장 적용 순서

1. 1~3단계를 함께 구현하고 로컬·테스트 환경에서 검증한다.
2. 관리자 계정과 테스트 학생만 대상으로 사전 점검한다.
3. 기존 사용자 기록을 보존한 채 DB 변경을 적용한다.
4. 전체 자동 테스트와 실제 기기 테스트를 통과한 후 배포 여부를 최종 확인한다.
5. 배포 후 저장 실패율과 비정상 종료 기록을 관찰한다.
