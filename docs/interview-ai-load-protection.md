# 면접 AI 요청 집중 시 기존 앱 보호

2026-10-20 로컬 구현·검증. 운영 DB 적용, 푸시, 배포는 수행하지 않았다.

## 반영한 동작

| 항목 | 적용 내용 |
|---|---|
| 학생 상태 조회 | 학생 등록 행의 `FOR UPDATE`와 전체 면접 카탈로그 조회 제거. 원문 근거를 매번 다시 추출하지 않음 |
| 자료 변경 확인 | 학생 자료 저장 시 작은 버전 행만 갱신. 상태 조회는 버전 비교로 변경 여부 확인 |
| 변경 없는 상태 | `version`이 같으면 `unchanged:true`만 반환하고 답변 본문 전송·화면 재렌더링 생략 |
| 생성 대기 | 변화가 없으면 5 → 10 → 20 → 최대 약 30초 간격 |
| 실제 생성 중 | 약 5초 간격으로 결과 확인 |
| 확인 필요(BLOCKED) | 약 60초 간격 |
| 숨겨진 화면 | 새 반복 조회 중단, 복귀 시 즉시 조회. 이미 전송된 응답은 폐기 |
| 조회 분산 | 간격에 ±10% 분산을 주어 여러 학생의 조회 시점을 분산 |
| 접수 상한 | 전체 QUEUED/PROCESSING/BLOCKED 합계 기본 300문항 |
| 학생 요청 제한 | 새 생성·선택 재요청 합계 기본 분당 4회. 같은 요청 재전송은 중복 생성하지 않음 |
| PC 처리기 | 일일 한도·기능 꺼짐·실행 확인 필요 상태에서는 60초 대기. 일반 새 작업 감지는 기본 2초 유지 |
| 기기 접속 기록 | `last_seen_at`을 요청마다 쓰지 않고 최대 분당 한 번 갱신 |
| 배포 캐시 | 서비스 워커 캐시 식별자와 AI 연결 모듈 URL을 변경하여 배포 후 이전 조회 코드를 계속 사용하지 않도록 준비 |

화면이 보이지 않거나 백그라운드인 경우 새 요청 접수 및 서버의 이미 진행 중인 생성은 취소되지 않는다. 숨겨진 화면의 결과 확인만 멈춘다. 오류 발생 시 재시도 간격은 늘어나고, 연결 복구 후 같은 상태를 받더라도 오류 안내를 해제한다.

`stale`는 자료 버전 변경을 보수적으로 알린다. 다른 작성 항목의 내용 변경이나 주제 활성 상태 변경도 표시를 갱신할 수 있다. 교사 피드백만 수정하거나 동일한 자료를 다시 저장한 경우에는 학생 자료 버전을 올리지 않는다. 생성 요청 시에는 기존과 동일하게 실제 근거를 추출하고 정확한 원문 해시를 검증한다.

## 서버 보호

`20261020074446_interview_ai_load_protection.sql`을 기존 AI 마이그레이션 다음에 적용한다. 기존 작성·인증 API는 교체하지 않는다. 기존 완료 답변과 학생 작성 내용을 보존한다.

전체 대기열 상한과 학생별 분당 한도는 `admin_configure`의 `maxPendingTotal`(30~5000), `requestsPerMinute`(1~60)로 설정한다. 관리자 권한 검사와 기존 일일 한도·학생별 미처리 한도도 유지한다.

AI 요청 접수끼리만 비대기 advisory lock을 공유하여 동시에 상한을 넘겨 등록하지 못하게 한다. 다른 접수가 진행 중이면 `admission_busy`, 공간이 부족하면 `queue_full`, 분당 한도에 도달하면 `request_rate_limited`를 HTTP 429와 `Retry-After`로 반환한다. 대기열에 일부 문항만 등록하지 않고 요청 전체를 거부한다. 관리자 실패 작업 재등록도 상한을 우회하지 못한다. 작성 내용은 기존 저장 경로에 남는다.

조회는 쓰기 잠금을 잡지 않는 경로이며 읽기 전용 트랜잭션 시험을 통과했다. AI 새 요청 등록의 중복·소유권 검증에 필요한 잠금은 유지한다. 새 버전 표는 RLS를 켜고 service_role에만 권한을 부여했다. 새 자료 추적 트리거는 `SECURITY INVOKER`다.

이 제한은 AI 생성 접수와 정상 화면의 반복 조회를 보호한다. 인터넷 전체의 악성 요청이나 기존 앱 전체 트래픽을 차단하는 방화벽을 구현한 것은 아니다. 인증 확인과 상태 조회는 계속 공유 DB를 사용하므로 운영 부하가 완전히 분리된 구조도 아니다.

## 검증 결과

- 50개 화면, 10분 대기, 응답 지연 없는 가상 시계: 기존 고정 5초 방식 6,050회 → 개선 후 1,100회. 약 **82% 감소**.
- 숨겨진 상태 10분: 추가 조회 **0회**.
- 상태 변화·완료·네트워크 복구·늦은 응답·로그아웃 분리 검사 통과.
- 읽기 전용 상태/요청 내역/사전 확인 검사 통과. 상태 조회 중 원문 추출 함수를 호출하면 실패하도록 만든 검사도 통과.
- 원문 변경 감지, 교사 피드백 제외, 이전 결과의 버전 이관, 학생 소유권 검사 통과.
- 전체 상한, 30문항 묶음의 전부 등록/전부 거부, 분당 한도, 상한 도달 후 동일 요청 재전송, 관리자 재등록 상한 검사 통과.
- 50명 상태 조회 300회와 기존 `life_save` 6회를 섞어 실행한 로컬 DB 검사 통과. 295회는 본문 없는 변경 없음 응답.
- 기존 AI DB 회귀 검사는 테스트에서만 상한 5,000·분당 60으로 올려 1,650문항 등록을 재검증했다. 운영 기본 상한은 300이다.

수치 원본은 `tests/fixtures/ai-load-report.json`에 있다. 이 파일의 지연 시간은 로컬 테스트 환경에서 관측한 값으로 운영 성능 목표가 아니다.

**검증 한계:** PGlite는 단일 DB 연결로 처리한다. 50개 클라이언트의 호출을 함께 제출했지만 실제 PostgreSQL 다중 연결의 잠금 경쟁·운영 서버 지연을 입증하지는 않는다. 현재 PC의 Docker 서버가 실행되지 않아 별도 실제 PostgreSQL 부하 시험은 하지 않았다. 운영 반영 전 별도 시험 DB에서 50명 동시 요청·기존 앱 저장을 함께 시험하고 기존 앱의 지연과 오류율을 확인해야 한다. 운영 DB에 부하를 발생시키는 시험은 수행하지 않았다.

## 실행

```powershell
node tests/interview-ai-polling.test.cjs
node tests/interview-ai-load-api.test.cjs
node tests/interview-ai-load.test.cjs
node tests/interview-ai-db.test.cjs
```

위 시험은 모델을 호출하지 않는다. 운영 설정의 하루 생성 예약 기본값 20회는 변경하지 않았다. 핵심 30제의 일일 처리 한도는 별도로 승인·설정해야 한다.

배포 시 DB 마이그레이션 → API/화면 배포 → 낮은 범위의 시험 운영 순서로 확인한다. 새 API의 버전 인자와 새 조회 화면을 쓰기 전에 마이그레이션을 적용한다. 마이그레이션에는 2초 DDL 잠금 제한을 두었으므로 기존 사용과 충돌하면 기다리며 서비스에 영향을 주는 대신 실패·롤백한다. 다시 적용할 시점을 정하고, 무조건 재시도하지 않는다.

참고: [PostgreSQL 잠금과 advisory lock](https://www.postgresql.org/docs/current/explicit-locking.html), [Supabase 인덱스 안내](https://supabase.com/docs/guides/database/postgres/indexes).
