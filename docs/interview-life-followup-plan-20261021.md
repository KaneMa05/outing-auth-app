# 면접반 인생그래프 추가 질문 기능 기획안

작성일: 2026-10-21 · 상태: 검토용 기획 · 적용 대상: 면접반 앱의 DB 정리 → 인생그래프

## 1. 제안 요약

기존 인생그래프의 경험마다 **‘추가 질문으로 자세히 쓰기’** 버튼을 둔다. 수강생이 적은 내용을 읽고 부족한 정보에 맞춰 한 번에 2~3개 질문을 제시한다. 답변을 받으면 다음 질문을 바꾸고, 마지막에 수강생이 확인한 정리 내용을 해당 경험에 반영한다.

목표는 글자 수를 늘리는 것이 아니라 **면접에서 설명할 수 있는 실제 상황·선택 이유·본인의 행동·결과를 확보하는 것**이다. 사건을 충분히 알아보기 전에 성격이나 장점을 단정하지 않는다.

권장 흐름:

> 경험 작성 → 경험 저장 → 추가 질문 → 답변 저장 → 답변에 맞는 다음 질문 → 내용 정리·검토 → 인생그래프에 반영

질문과 답변은 원래 경험과 별도로 보관한다. AI 정리 결과가 원문을 자동으로 바꾸지 않도록 하며, 기존 경험 작성과 저장은 추가 질문 이용 여부와 관계없이 가능하게 한다.

## 2. 현행 앱과 적용 위치

아래 내용은 로컬 소스와 마이그레이션 기준이다. 운영 배포본과의 일치 여부는 개발 착수 시 확인한다.

| 항목 | 현행 | 제안 |
|---|---|---|
| 진입 | 면접반 앱 → DB 정리 → 인생그래프 | 같은 위치 유지 |
| 경험 입력 | 당시 나이·만족도·키워드·내용·면접관에게 어필할 점 | 기존 항목 유지, 경험별 추가 질문 버튼 제공 |
| 그래프 | 나이와 만족도로 경험 표시 | 표시 방식 유지, 상세보기에도 추가 질문 진입 제공 |
| 저장 | 경험별 저장·수정, 프로필 revision으로 충돌 검사 | 질문 답변은 별도 저장, 최종 반영은 기존 충돌 검사 적용 |
| 기존 AI | 작성하기 등에서 답변 초안 생성 | 경험을 탐색하는 별도 질문 기능 추가 |
| 강사 확인 | 기존 인생그래프 내용 조회 및 피드백 | 1차에서는 반영된 내용을 기존 화면에서 확인 |

확인한 제약은 경험 최대 40개, 경험의 ‘내용’ 최대 12,000자, ‘어필할 점’ 최대 2,000자다. 전체 프로필에도 JSON 크기 제한이 있어 문답 전체를 기존 내용 필드에 계속 붙이는 구조는 적합하지 않다.

만족도 -25~+25는 수강생이 느낀 경험의 만족도이며, 면접 역량 점수로 해석하거나 AI가 자동 수정하지 않는다.

## 3. 강의 분석을 제품에 적용하는 방법

앞서 분석한 두 강의의 중심 흐름을 다음과 같이 적용한다. 아래는 의미를 재구성한 기획이며 강사의 발언을 그대로 옮긴 문장이 아니다.

| 강의에서 확인한 접근 | 앱 적용 |
|---|---|
| 사건을 설명한 뒤 여러 질문으로 정보를 펼침 | 처음부터 완성된 자기소개를 요구하지 않고 경험별 문답 제공 |
| 왜 했는지와 어떻게 했는지를 함께 확인 | 동기 질문과 행동 과정 질문을 구분 |
| 같은 선택이라도 만족도가 다른 이유 탐색 | 다른 경험을 수강생이 선택하면 차이를 묻는 비교 질문 제공 |
| 조건을 바꾸어 중요하게 여긴 요소 탐색 | 실제 사실을 확보한 뒤 선택적으로 가정 질문 제공 |
| 유년기 경험을 이후 경험과 연결 | 현재 행동을 보여주는 다른 경험을 찾도록 제안 |
| 경험을 충분히 들은 후 의미 해석 | 사실 정리 후 근거가 있는 의미 후보만 제시 |

‘누군가 도와줬다’는 사실만으로 협업 능력이 입증되지는 않는다. ‘힘든 일을 했다’는 사실만으로 어떤 어려움이든 견딜 수 있다고 결론 내리지 않는다. 앱은 이런 해석을 먼저 제시하기보다 본인의 행동과 이후 사례를 확인한다.

## 4. 수강생 이용 흐름

### 4.1 경험을 처음 작성할 때

기존 입력 화면에서 나이·키워드·내용을 우선 작성한다. 만족도와 어필할 점도 기존 방식으로 입력할 수 있다. ‘어필할 점’을 아직 모르더라도 초안 저장 후 추가 질문을 시작할 수 있게 한다.

추가 질문의 시작 조건은 **선택한 경험에 나이·키워드·간단한 내용이 저장되어 있는 것**으로 제안한다. 내용의 최소 글자 수로 품질을 판정하지 않는다. 내용이 너무 추상적이면 첫 질문이 구체적인 사건을 요청한다.

전체 기본 이력이나 다른 경험의 작성 완료는 시작 조건으로 삼지 않는다. 기존 전체 제출의 필수 항목 검사는 유지하며, 추가 질문을 시작하기 위한 조건과 구분한다.

저장하지 않은 수정이 있으면 해당 경험 저장이 성공한 뒤 시작한다. 저장 충돌이나 검증 실패가 있으면 먼저 해결하도록 안내한다.

### 4.2 경험 카드에 표시할 요소

```text
22세 · 어학연수 · 만족도 +18
혼자 준비해서 어학연수를 다녀왔고 자신감을 얻었다.

[내용 수정]  [추가 질문으로 자세히 쓰기]
```

진행 이력이 있으면 버튼명을 ‘추가 질문 이어쓰기’로 바꾸고 ‘답변 5개 저장됨’처럼 실제 저장 상태를 표시한다. 완료 횟수로 경험의 우열을 나타내지 않는다.

### 4.3 추가 질문 화면

모바일에서는 길게 작성할 수 있는 별도 패널 또는 화면으로 연다. 그래프의 상세 팝업 안에 긴 대화를 중첩하지 않는다. 상단에 선택한 경험과 돌아가기 버튼을 고정한다.

```text
어학연수 경험 자세히 쓰기
기억나는 만큼 적어주세요. 모르는 내용은 건너뛸 수 있습니다.

질문 1. 어학연수를 가기로 결정한 계기는 무엇이었나요?
[답변 입력]
[기억나지 않아요] [건너뛰기]

질문 2. ‘혼자 준비했다’고 했는데, 직접 처리한 일 하나는 무엇인가요?
[답변 입력]
[기억나지 않아요] [건너뛰기]

[답변 저장] [저장하고 다음 질문] [지금까지 내용 정리]
```

1차에서는 명시적인 답변 저장을 기본으로 한다. ‘다음 질문’과 ‘지금까지 내용 정리’도 답변 저장 성공 후 실행한다. 미저장 상태로 나가면 기존 앱 방식과 일관되게 알리고, 저장한 답변은 재접속 후 복원한다.

다음 질문을 준비하는 동안 저장된 답변을 읽고 다른 화면으로 이동할 수 있다. 화면 이동으로 같은 생성 요청을 다시 만들지 않는다.

### 4.4 질문 수와 종료

- 한 묶음에 2~3개 질문을 제시한다. 필요한 질문이 하나라면 하나만 제시한다.
- 기본 안내는 2~3묶음, 총 4~9개 정도로 한다. 모든 경험에 같은 질문 수를 강제하지 않는다.
- 충분한 사실이 있으면 일찍 정리할 수 있다. 깊이 탐색은 선택적으로 최대 5묶음·15개 질문을 초기 운영 상한으로 제안한다.
- ‘기억나지 않아요’와 ‘건너뛰기’는 응답 상태로 보관하고 같은 내용을 반복해서 요구하지 않는다.
- 질문 상한이나 이용 한도에 도달해도 답변 저장·수정·기존 경험 작성은 가능하다. AI 정리 없이 직접 반영하는 경로도 제공한다.
- 입력량에 따른 점수, 필수 답변률 100%, 답변 시간 제한은 두지 않는다.

질문 수 상한은 비용과 사용성을 확인하기 위한 제안값이며 실제 운영 결과에 따라 조정한다.

## 5. 어떤 추가 정보를 확보할 것인가

아래 항목은 내부 질문 선택 기준이다. 수강생에게 모든 칸을 채우는 의무 설문으로 보여주지 않는다.

| 탐색 항목 | 확보할 정보 | 질문 예시 |
|---|---|---|
| 구체적 장면 | 언제·어디서·누구와 있었던 어떤 일인지 | 가장 선명하게 기억나는 장면 하나를 설명해 주세요. |
| 계기 | 기회를 알게 된 경로와 시작 상황 | 그 활동을 처음 어떻게 알게 되었나요? |
| 선택 기준 | 선택지와 본인이 중요하게 본 조건 | 다른 선택도 가능했다면, 이것을 고른 이유는 무엇인가요? |
| 기대와 목표 | 당시 바랐던 변화 | 시작할 때 얻고 싶었던 것은 무엇이었나요? |
| 본인의 행동 | 실제 수행한 일과 순서 | 그 상황에서 가장 먼저 한 일은 무엇이었나요? |
| 장애물과 대응 | 막힌 지점, 해결 시도와 수정 | 계획대로 되지 않았을 때 어떻게 대응했나요? |
| 타인과 역할 | 받은 도움, 본인 기여, 상호작용 | 함께한 사람들과 본인의 역할은 어떻게 달랐나요? |
| 감정과 만족도 | 사건에서 중요했던 요소 | 이 경험에 그 만족도를 준 가장 큰 이유는 무엇인가요? |
| 결과 | 실제 변화, 본인 기여와 외부 요인 | 본인이 한 일 이후 어떤 변화가 있었나요? |
| 이후 변화 | 배움이 드러나는 후속 행동 | 이후 비슷한 상황에서 행동이 달라진 사례가 있나요? |
| 다른 경험과 비교 | 반복되는 선택 기준과 차이 | 두 경험 모두 직접 선택했는데 만족도가 달랐던 이유는 무엇인가요? |
| 조건 변경 | 결과와 과정 중 중요한 요소 | 결과가 달랐어도 이 경험을 비슷하게 평가했을까요? |

횟수·기간·인원·성과 수치는 실제로 기억하는 범위에서만 묻는다. 정확한 수치가 없으면 대략적인 표현이나 수치 없는 설명을 허용한다. 실패나 평범한 경험에도 질문을 제공한다.

## 6. 답변에 따라 질문이 달라지는 규칙

### 6.1 다음 질문 선택 과정

1. 원래 경험과 지금까지의 답변에서 사실·본인의 해석·가정 응답을 구분한다.
2. 탐색 항목별로 ‘확인됨 / 일부 확인 / 미확인 / 해당 없음 / 건너뜀’을 내부 기록한다.
3. 부족한 사실 중 현재 사건을 이해하는 데 중요한 것부터 고른다. 보통 구체적 장면과 본인의 행동을 우선한다.
4. 이미 답변한 질문과 의미가 같은 질문을 제외한다. 질문 문장이 달라도 같은 정보를 요구하면 중복으로 본다.
5. 학생의 실제 표현을 짧게 인용해 2~3개 질문을 만든다. 한 질문에는 하나의 중심 주제만 담는다.
6. 사실이 충분할 때만 비교·가정·의미 탐색으로 넘어간다. 가정 질문은 묶음당 최대 하나로 제한한다.
7. 더 물을 핵심 정보가 없으면 새 질문을 억지로 만들지 않고 정리를 제안한다.

질문 후보는 검토된 질문 틀과 생성형 AI를 함께 사용한다. 질문 틀이 탐색 범위를 정하고, AI는 실제 답변을 반영해 표현과 순서를 조정한다. AI가 실패하면 해당 항목의 기본 질문을 제시할 수 있지만, 이것을 개인 답변을 깊게 분석한 결과처럼 표시하지 않는다.

### 6.2 표현별 분기 예시

| 수강생 표현 | 다음 질문의 방향 | 피할 질문·해석 |
|---|---|---|
| 열심히 했다 | 실제 행동과 빈도 | 그러면 성실한 사람이군요? |
| 힘들었다 | 어려웠던 장면과 대응 | 끝까지 잘 극복했죠? |
| 친구 덕분이다 | 받은 도움과 자신의 행동 | 협동심이 뛰어나다는 뜻이네요. |
| 내가 선택했다 | 다른 선택지와 결정 기준 | 원래 독립적인 성격인가요? |
| 성장했다 | 이전과 이후의 행동 차이 | 얼마나 훌륭한 사람이 되었나요? |
| 성과를 냈다 | 실제 결과와 자신의 기여 | 팀 성과를 혼자 달성한 것처럼 정리 |
| 기억나지 않는다 | 다른 확인 가능한 부분 탐색 | 같은 내용을 표현만 바꿔 반복 |

### 6.3 금지하거나 구분할 처리

- 답변하지 않은 역할·수치·감정·성과를 대신 만들어 넣지 않는다.
- ‘책임감·희생·리더십’처럼 원하는 결론으로 유도하지 않는다.
- 가정 질문에 대한 응답을 실제 행동 이력으로 사용하지 않는다.
- 유년기 경험 하나만으로 현재 직무 역량을 확정하지 않는다.
- 가족 사정 등 민감한 배경의 공개를 계속 요구하지 않는다. 경험 이해에 필요한 범위만 묻고 건너뛰기를 존중한다.
- 서로 다른 사건의 행동이나 성과를 하나의 사건으로 합치지 않는다.
- 학생의 정정이 있으면 이전 답변에서 나온 분석과 정리 결과를 재검토 대상으로 표시한다.

아래는 기능 설명을 위해 새로 만든 예시이며 강의 수강생의 실제 발언이 아니다.

**최초 입력**

> 22세, 어학연수, 만족도 +18. 혼자 준비해서 중국 어학연수를 다녀왔고 자신감을 얻었다.

**첫 질문 묶음**

1. 중국 어학연수를 가기로 결정한 계기는 무엇이었나요?
2. ‘혼자 준비했다’고 했는데, 직접 처리한 일 하나를 설명해 주세요.
3. 자신감이 생겼다고 느낀 현지의 장면 하나는 무엇인가요?

**수강생 답변 예시**

> 중국어로 대화해 보고 싶어서 지원했다. 학교 홈페이지에서 프로그램을 비교했고 신청서를 직접 냈다. 현지에서 기숙사 방에 문제가 생겨 처음에는 친구에게 부탁하려다가 직접 사무실에 가서 설명했다.

**답변에 맞춰 바뀐 다음 질문**

1. 프로그램을 비교할 때 최종 선택에 가장 영향을 준 조건은 무엇이었나요?
2. 친구에게 부탁하려다가 직접 설명하기로 바꾼 이유는 무엇이었나요?
3. 사무실에 설명한 뒤 방 문제는 어떻게 처리되었나요?

여기서는 이미 답한 ‘어떻게 알아봤나요?’를 반복하지 않는다. 문제 해결 여부도 아직 확인되지 않았으므로 성공한 경험이라고 먼저 정리하지 않는다.

이후 ‘직접 설명했지만 해결되지 않았다’고 답해도 탐색을 계속한다. 그 뒤의 대응을 묻거나, 결과와 별개로 직접 설명해 본 행동이 어떤 의미였는지 확인한다.

**다른 경험으로 확장**

> 그 이후에도 도움을 요청하거나 직접 설명해 본 비슷한 일이 있었나요?

새로운 사건이 나오면 ‘다른 경험으로 추가하기’를 제안한다. 수강생이 확인하고 나이·만족도 등을 입력한 경우에만 새 경험으로 저장한다. 경험 40개 제한에 도달하면 새 저장을 안내하고 기존 경험을 자동 삭제하지 않는다.

1차에서는 새 경험 입력 화면으로 연결하고, 두 경험을 함께 분석하는 기능은 2차로 둔다.

## 8. 정리 결과와 인생그래프 반영

### 8.1 정리 화면 구성

| 구역 | 표시할 내용 | 취급 |
|---|---|---|
| 확인한 사실 | 배경·선택·행동·결과·후속 변화 | 학생이 실제 작성한 근거만 사용 |
| 더 확인할 내용 | 아직 답하지 않은 중요한 부분 | 비워둘 수 있으며 자동으로 채우지 않음 |
| 경험 내용 초안 | 확인한 사실을 읽기 쉽게 연결한 글 | 수강생 검토·수정 필요 |
| 어필할 점 후보 | 근거가 있는 의미와 연결되는 행동 | 확정 성격 진단이 아닌 검토 후보 |

사실 문장과 어필 후보마다 원래 입력 또는 답변 ID를 연결한다. 사용자에게는 필요할 때 ‘이 내용의 근거 보기’로 보여준다. 근거 없는 후보는 출력하지 않는다.

경험 탐색 단계에서는 자기소개나 지원 동기 답변까지 한꺼번에 만들지 않는다. 먼저 인생그래프에 사용할 사실을 정리하고 기존 ‘작성하기’ 기능이 이를 활용하도록 한다.

### 8.2 반영 방식

‘기존 내용’과 ‘반영할 내용’을 비교해 보여주고 수강생이 편집하게 한다. ‘내용에 반영’과 ‘어필할 점에 반영’을 각각 선택한 뒤 명시적으로 저장한다. 기존 문장에 무조건 덧붙이지 않고, 확인한 원문 사실을 보존한 통합 초안을 검토하게 한다.

반영 직전 원본이 바뀌었으면 자동 덮어쓰기를 중단한다. 최신 원본을 보여주고 다시 비교하도록 한다. 반영 직전 값과 결과 버전을 보관해 복구할 수 있게 하되, 복구도 최신 수정 사항과 충돌을 검사한다.

12,000자·2,000자 제한을 넘으면 글자 수를 표시하고 수정을 요청한다. 서버에서 조용히 잘라 저장하지 않는다. 전체 프로필 용량 제한도 기존 저장 검증을 통과해야 한다.

프로필의 제출·검토 상태는 기존 수정 정책을 따른다. 승인된 내용의 변경이 재검토를 요구하는지 현행 정책을 확인하고 동일하게 적용한다. 추가 질문 반영만으로 승인 상태를 새로 부여하지 않는다.

## 9. 저장 구조와 API 설계안

### 9.1 별도 저장이 필요한 이유

현재 경험은 `ip_life_profiles.content.experiences` 안의 JSON이며 경험별 UUID가 있다. 질문과 답변 전체를 이 JSON에 추가하면 필드 허용 목록·용량 제한·기존 AI 입력이 함께 영향을 받는다. **원래 경험 구조는 유지하고 별도 테이블에 문답을 저장하는 방식**을 권장한다.

다음 이름과 필드는 신규 설계안이며 현재 존재하는 기능이 아니다.

| 저장 단위 | 주요 내용 |
|---|---|
| `ip_life_followup_sessions` | 학생 ID, 경험 UUID, 원본 해시, 시작 revision, 진행 상태, 질문 정책 버전 |
| `ip_life_followup_questions` | 세션 ID, 질문 ID, 묶음 번호, 탐색 항목, 질문 문장, 근거 참조, 실제/가정 구분 |
| `ip_life_followup_answers` | 질문 ID, 답변 원문, 답변/기억 안 남/건너뜀 상태, 답변 버전, 수정 시각 |
| `ip_life_followup_outputs` | 정리 버전, 사용한 원본·답변 버전, 정리 결과, 근거 참조, 반영 전후 값과 반영 시각 |
| 생성 요청 기록 | 요청 키, 입력 해시, 처리 상태, 엔진·모델·프롬프트 버전, 사용량·오류 정보 |

경험 UUID는 JSON 내부 값이므로 기존 경험 행을 대상으로 한 외래 키가 있다고 가정하면 안 된다. 서버가 학생 소유 프로필에 해당 경험이 실제로 존재하는지 확인해야 한다.

### 9.2 동기화 원칙

- 세션의 원본 해시는 해당 경험의 질문 관련 필드로 만든다. 다른 경험 수정만으로 불필요하게 세션을 무효화하지 않는다.
- 질문 생성은 원본 해시·답변 revision·질문 정책 버전 조합에 연결한다.
- 학생이 과거 답변을 고치면 이를 사용한 후속 질문과 정리를 ‘이전 답변 기준’으로 표시한다. 다음 생성에서는 최신 답변을 사용하며 이미 쓴 후속 답변은 보존한다.
- 질문 생성 후 원본이나 답변이 바뀌면 늦게 도착한 결과를 현재 결과로 채택하지 않는다.
- 최종 반영은 최신 프로필 revision과 대상 경험의 원본 해시를 함께 검사하고 원자적으로 저장한다.
- 원래 경험이 삭제되면 관련 생성 작업을 무효화하고 문답·정리의 접근을 차단한다. 이력 보관·최종 삭제는 수강생 데이터 보관 정책에 맞춘다.
- 계정 삭제와 기존 데이터 삭제 작업에 신규 테이블도 포함한다.

### 9.3 서버 인터페이스

전용 `/api/interview-life-followup`을 제안한다. 기존 `life_save`나 작성하기 AI에 임의 필드를 추가해 호출하지 않는다.

| 동작 | 역할 |
|---|---|
| `start` / `get` | 저장된 경험 확인, 세션 시작 또는 복원 |
| `save_answers` | 답변과 건너뜀 상태 저장, 답변 버전 충돌 검사 |
| `generate_questions` | 최신 입력으로 다음 묶음 생성, 요청 키로 중복 방지 |
| `status` | 진행 중 요청 조회, 서버가 안내하는 간격으로 확인 |
| `summarize` | 답변 근거가 있는 정리 초안 생성 |
| `apply` | 선택한 초안을 기존 경험에 충돌 검사 후 반영 |

초안 저장과 생성 요청을 분리한다. 생성에 실패해도 저장된 답변은 남는다. 더블 클릭·재시도·재접속에는 같은 요청 키를 재사용해 중복 생성을 방지한다.

## 10. AI 처리와 비용·응답 시간

현행 로컬 문서의 작성하기 AI는 서버 큐와 로컬 워커를 사용하는 경로를 설명한다. 이 방식의 실제 운영 가동 상태와 응답 시간은 별도 확인해야 한다. 기존 작성하기의 준비 조건과 결과 형식은 경험 탐색용 질문에 그대로 맞지 않는다.

**권장 구성은 검토된 질문 틀 + 전용 텍스트 생성 처리기다.** 인증, 요청 중복 방지, 상태 조회, 호출 제한 방식은 재사용하되 입력 조건·프롬프트·출력 검증은 별도로 만든다.

개발 초기에 대표 경험 10~20건으로 기존 워커의 대기 시간과 질문 품질을 확인한다. 상호작용에 충분한 응답 시간이 나오면 별도 작업 유형으로 확장하고, 그렇지 않으면 서버에서 호출하는 전용 생성 API를 검토한다. 모델과 서비스 선택은 이 검증 및 비용 산정 후 확정한다.

- 생성은 ‘다음 질문’ 또는 ‘내용 정리’의 명시적 실행 때만 한다. 입력할 때마다 AI를 호출하지 않는다.
- 한 번에 질문 묶음을 생성한다. 문장 하나마다 별도 요청하지 않는다.
- 동일 입력 결과는 재사용한다. 자동으로 다음 질문을 끝없이 생성하지 않는다.
- 학생별 동시 생성 1건을 기본으로 하고 일일 생성 한도와 전체 예산 한도를 설정한다. 구체 한도는 예상 인원과 실제 사용량으로 확정한다.
- 생성에는 선택한 경험과 관련 문답만 보낸다. 전체 이력이나 다른 학생 정보를 기본 입력으로 넣지 않는다.
- 지연·실패 때는 저장된 답변과 기본 질문을 이용할 수 있게 한다. 기존 인생그래프 작성은 계속 가능해야 한다.

비용은 ‘월 이용 학생 수 × 학생당 탐색 경험 수 × 경험당 질문·정리 요청 수 × 실측 요청 비용’으로 산정한다. 검증 전 무료 운영이나 특정 금액을 약속하지 않는다. 사용자 최종 확인 전에 유료 서비스 도입·푸시·배포를 실행하지 않는다.

## 11. 권한과 기능 범위

기존 면접반 포털 인증을 사용하며, 학생 ID를 클라이언트 요청 값만으로 신뢰하지 않는다. 모든 조회·저장·생성·반영에서 현재 학생의 경험인지 확인한다. 교사·관리자의 접근도 기존 역할 및 면접반 권한을 따른다.

신규 테이블의 접근 권한과 RLS를 함께 설계한다. 서비스 권한을 사용하는 서버 경로에서는 별도로 소유권을 검사한다. 브라우저에 서비스 키를 전달하지 않으며 신규 RPC의 실행 권한도 명시적으로 제한한다. 이는 Supabase의 [API 보안 가이드](https://supabase.com/docs/guides/api/securing-your-api)에 맞춰 실제 마이그레이션을 검토한다.

학생 답변은 분석할 자료로 취급한다. 답변 안의 지시문이 시스템 규칙이나 권한 검사를 바꾸게 하지 않는다. AI 출력은 질문 개수·길이·필수 필드·유효한 근거 참조를 서버에서 검증한다.

1차 적용은 면접반 인생그래프에 한정한다. 오프라인 수강생·온라인 관리반·인터넷 수강생 앱과 기존 교사·관리자 화면에는 새로운 UI나 이용 조건을 추가하지 않는다. 강사는 학생이 반영한 내용을 기존 인생그래프 조회에서 확인한다.

강의에서의 조별 질문 방식을 그대로 옮겨 학생 간 원문 공개 기능을 만들지는 않는다. 동료 문답과 강사용 문답 열람 화면은 별도 기획 대상으로 둔다.

## 12. 개발 작업 범위

| 영역 | 작업 |
|---|---|
| `interview-life-ui.js` | 경험별 진입 버튼, 저장 후 시작, 진행 표시, 정리 비교와 반영 |
| `interview-workspace.js` | DB 정리 영역에 전용 요청 인터페이스 전달, 화면 이동·미저장 처리 연결 |
| 신규 질문 UI·클라이언트 모듈 | 묶음별 문답, 저장·복원, 요청 중복 방지, 상태 조회 |
| 신규 API·검증 모듈 | 소유권·버전 검사, 질문 생성, 정리, 반영 계약 |
| AI 처리기 | 전용 작업 유형과 프롬프트, 구조화 결과 검증, 실패 시 기본 질문 |

| 기존 저장·AI 연계 | 최종 반영 후 관련 AI 입력 최신 여부 갱신, 기존 결과의 오래된 상태 처리 |
| 테스트 | 질문 품질, 권한, 충돌, 저장 복원, 기존 앱 기능 영향 |

`interview-ai.js`의 기존 작성하기 종류와 결과 형식에 질문 기능을 억지로 끼워 넣지 않는다. 현재 `mountLife` 호출에는 전용 AI 인터페이스가 없으므로 이를 명시적으로 연결해야 한다.

## 13. 단계별 도입

### 준비 단계: 생성 방식 검증

대표 경험에 대한 기대 질문과 피해야 할 질문을 만든다. 추상적 경험·실패·유년기·평범한 일상·타인의 도움·모순되는 답변을 포함한다. 기존 처리기의 지연과 비용을 측정해 생성 경로를 정한다.

### 1차: 경험 한 건을 깊게 작성하는 기능

포함: 경험별 진입, 답변에 따른 2~3개 질문, 저장·이어쓰기, 기억 안 남·건너뛰기, 정리 비교, 학생 확인 후 반영, 권한·충돌 검사, 사용량 제한.

새 경험을 발견하면 기존 새 경험 입력으로 연결한다. 첫 출시부터 여러 경험을 자동으로 함께 읽거나 성격 점수를 만들지 않는다.

### 2차: 경험 간 연결과 강사 지도

학생이 선택한 두 경험의 만족도·선택 기준 비교, 이후 사례 연결, 강사용 문답 근거 보기, 강사가 남기는 추가 질문을 검토한다. 교사·관리자 화면 변경은 이 단계의 별도 범위로 승인받는다.

### 공개 방식

서버와 화면에 기능 플래그를 두고 기본 비활성 상태로 개발한다. 테스트 계정에서 검증한 뒤 소수 수강생에게 적용한다. 기존 저장을 바꾸는 파괴적 마이그레이션은 피하고, 문제가 있으면 기능 플래그를 내려 기존 작성 흐름으로 복귀한다. 이때 저장된 문답은 보존한다.

푸시와 배포는 실제 변경 내역·검증 결과·예상 운영 비용을 검토한 후 사용자의 최종 확인을 받아 진행한다.

## 14. 완료 기준과 검증 시나리오

| 검증 상황 | 기대 결과 |
|---|---|
| 어필할 점이 비어 있는 경험 초안 | 저장 후 추가 질문을 시작할 수 있음 |
| 다른 기본 이력이 미완성 | 해당 경험 탐색이 막히지 않음 |
| ‘열심히 했다’ 같은 짧은 내용 | 구체적 행동을 묻고 장점을 먼저 단정하지 않음 |
| 이미 답한 내용을 다른 표현으로 작성 | 같은 정보를 다시 묻지 않음 |
| 건너뜀·기억 안 남 | 같은 질문을 강제로 반복하지 않음 |
| 실패하거나 결과가 불명확한 경험 | 성공을 가정하거나 성과를 만들어내지 않음 |
| 가정 질문에 대한 답변 | 실제 행동 사실과 구분해 저장·정리 |
| 답변 저장 후 종료·재접속 | 저장된 문답과 진행 상태 복원 |
| 네트워크 끊김·더블 클릭 | 기존 답변 보존, 중복 생성·중복 과금 요청 방지 |
| 다른 기기에서 원본 경험 수정 | 오래된 정리로 덮어쓰지 않고 비교 안내 |
| 과거 답변 정정 | 이전 입력에 기반한 질문·정리를 표시하고 최신 답변 반영 |
| 경험 삭제 중 생성 결과 도착 | 삭제된 경험에 결과를 적용하지 않음 |
| 다른 학생의 세션 ID로 요청 | 조회·생성·수정 모두 거부 |
| 글자 수·프로필 크기 한도 초과 | 원문 보존, 명확한 수정 안내, 무단 잘라내기 없음 |
| AI 지연·오류·예산 한도 도달 | 기존 경험 작성·문답 저장 가능 |
| 기능 비활성·기존 사용자 | 인생그래프 입력·그래프·제출·조회 기능 유지 |
| 다른 수강생 유형과 교사·관리자 화면 | 기존 UI와 주요 동작 유지 |

질문 품질은 정답 문장 일치로 검사하지 않는다. 실제 답변을 근거로 묻는지, 중복이 없는지, 확인되지 않은 사실을 가정하지 않는지 검토한다. 작은 고정 사례 묶음으로 품질을 비교하고 실제 시범 사용의 질문·답변을 추가 평가한다.

시범 운영에서는 경험당 새로 확인된 구체적 사실 수, 중복 질문 비율, 건너뛰기와 중도 종료 지점, 정리 반영률, 학생 수정량, 생성 응답 시간과 비용을 측정한다. 글자 수 증가만으로 성공을 판단하지 않는다. 통과 기준과 목표 응답 시간은 대표 사례 검증 후 정한다.
