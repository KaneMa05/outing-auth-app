# 제출물 첨삭 게시판

교사 화면의 **면접반 → 피드백 관리**는 제출물 게시판을 먼저 표시한다. 열 순서는 **번호 · 학생 · 항목 · 차수 · 제출일 · 관리 · 처리상태**다. 자기소개·지원동기·공직관의 최신 제출을 한 줄씩 표시하고, 제목·학생 이름·수험번호·학생 ID 검색, 항목·처리 상태 필터, 30건 단위 페이지 이동을 제공한다. 기존 나의 DB와 미제출 답변 조회는 **학생별 전체 기록**에서 유지한다.

기본 목록에는 **관리자가 처리해야 하는 확인 대기 제출물만** 표시한다. 보완요청한 항목은 학생의 재제출을 기다리는 상태이므로 기본 목록에서 제외한다. 상단 **확인 대기 / 보완요청 / 첨삭완료 숫자**를 누르면 검색어·제출 항목을 유지한 해당 목록으로 이동하며, **제출물 게시판으로**를 누르면 확인 대기로 돌아온다. 기록은 삭제하지 않으며, 학생이 다시 제출하면 기본 목록에 나타난다. 기존 DB의 상태별 조회로 페이지 분할과 건수를 계산한다.

## 첨삭과 학생 확인

1. 관리 열에는 **첨삭 / 삭제**를 나란히 표시한다. 삭제 확인 후 해당 제출 회차를 게시판에서 제외하며, 학생 원문과 첨삭 이력은 보존한다. 학생이 같은 답변을 다시 제출해도 새 회차로 목록에 나타난다. 조회 전용 계정에는 삭제를 표시하지 않는다.

목록에서 **첨삭**을 누르면 별도 창에서 해당 제출물만 열린다. AI 생성 기록은 표시하거나 요청하지 않는다. 새 창도 교사 세션과 조회·쓰기 권한을 확인하며, 팝업 차단 시 직접 열기 링크를 제공한다.
2. 제출 원문에서 문장을 선택해 **밑줄 / 빨간 취소선 / 괄호**를 누른다. 코멘트는 원문의 원하는 위치를 클릭해 바로 입력한다. 별도 삽입 버튼은 없으며 학생 원문은 보존한다.

글자색은 원문 문장을 선택하거나 원문 안의 코멘트를 누른 뒤 **글자색 ▾**의 빨강·파랑·검정·초록·보라 5색 색상표에서 클릭하면 바로 적용한다. 별도 적용 버튼은 없다. 같은 부분에 색을 다시 적용하면 마지막 색을 사용한다. 글자색도 저장·회차 기록·학생 화면에 함께 반영한다.

3. 처리는 **보완요청 / 첨삭완료 (수고하셨습니다.)** 중 선택하고 **첨삭 저장 · 학생에게 전달**을 누른다. 목록으로 돌아오면 기존 검색·필터·페이지를 유지하며 상태를 갱신한다. 별도 표시 목록·메모 입력란·총평 칸은 없다. 원문 안의 코멘트에는 `교사:` 접두사·앞뒤 괄호·× 버튼을 표시하지 않는다. 코멘트는 그 자리에서 수정하며, 삭제할 때는 글자를 지우고 저장한다. 선택한 서식은 **선택 표시 지우기**, 직전 변경은 **되돌리기**로 취소한다.
4. 학생은 해당 작성 화면에서 첨삭을 확인한다. 재제출 전후의 원문·첨삭은 회차별 기록에 남는다.

자기소개·지원동기·공직관의 학생 제출과 재제출은 2026-11-20부터 가능하도록 제출 제한을 해제했다. 기존 11/23 이후 제출 가능 안내도 삭제했다. 빈 답변·이용 권한·저장 중 중복 클릭 검증은 유지한다.

표시와 코멘트는 원문 기준 Unicode 코드 포인트 범위로 저장한다. 코멘트는 글자 사이에도 삽입할 수 있고, 앞에 코멘트를 넣어도 뒤쪽 원문의 위치는 변하지 않는다. 기존 텍스트 피드백은 원문 끝의 코멘트로 표시하며 보존한다. 사용자 HTML을 실행하지 않으며, 교사가 학생 원문을 변경하지 않는다. 재제출 후에도 이전 표시에는 이전 원문을 연결한다. 표시는 최대 100개이며 각 메모는 최대 1,000자다. 미저장 이탈 확인, 저장 실패 시 입력 유지, revision 충돌 처리는 기존 저장 흐름을 따른다.

게시판 API는 기존 교사 세션의 `interview.read`, 첨삭 저장은 `interview.write` 권한을 검사한다. 브라우저 DB 역할에는 새 RPC 실행 권한이 없으며, 서버의 검증된 actor만 기존 service_role 경로로 접근한다. 게시판 목록에는 답변 본문을 포함하지 않는다.

## 로컬 검증

- `npm run test:interview`: 기존 면접 기능 회귀 및 첨삭/게시판 DB·API 테스트.
- `node tests/release-safety.test.js`: 설정 보호, 서비스 워커 자산 및 API 캐시 제외.
- `node scripts/interview-prep-ui-qa.cjs`: 격리된 메모리 Postgres와 실제 로컬 API를 사용하는 교사·학생 브라우저 흐름.
- `node scripts/interview-prep-ui-qa.cjs --writing-board-only`: 별도 창·팝업 차단·권한·AI 기록 미호출·색상표·저장 실패/재시도·재조회·상태 갱신·학생 첨삭 조회/임시저장 및 PC/휴대폰 화면 집중 검증. 테스트 의존성 경로는 `PGLITE_MODULE`, `PLAYWRIGHT_MODULE`로 지정할 수 있다.

2026-11-20 검증: 첨삭/게시판·작성·회차·학생별 조회 DB/API 테스트와 집중 브라우저 검증, 로컬 빌드를 확인했다. 확인 대기만 표시·보완요청/완료 건수 클릭·기본 목록 복귀·검색 조건 유지·페이지 분할·재제출 복귀를 포함한다. 전체 브라우저 회귀 테스트는 기출 질문 저장의 입력 검증 단계에서 중단되며, 동일한 실패를 변경 전 HEAD 파일로도 재현했다. 전체 마이그레이션 검증은 기존 `20261110074450_interview_access_products.sql`의 함수 정의 확인 단계에서 중단된다. 해당 기존 실패를 이번 변경에서 수정하지 않았다.

브라우저 결과는 `.tmp/interview-qa/annotation-*.png`와 `student-annotation-feedback-mobile.png`에 저장한다. 테스트 중 운영 DB나 외부 AI는 호출하지 않는다. 로컬 빌드 후 기존 `config.js`를 원래 바이트로 복원하여 작업 폴더의 설정을 보존한다.

## 운영 반영 순서 — 사용자 최종 확인 후

1. `20261120050820_interview_writing_board_delete.sql`을 먼저 적용한다. 게시판 제외 이력과 관리자 삭제 RPC를 추가하고, 숨긴 제출물의 재제출을 허용한다. 원문·첨삭·기존 제출 이력은 보존한다.
2. 첨삭 모듈, 게시판, 새 `interview-writing-review.html`·JS, 갱신한 CSS·학생/관리자 진입 모듈을 함께 배포한다. 같은 체크아웃에 있는 별도 작업 변경은 이번 변경과 따로 검토한다.
3. 허가된 테스트 계정에서 제출 → 교사 첨삭 → 학생 확인을 점검한다.

프런트엔드를 이전 버전으로 되돌려야 해도 새 DB 열과 기록은 보존한다. 첨삭 JSON을 모르는 이전 화면에서도 텍스트 피드백은 계속 동작한다. 운영 적용 결과는 `docs/releases/20261120-feedback-worker-production.txt`에 기록한다.
