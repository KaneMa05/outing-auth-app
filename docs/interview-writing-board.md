# 제출물 첨삭 게시판

교사 화면의 **면접반 → 피드백 관리**는 제출물 게시판을 먼저 표시한다. 열 순서는 **번호 · 학생 · 항목 · 차수 · 제출일 · 관리 · 처리상태**다. 자기소개·지원동기·공직관의 최신 제출을 한 줄씩 표시하고, 제목·학생 이름·수험번호·학생 ID 검색, 항목·처리 상태 필터, 30건 단위 페이지 이동을 제공한다. 기존 나의 DB와 미제출 답변 조회는 **학생별 전체 기록**에서 유지한다.

기본 목록에는 **관리자가 처리해야 하는 확인 대기 제출물만** 표시한다. 보완요청한 항목은 학생의 재제출을 기다리는 상태이므로 기본 목록에서 제외한다. 상단 **확인 대기 / 보완요청 / 첨삭완료 숫자**를 누르면 검색어·제출 항목을 유지한 해당 목록으로 이동하며, **제출물 게시판으로**를 누르면 확인 대기로 돌아온다. 기록은 삭제하지 않으며, 학생이 다시 제출하면 기본 목록에 나타난다. 기존 DB의 상태별 조회로 페이지 분할과 건수를 계산한다.

## 첨삭과 학생 확인

1. 관리 열에는 **첨삭 / 삭제**를 나란히 표시한다. 삭제 확인 후 해당 제출 회차를 게시판에서 제외하며, 학생 원문과 첨삭 이력은 보존한다. 학생이 같은 답변을 다시 제출해도 새 회차로 목록에 나타난다. 조회 전용 계정에는 삭제를 표시하지 않는다.

목록에서 **첨삭**을 누르면 사용 중인 모니터의 작업 영역 가운데에 별도 창을 연다. AI 생성 기록은 표시하거나 요청하지 않는다. 새 창도 교사 세션과 조회·쓰기 권한을 확인하며, 브라우저가 새 창 열기를 지원하지 않거나 창이 보이지 않을 때 사용할 직접 열기 링크를 표시한다. 목록 자동 갱신 중에도 첨삭 클릭은 실행한다. 첨삭 창 본문에서는 상단 학생 정보·닫기 영역, 제출 차수·제출일·회차 기록과 편집·회차 안내 문구를 생략한다. 학생 화면과 학생별 전체 기록에는 기존 제출 정보와 회차 기록을 유지한다.
2. 제출 원문에서 문장을 선택해 **밑줄 / 빨간 취소선 / 괄호**를 누른다. 코멘트는 원문의 원하는 위치를 클릭해 바로 입력한다. 별도 삽입 버튼은 없으며 학생 원문은 보존한다.

글자색은 원문 문장을 선택하거나 원문 안의 코멘트를 누른 뒤 **글자색 ▾**의 빨강·파랑·검정·초록·보라 5색 색상표에서 클릭하면 바로 적용한다. 기본 글자색은 파랑이다. 코멘트는 원문과 같은 글꼴·크기·굵기·행간으로 표시하며, 별도 배경·테두리·추가 여백 없이 글자색만 적용한다. 입력 커서는 일반 글과 같은 어두운 색이고, 코멘트를 모두 지우면 빈 박스나 여백이 남지 않는다. 별도 적용 버튼은 없다. 같은 부분에 색을 다시 적용하면 마지막 색을 사용한다. 글자색도 저장·회차 기록·학생 화면에 함께 반영한다.

3. 처리는 **보완요청 / 첨삭완료 (수고하셨습니다.)** 중 선택하고 **첨삭 저장 · 학생에게 전달**을 누른다. 버튼이 **첨삭 저장 중… → ✓ 첨삭 저장 완료**로 바뀌며, 완료는 초록색으로 표시하고 버튼 바로 아래에 저장 결과를 안내한다. 별도 첨삭 창에서는 저장 성공 직후 저장 완료 버튼 옆에 **창 닫기**가 나타나며, 누르면 해당 창만 닫힌다. 저장 중·실패·재수정 상태에서는 닫기 버튼을 숨긴다. 완료 뒤 다시 수정하면 저장 버튼을 활성화하고 이전 저장 완료 메시지를 지운다. 작성 중 미저장 안내 문구는 표시하지 않는다. 실패한 경우 입력을 보존하며 **첨삭 다시 저장**으로 재시도할 수 있다. 목록으로 돌아오면 기존 검색·필터·페이지를 유지하며 상태를 갱신한다. 별도 표시 목록·메모 입력란·총평 칸은 없다. 원문 안의 코멘트에는 `교사:` 접두사·앞뒤 괄호·× 버튼을 표시하지 않는다. 코멘트는 그 자리에서 수정하며, 삭제할 때는 글자를 지우고 저장한다. 선택한 서식은 **선택 표시 지우기**, 직전 변경은 **되돌리기**로 취소한다.
4. 학생은 해당 작성 화면에서 첨삭을 확인한다. 재제출 전후의 원문·첨삭은 회차별 기록에 남는다. 학생 화면의 **회차별 제출·피드백 기록**은 답변 작성·제출 안내와 AI 초안 영역 다음인 페이지 맨 아래에 배치한다. 기록은 기존처럼 펼쳤을 때 불러오며, 학생별 전체 기록을 보는 관리자 화면의 배치는 유지한다.

자기소개·지원동기·공직관의 학생 제출과 재제출은 **2026-11-23 00:00(한국 시간)**부터 가능하다. 그전에도 임시저장·저장은 가능하다. 개시 전 제출 버튼의 `11/23 00시부터` 표시와 함께 학생 작성 화면에 정확한 시작 시각과 저장 가능 안내를 표시한다. 화면을 열어둔 상태에서도 작성 중인 입력을 유지한 채 개시 시각 제한을 해제한다. 서버도 같은 개시 시각을 검사하므로 기기 시각이나 버튼 상태를 바꿔 조기 제출할 수 없다. 핵심인성 질문의 공개/작성 권한, 빈 답변·이용 권한·저장 중 중복 클릭 검증은 유지한다.

학생이 답변을 제출하면 **해당 항목은 교사의 현재 회차 피드백을 받은 뒤에만 다시 제출할 수 있다**. 핵심인성은 질문별로 적용하며, 다른 항목의 첫 제출은 제한하지 않는다. 대기 중에는 **교사 피드백 대기 중** 버튼과 안내를 표시하고 임시저장·저장은 계속 허용한다. 보완요청 또는 첨삭완료 피드백을 받은 뒤 작성 화면을 다시 열면 재제출할 수 있고, 새 회차를 제출하면 다시 피드백을 기다린다. 이전 회차에서 넘어온 피드백과 작업본의 임시저장/저장 상태는 새 제출을 허용하는 근거로 사용하지 않는다.

사용자가 선택한 예외에 따라 **관리자가 게시판에서 삭제한 제출물은 피드백 전에도 다시 제출할 수 있다**. 삭제 예외는 해당 제출 revision에만 적용하며, 재제출한 새 회차에는 적용되지 않는다. 서버가 `awaiting_feedback`을 계산해 반환하고 기존 작성 RPC의 행 잠금 안에서 새 회차를 검사한다. 대기 중 변경 제출은 `feedback_pending`/HTTP 409로 거부하며 원문·작업본·피드백·회차 이력을 변경하지 않는다. 동일 제출의 중복 요청은 기존 결과만 반환한다.

표시와 코멘트는 원문 기준 Unicode 코드 포인트 범위로 저장한다. 코멘트는 글자 사이에도 삽입할 수 있고, 앞에 코멘트를 넣어도 뒤쪽 원문의 위치는 변하지 않는다. 기존 텍스트 피드백은 원문 끝의 코멘트로 표시하며 보존한다. 사용자 HTML을 실행하지 않으며, 교사가 학생 원문을 변경하지 않는다. 재제출 후에도 이전 표시에는 이전 원문을 연결한다. 표시는 최대 100개이며 각 메모는 최대 1,000자다. 미저장 이탈 확인, 저장 실패 시 입력 유지, revision 충돌 처리는 기존 저장 흐름을 따른다.

게시판 API는 기존 교사 세션의 `interview.read`, 첨삭 저장은 `interview.write` 권한을 검사한다. 브라우저 DB 역할에는 새 RPC 실행 권한이 없으며, 서버의 검증된 actor만 기존 service_role 경로로 접근한다. 게시판 목록에는 답변 본문을 포함하지 않는다.

- `npm run test:interview`: 기존 면접 기능 회귀 및 첨삭/게시판 DB·API 테스트.
- `node tests/release-safety.test.js`: 설정 보호, 서비스 워커 자산 및 API 캐시 제외.
- `node --test tests/interview-writing-schedule.test.cjs`: 한국 시간 개시 직전/정각/직후 API 제한, 임시저장·저장 및 기존 핵심인성 제출 유지.
- `node tests/interview-writing-feedback-gate.test.cjs`: 항목별 피드백 대기, 작업본 저장, 두 피드백 상태의 해제, 과거 피드백/삭제 예외 범위, 중복/동시 요청, API 오류와 서비스 전용 권한.
- `node scripts/interview-prep-ui-qa.cjs`: 격리된 메모리 Postgres와 실제 로컬 API를 사용하는 교사·학생 브라우저 흐름.
- `node scripts/interview-prep-ui-qa.cjs --writing-board-only`: 별도 창·팝업 차단·권한·AI 기록 미호출·색상표·저장 실패/재시도·재조회·상태 갱신·학생 첨삭 조회/임시저장 및 PC/휴대폰 화면 집중 검증. 테스트 의존성 경로는 `PGLITE_MODULE`, `PLAYWRIGHT_MODULE`로 지정할 수 있다.

2026-11-20 검증: 첨삭/게시판·작성·회차·학생별 조회 DB/API 테스트와 집중 브라우저 검증, 로컬 빌드를 확인했다. 확인 대기만 표시·보완요청/완료 건수 클릭·기본 목록 복귀·검색 조건 유지·페이지 분할·재제출 복귀를 포함한다. 전체 브라우저 회귀 테스트는 기출 질문 저장의 입력 검증 단계에서 중단되며, 동일한 실패를 변경 전 HEAD 파일로도 재현했다. 전체 마이그레이션 검증은 기존 `20261110074450_interview_access_products.sql`의 함수 정의 확인 단계에서 중단된다. 해당 기존 실패를 이번 변경에서 수정하지 않았다.

브라우저 결과는 `.tmp/interview-qa/annotation-*.png`와 `student-annotation-feedback-mobile.png`에 저장한다. 테스트 중 운영 DB나 외부 AI는 호출하지 않는다. 로컬 빌드 후 기존 `config.js`를 원래 바이트로 복원하여 작업 폴더의 설정을 보존한다.

## 운영 반영 순서 — 사용자 최종 확인 후

1. 기존 적용된 `20261120050820_interview_writing_board_delete.sql` 등 과거 마이그레이션은 재실행하지 않는다. 새 후보 빌드와 격리 API/Postgres 시나리오를 먼저 검증한다.
2. 새 오류 코드 매핑과 학생 모듈을 포함한 앱/API를 전환하고, 같은 반영 작업에서 `20261120071538_interview_writing_feedback_before_resubmission.sql`을 적용한다. 새 UI는 기존 응답에도 대기 상태를 추론하며, DB 적용 후 관리자 삭제 예외와 서버의 동시 제출 제한까지 활성화된다. 원문·첨삭·기존 회차는 보존한다.
3. 운영 함수 정의·서비스 전용 권한을 확인한다. 제출 → 피드백 대기 → 교사 첨삭 → 재제출, 관리자 삭제 예외는 격리 fixture에서 검증하고, 운영 학생 자료로 시험하지 않는다.

프런트엔드를 이전 버전으로 되돌려야 해도 새 DB 열과 기록은 보존한다. 첨삭 JSON을 모르는 이전 화면에서도 텍스트 피드백은 계속 동작한다. 최초 통합 운영 결과는 `docs/releases/20261120-feedback-worker-production.txt`, 제출 개시 시각·일반 글 코멘트·저장 후 닫기를 포함한 승인 배포 결과는 `docs/releases/20261120-feedback-final-approved-production.txt`에 기록한다. 학생 제출 안내·현재 피드백 후 재제출·학생 기록 하단 배치의 운영 반영은 `docs/releases/20261120-writing-feedback-gate-production.txt`에 기록한다.
