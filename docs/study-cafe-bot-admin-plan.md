# 스터디카페 봇 관리자 기능 기획안

작성일: 2026-09-11

관리자가 기존 봇 5개의 운영 상태를 관리하고, 각 봇의 보유 포인트로 기존 상점 아이템을 구매·착용할 수 있도록 한다. 1차는 관리자 수동 구매로 진행하며, 봇이 스스로 상품을 고르는 자동 구매는 후속 기능으로 둔다.

사용자 확인 사항: 대상은 이미 운영 중인 봇 5개다. 기존 봇에 관리자 조작 화면을 연결하는 작업이며, 봇 생성·재등록·교체·초기화는 범위에 포함하지 않는다. 기존 ID, 운영 설정, 공부 기록, 지갑, 보유·착용 아이템을 그대로 이어서 사용한다. 관리자가 변경한 설정만 해당 봇에 반영한다.

## 1. 현재 구조에서 확인한 사항

아래는 로컬 코드와 SQL 기준이다. 운영 DB의 실제 적용 상태, 현재 잔액·보유 아이템·가동 여부는 구현 전 읽기 전용으로 확인해야 한다.

| 봇 ID | 관리용 이름 | 직렬 |
| --- | --- | --- |
| 29999701 | 김도윤 | 공채 |
| 29999702 | 이서준 | 공채 |
| 29999703 | 정유진 | 공채 |
| 29999704 | 박지훈 | 함정요원 항해 |
| 29999705 | 최민재 | 함정요원 기관 |

- 봇 설정은 `private.study_cafe_agents`, 공부 기록과 좌석은 기존 수강생 테이블을 사용한다.
- 봇은 `online_managed` 유형이며, 하루 3개 시간대에 분 단위 작업으로 공부·휴식·퇴실을 처리한다. 방문별 임시 닉네임을 생성한다.
- 관리자 스터디카페에는 현황 조회, 공부 종료, 좌석 해제 등이 있으나 봇 설정·상점 전용 기능은 없다. 일반 좌석 해제만 하면 다음 자동 실행에서 봇이 돌아올 수 있다.
- 상점에는 상품, 지갑, 포인트 내역, 보유 아이템, 착용 데이터와 구매·착용 처리 함수가 있다.
- 현재 학생용 상점 접근과 포인트 적립 대상은 `lecture`로 제한된다. 봇 자동 실행에는 포인트 적립 호출이 없다. 따라서 공부 기록이 있다고 포인트가 이미 적립됐다고 가정해서는 안 된다.
- 다른 이용자 좌석에 보이는 착용 정보는 별도 확인이 필요하다. 현재 상점 장비 조회는 주로 본인 기준이므로 구매 저장과 공개 좌석 표시를 각각 검증한다.

근거 파일: `supabase/add-study-cafe-agents.sql`, `api/study-cafe-admin.js`, `teacher.js`, `api/study-cafe.js`, `study-shop.js`, `supabase/add-study-cafe-shop.sql`, `supabase/expand-study-cafe-shop-category-access.sql`, `supabase/add-study-cafe-hair-shop.sql`.

## 2. 관리자 화면

진입 경로: **관리자 → 온라인 스터디카페 → 봇 관리**. 관리자에게만 진입 버튼과 기능을 제공한다.

### 봇 목록

5개 봇을 한 화면에서 확인한다.

| 영역 | 표시·조작 |
| --- | --- |
| 식별 | 관리용 이름, 봇 ID, 현재 표시 닉네임, 캐릭터 미리보기 |
| 운영 | 운영 켜짐/꺼짐, 공부 중/휴식 중/퇴실, 현재 좌석·과목 |
| 포인트 | 보유 포인트, 오늘 적립, 오늘 순공시간, 최종 정산 시각 |
| 꾸미기 | 착용 아이템 요약, 상점·보관함 열기 |
| 관리 | 상세 설정, 운영 중지/재개 |

가동 설정과 실제 접속 상태를 구분한다. 운영 켜짐이더라도 시간표 밖이면 퇴실 상태일 수 있다. 오류가 난 잔액은 0P로 표시하지 않고 “조회 실패”와 재시도를 제공한다.

### 봇 상세

- **기본 정보:** 관리용 이름, 직렬·공부 과목, 캐릭터 기본 색상, 닉네임 자동/고정 설정. 기본값은 현재 자동 방식 유지.
- **운영 설정:** 운영 켜짐/꺼짐, 기존 3개 공부 시간대, 선호 좌석. 시간대는 한국 시간으로 보여주고 익일 시각을 구분한다. 시간대 역전·겹침과 허용 좌석 범위를 검사한다.
- **상점:** 현재 판매 상품, 가격, 보유/미보유/착용 상태, 구매 가능 여부. 기존 상점 상품 정보를 공유한다.
- **보관함:** 구매한 아이템 착용·해제, 캐릭터·좌석 미리보기.
- **활동 내역:** 포인트 적립·사용, 구매·착용, 설정 변경과 처리 관리자.

운영 중지는 진행 중 공부를 정상 종료·정산하고 좌석을 반환하며 이후 자동 재입실을 막는다. 재개는 현재 시간표에 따라 다음 정상 실행부터 동작한다. 중지 상태에서도 보유 포인트로 구매·꾸미기는 가능하다. 설정 저장은 다음 자동 실행에 반영하며, 구매·착용은 성공 직후 저장 결과를 보여준다.

## 3. 구매와 착용 흐름

1. 관리자가 목록에서 봇을 선택한다.
2. 서버가 미정산 포인트를 정산하고 최신 잔액·상품·보유 목록을 반환한다.
3. 관리자가 상품을 선택하면 대상 봇, 상품 가격, 구매 후 잔액과 미리보기를 표시한다.
4. `구매` 또는 `구매 후 착용`으로 진행한다.
5. 성공하면 잔액·보관함·착용 상태·내역을 갱신하고 공개 좌석에도 반영한다.

예시: **김도윤 · 보유 1,200P → 500P 아이템 구매 → 잔액 700P**. 이 숫자는 동작 설명용이며 실제 잔액·상품 가격이 아니다.

- 포인트 부족: 부족한 포인트를 보여주고 구매를 막는다. 서버에서도 최신 잔액을 다시 확인한다.
- 이미 보유: 추가 차감 없이 보유 상태를 표시하고 착용을 제공한다.
- 판매 종료·가격 변경: 최신 상품 정보로 갱신하고 변경 내용을 확인한 후 구매하게 한다.
- 의상·머리·머리 장식·의자는 슬롯별 하나, 책상 장식은 현재 규칙인 최대 4개를 따른다. 운영 DB의 머리 상점 적용 여부를 확인한다.
- `구매 후 착용`은 한 트랜잭션으로 처리한다. 슬롯 초과 등 착용 불가 시 구매도 확정하지 않으며, 관리자가 `구매만`을 선택할 수 있다.
- 응답 유실·중복 클릭·동시 관리자 요청에도 중복 차감이나 음수 잔액이 생기지 않는다. 실패·시간 초과 시 입력한 대상 봇과 선택 상품을 유지하고 실제 처리 결과를 재조회한다.

## 4. 포인트 운영 정책

- **지갑은 봇별 독립:** 다른 봇 또는 수강생의 포인트를 사용할 수 없다.
- **적립 기준:** 기존과 동일하게 순공시간 30분당 5P. 휴식·퇴실 시간은 제외한다.
- **날짜 기준:** 한국 시간 오전 4시. 날짜가 바뀌어도 보유 잔액은 유지하고 오늘 적립 수치만 새로 계산한다.
- **자동 정산:** 기존 봇 실행 과정에 중복에 안전한 정산을 연결한다. 관리자 화면을 열지 않은 날도 적립되도록 한다.
- **경계·장애 처리:** 마지막 정산일을 기록하고 오전 4시 경계, 여러 날의 작업 중단, 재시도에도 미정산 공부일을 순서대로 처리한다. 당일만 계산하는 기존 함수를 그대로 호출하는 것으로는 지난 날짜 누락을 해결할 수 없다.
- **기존 포인트 연결:** 운영 중인 봇의 실제 지갑·적립·구매 내역을 조회하여 현재 보유 포인트를 그대로 사용한다. 잔액을 0으로 초기화하거나 새로운 시작 잔액을 부여하지 않는다. 정산 연동 보완은 실제 누락 여부를 확인한 뒤 기존 지급분과 중복되지 않게 처리하며, 과거 공부 기록을 임의로 포인트로 환산하지 않는다.

## 5. 구현 방향과 영향 범위

- 기존 봇 등록 데이터를 조회하여 관리 목록을 구성한다. 봇 설치·초기화 SQL을 재실행하거나 코드의 초기 이름·시간표·과목으로 운영 데이터를 덮어쓰지 않는다. 기존 자동 운영 작업에 필요한 관리 기능만 연결한다.
- 봇의 수강생 유형을 바꾸지 않는다. 학생용 상점 접근 범위는 유지하고, 관리자 전용 요청에서 등록된 봇만 허용한다.
- 관리자 세션을 검증한 서버가 봇 목록을 조회하고 구매·착용·설정을 처리한다. 화면 버튼 숨김뿐 아니라 모든 요청에서 관리자 권한과 실제 봇 등록 여부를 확인한다.
- `private.study_cafe_agents`는 브라우저에 직접 공개하지 않는다. 서버 전용 접근 함수는 필요한 작업만 허용하고 서비스 역할에만 실행 권한을 준다.
- 상품·지갑·내역·보관함·착용 테이블을 재사용한다. 봇 정산 상태와 관리자 작업 이력은 필요한 만큼 추가한다.
- 기존 구매 함수의 지갑 잠금·보유 중복 검사·포인트 내역을 활용하되, 봇 작업 검증과 구매 후 착용을 묶는 서버 전용 처리를 추가한다. 구매·설정 변경 이력은 해당 변경과 함께 확정한다.
- 정산·운영 중지·자동 실행·구매 사이의 동시 요청 처리 순서를 정하고 봇 단위로 충돌을 방지한다. 중지 직후 이전 자동 작업이 좌석을 다시 만들지 않게 한다.
- 닉네임·색상 등 자동 실행이 덮어쓰는 필드를 확인하고, 관리자가 저장한 고정 설정과 구매 장비가 다음 실행·재입실·날짜 변경에도 유지되게 한다.
- 수강생 화면에는 봇의 공개 캐릭터·좌석 표현에 필요한 착용 정보만 전달한다. 잔액, 보유 목록, 관리자 설정은 공개 응답에 포함하지 않는다.
- 기존 좌석 조회·캐릭터 렌더링 경로를 활용하고 착용 변경 시 갱신한다. 장비 추가 조회는 좌석마다 실행하지 않고 묶어서 처리한다.
- 봇 5개 목록은 일괄 조회하고, 상세·상점·내역은 선택 시 불러온다. 기존 분 단위 작업을 활용하며 별도 고빈도 실행 작업은 추가하지 않는다. 정산 실패가 공부·좌석 운영 전체를 중단시키지 않게 하고 재처리 상태를 남긴다.
- 다른 학생 유형의 상점 권한과 교사 화면 기능을 확대하지 않는다. 봇 통계·랭킹 정책 변경은 이번 범위에서 별도로 추가하지 않는다.

예상 변경 위치: `teacher.js`와 관리자 스타일·화면 연결, 관리자 API, 봇 운영 SQL·정산 처리, 공개 좌석 장비 조회·렌더링 경로, 관련 테스트. 기존 상점 화면 전체를 복제하기보다 상품·미리보기 등 공통 부분을 재사용한다.

## 6. 단계와 완료 기준

### 1차 필수 범위

봇 5개 목록·상세, 운영 중지/재개, 기본 설정·시간표, 봇별 잔액·자동 적립, 수동 구매·구매 후 착용·해제, 공개 좌석 반영, 관리자 작업 내역.

구현 순서:

1. 운영 DB 적용 상태·잔액·정산 이력·장비 표시 경로를 읽기 전용으로 확인한다.
2. 봇 권한 검증, 정산, 구매·착용, 운영 중지의 데이터 처리를 구현한다.
3. 관리자 목록·상세·상점 화면과 공개 좌석 반영을 연결한다.
4. 아래 완료 기준으로 검증하고 빌드한다.
5. 변경 결과와 DB 적용 순서·복구 방법을 제시한 후 사용자의 최종 확인을 받아 푸시·배포한다.

완료 기준:

- 기능 적용 전후 봇 5개의 ID·설정·공부 기록·포인트·아이템이 보존되고, 관리자 화면에 현재 운영 데이터가 표시된다.
- 관리자만 정확히 등록된 5개 봇을 관리할 수 있고, 일반 학생 ID를 바꿔 넣은 요청은 거절된다.
- 보유 포인트로 구매 시 해당 봇의 잔액만 정확히 차감되고 상품·내역이 함께 저장된다.
- 부족 잔액, 중복 구매, 동시 구매, 응답 유실 후 재시도에서 데이터가 일관된다.
- 착용 제한을 지키며, 구매 후 착용 실패 시 포인트·보유 상태가 부분적으로 변경되지 않는다.
- 관리자 화면을 닫아도 정상 적립되고, 오전 4시·작업 중단·재시도에서 중복 적립과 누락이 없다.
- 운영 중지 후 다음 자동 실행에도 재입실하지 않으며 재개는 시간표를 따른다.
- 장비와 고정 닉네임은 다음 자동 실행과 재입실 후에도 유지된다.
- 다른 이용자 화면에서도 봇의 구매 장비가 보이고, 실제 이용자의 좌석·공부 타이머·상점 사용에는 영향이 없다.
- 봇 기능 미적용·오류 시 기존 관리자 현황과 학생 스터디카페는 계속 사용할 수 있다.

### 후속 확장

아이템 구매 우선순위·최소 잔액·일일 예산을 설정하는 자동 구매, 여러 봇 일괄 꾸미기는 실제 운영 후 필요에 따라 추가한다.

이 문서는 기획안이며 앱 코드나 운영 DB를 변경하지 않는다. 푸시·배포는 사용자 최종 확인 이후 진행한다.
